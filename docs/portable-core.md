# 通用核心与本仓特有

这份清单回答一个问题：**这套工作流装到第二个仓库时，哪些应该原样搬过去，哪些必须重写。**

维护者已经确认，这套东西不是给外人看的样板，是他本人的通用工作流，以后所有仓库、所有沟通都要用。
所以本仓的形状不是终点，只是第一块底盘。

> **这张表是当前推断，不是结论。** 目前只有一个接入方，证据不足以把它写成机器约束——写死等于把
> 猜测当结论。第二个仓接入时按实际情况订正这份文档，那一次才是它第一次被验证。

## 读这份文件需要先知道的词

| 词 | 意思 |
|---|---|
| **本仓** | `delivery-spec-runtime`。这套工作流本身住在这里，别的仓库把它作为 Git 子模块接进去用。 |
| **接入方** | 接了这套工作流的下游仓库。目前只有一个。 |
| **工件** | 走一遍流程会产出的那批文件（方案文档、测试方案、验收记录、各种状态 JSON）的统称。 |
| **门** | 必须由人表态才能过的节点。人的视角只有三道：立项、方案、验收。 |
| **事项记录** | `openspec/intake/` 下的一份份记录，每份记一件事的来龙去脉。 |
| **陌生读者关** | 把一段要长期留存的文字交给一个没读过本仓任何东西的会话读一遍，请它只圈看不懂的地方。 |

## 通用核心：换个仓库也应该原样成立

| 项 | 为什么它与仓库内容无关 |
|---|---|
| **三道门**（立项、方案、验收） | 「做不做、怎么做、认不认」是任何事项都要回答的三个问题。 |
| **事项记录** | 一件事的来龙去脉需要一个不依赖对话记忆的落点。这是维护者唯一会主动来找的资产。 |
| **独立评审**（另起一个不知道实施过程的会话逐条复查） | 本仓迄今唯一有拦截战果的机制：12 份评审记录查出 51 条问题，其中两条最严重的都发生在 agent 自查报「零问题」之后。它有效的原因与仓库内容无关——它换了一双眼睛。 |
| **陌生读者关** | 同上：它有效的原因是「写的人忘不掉自己已经知道的事」，这是人的性质，不是仓库的性质。 |
| **禁词名单** | 审读关负责发现「这个词读者看不懂」，名单负责让同一个词不再犯第二次。两者互补，都与内容无关。 |
| **「有读者才产出」这条判据** | 判断一份工件该不该存在的通用尺子：要么有代码真的读它并据此放行或拒绝，要么有人在某个确定场合真的会看它。 |
| **「写进机器才算数」这条纪律** | 由反例证明：一条只写进文档、没写进机器检查的要求，在本仓连续三单零执行。 |
| **证据按「能不能再跑一遍」分派** | 见下一节——这一条虽然通用，但它在不同仓库里的结论正好相反，所以单独说。 |
| **摆材料要附文件位置** | 人在门口只看到一屏摘要时，需要知道想细看该翻哪个文件。 |

## 一条通用规则，两种相反的结论：证据

这是目前已知**最关键的一处差异**，也是第二个仓接入时最容易踩空的地方。

**规则是通用的**：证据留不留，判据不是「它重不重要」，而是**「这次验证能不能再跑一遍」**。

- **可以重跑** → 不留运行日志。要复核就当场再跑一遍；存下来的日志无法证明它对应的是当前这版代码，
  留着只会让人以为有据可查。
- **不可重跑** → 必须记录。做完这一次就没了，那是唯一一次机会。

**但两个仓库落在规则的两侧**：

| | 本仓 | 维护者公司的仓库 |
|---|---|---|
| 验证方式 | 自动化测试，随时可重跑 | 没法写自动化测试，只能构造请求走一遍场景 |
| 落在规则哪一侧 | 全部「可重跑」 | 全部「不可重跑」 |
| 结果 | 不留任何运行日志 | 每一次验证都必须留记录 |

所以：**「记录验证过程」这个能力必须留在底盘上，只是在本仓恒为关闭。** 谁要是因为「本仓从来不用」
而把它删掉，公司仓接入的第一天就得重新造一遍——而那时丢掉的证据再也补不回来。

机器上的落点是任务状态里的 `replayable` 字段：新写入必须显式声明，不许吃缺省值。理由是
「这次验证能不能重跑」需要人判断，交给默认值回答等于没人回答过。

## 本仓特有：换个仓库大概率要改

| 项 | 为什么它是本仓特有的 |
|---|---|
| **工件的具体分层**（今天六层） | 分层是按「治理一套工作流」这件事的形状定的。一个非代码事项未必需要测试方案，也未必需要长期规范增量。 |
| **路由表里的路径前缀** | 全是本仓的目录名。 |
| **交付线七个站的站名** | 与本仓的机器契约一一对应。 |
| **各种状态文件的字段** | 同上。 |
| **哪些改动必须先走分析线** | 取决于本仓「改错一次会让此后每一单都建立在错门禁上」这个特点。别的仓库的重心不在这里。 |
| **指标子系统** | 零使用，去留本身还没裁。 |
| **禁词名单的具体条目** | 名单机制通用，但「哪个词碍眼」因人因仓而异。 |

## 还不知道属于哪一侧

- **快车道**（给低风险小改动的短流程）：本仓至今没真正用过，无法判断它是通用的还是多余的。
- **批准记录的形态**：现在按「人真实表态一次记一条」记，每份工件逐一记内容哈希。换成非代码事项之后，
  「工件内容哈希」这个概念还成不成立，没有证据。
- **陌生读者关的成本**：本仓实测一次约五分钟外加一轮订正。这个数字在文字量更大的仓库里会不会失控，
  未知。

## 第二个仓接入时该做什么

1. 先把上面「通用核心」那张表原样搬过去，一条都别改。
2. 逐条问「本仓特有」那张表：这一条在新仓里应该是什么样？
3. **优先确认证据那一条落在哪一侧**——它决定新仓要不要打开「记录验证过程」这个能力。
4. 把「还不知道属于哪一侧」那三条当成观察点，跑完第一个事项之后回来订正这份文档。
