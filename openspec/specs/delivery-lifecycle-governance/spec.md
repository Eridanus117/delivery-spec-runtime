# delivery-lifecycle-governance Specification

## Purpose

使 Runtime `delivery-change` 以独立方案提案和决策、绑定源码的实现 Review、内容寻址验收和先归档后 PR 的顺序完成可审计闭环。

> **MUST 与 SHALL 在本文件里同强度**，都表示「必须」。混用只是不同时期的写作习惯，没有分级含义。
> 本文件的仓内词汇统一解释在 `docs/glossary.md`。

## Requirements

### Requirement: 方案提案与决策必须是独立 Artifact

Schema MUST 在 05 中依次要求 `solution-proposal` 与 `solution-decision`，两者 MUST 保持为两份独立工件（理由：提案作者不能代替维护者作决定；写在同一份文件里，就没法区分「我建议」和「他同意」）。Proposal MUST 呈现现状、候选与 trade-off、落地后可感知的变化清单；Decision MUST 记录维护者选择、依据、拒绝方案和接受后果。

实施切片、迁移与回滚 MUST NOT 另立工件，MUST 写进 `07-实施任务/实施任务.md` 的对应一节（理由：它与任务清单同在方案决策之后产生、同是写给实施者看的，拆成两份的唯一后果是多出一份没有读者的文档）。

这一门的批准 MUST 按人真实表态的次数记，一次表态一条记录，覆盖当时的全部工件，且 MUST 逐份记录每份工件的内容哈希（理由：本条原先要求提案、决策、改造计划**三份各自计算内容哈希并分别批准**——第三份就是第 7 版被并进实施任务的那一份，于是一句「同意」被展开成多条各自签发的记录，读批准链的人分不清「表了几次态」和「表了一次被复制成几条」。改成按表态记之后，「改了哪一份就失效、并且能点名是哪一份」的定位能力靠逐份哈希保住，一份不丢）。

#### Scenario: 未决提案不得进入实施计划

- **WHEN** Proposal 缺少两个候选、Trade-off、推荐或未决问题，或者 Decision 未批准
- **THEN** `guard apply` 非零拒绝

#### Scenario: 一次表态只产生一条批准记录

- **WHEN** 维护者在方案门给出一次表态
- **THEN** 系统 MUST 记录一条批准，并 MUST 在其中逐份列出被覆盖工件的内容哈希；MUST NOT 为同一次表态签发多条各自独立的记录

### Requirement: Implementation Review 必须绑定完整实现范围

Review 状态 MUST 绑定 baseline commit、reviewed commit、baseline→reviewed 的全部实现路径、逐路径 SHA-256、聚合摘要、Reviewer、findings 和结论。当前路径或 commit 与记录不一致时 MUST stale。

#### Scenario: Review 遗漏实现文件

- **WHEN** reviewedPaths 少于或多于 baseline→reviewed 的实现路径集合
- **THEN** Review 写入非零拒绝

#### Scenario: Review 后实现变化

- **WHEN** Review PASS 后任一受审实现路径变化、删除，或者 reviewed commit 不再是当前 HEAD 的祖先
- **THEN** Review inspect 和后续 Acceptance 非零拒绝并报告 stale；只增加当前 Change 生命周期证据或同步后的长期 spec 不使 Review stale

#### Scenario: Finding 未解决

- **WHEN** 存在任意 OPEN finding
- **THEN** Review 不能记录 PASS

### Requirement: Acceptance 必须内容寻址当前 Review

Acceptance State MUST 绑定 PASS 且未 stale 的 Review 摘要、`task-state.json` 摘要、验收正文摘要和 reviewed commit。全部实现任务 verified、Review 当前且验收正文严格 PASS 后才能写入；Review、任务状态或正文后续变化时 MUST stale。`acceptedAt` MUST 晚于 `reviewedAt`。

#### Scenario: 验收引用旧 Review

- **WHEN** Review、实现路径、task state 或验收正文在 Acceptance 后变化
- **THEN** acceptance guard 非零拒绝

### Requirement: Archive 必须在 PR 前由严格状态放行

Archive Readiness MUST 绑定当前 Acceptance、Spec Sync 输入输出摘要、strict validation、cleanup PASS 证据和 `prStarted=false` 维护者声明，且 `attestedAt` MUST 晚于 `acceptedAt`。Archive guard MUST 只接受当前 `READY` 状态，不得依赖 09 Markdown 关键词或 PR URL。归档 MUST NOT 要求验收之外的第二次人工表态：验收记录中的维护者「同意」即构成归档授权，归档 MUST 是机器步骤。

#### Scenario: 归档准备完整

- **WHEN** Review、Acceptance、Spec Sync、strict validation 和 cleanup 全部当前，且维护者声明尚未创建 PR
- **THEN** Archive guard 返回 allowed
- **AND** Change 可在功能分支归档后进行 final validation

#### Scenario: 归档不再索取第二次人工表态

- **WHEN** 验收已由维护者表态通过且 readiness 为当前 `READY`
- **THEN** 归档 MUST 直接放行，MUST NOT 要求维护者再次盖章或再摆一次决策材料

#### Scenario: PR 已开始或规格未同步

- **WHEN** `prStarted=true`、delta/main spec 摘要缺失、状态 stale 或 cleanup 非 PASS
- **THEN** Archive guard 非零拒绝

### Requirement: PR 反馈导致的行为变化必须受控 Reopen

归档后的 Change 若因 PR 反馈需要修改实现或规格，MUST 通过受控 reopen 恢复 active；新生命周期 MUST 从 Review 重新开始，旧 PASS 状态 MUST NOT 继续通过门禁。Reopen MUST NOT 写出无机器读者的留痕资产：`reopen-state.json` 与 lifecycle history 快照目录 MUST 不再生成。历史证据由版本控制承载。

#### Scenario: 归档后修改行为

- **WHEN** PR 反馈要求修改代码、合同、长期 spec 或可观察行为
- **THEN** 工具恢复 active Change 并使旧 PASS 状态失效
- **AND** reopen 后 Change 目录 MUST NOT 新增 `reopen-state.json` 或历史快照目录

### Requirement: Runtime 与消费仓归档必须解耦

Runtime Change 的 Archive MUST NOT 等待消费仓 gitlink 升级。消费仓采用新 Runtime commit MUST 在各自仓库的独立 Change 中验证和归档。

#### Scenario: Runtime 已准备交付但消费仓尚未升级

- **WHEN** Runtime 内部 Review、Acceptance、Spec Sync 和 Readiness 全部通过
- **THEN** Runtime Change 可以归档并创建 PR
- **AND** 不得因消费仓尚未采用而阻塞 Runtime Archive

### Requirement: 交付站位定义必须有唯一权威真源

交付流水线的站位、人工判断标记与站位对应的门禁 MUST 只有一份权威定义；另一份定义 MUST 或者引用该权威、或者被移除。Runtime MUST NOT 同时保留两份互不引用的站位定义。权威定义变更时，非权威侧 MUST 在同一次变更内对齐或删除。

#### Scenario: 单侧修改被拒绝

- **WHEN** 只修改非权威侧的站位定义而未同步权威侧
- **THEN** 合同检查 MUST 非零拒绝，并报告两侧不一致的站位

#### Scenario: 人工判断标记与真门禁一致

- **WHEN** 检查任一站位的人工判断标记
- **THEN** 该标记 MUST 与真实门禁是否索取人工表态一致；标记为人工判断却无对应门禁、或有门禁却未标记，MUST 判为不一致

### Requirement: 任务证据一旦存在就必须机器可校验

任务状态里**保存了**证据路径时，每一条 MUST 被解析为 Change 内的相对路径，并 MUST 校验该路径存在且内容非空。路径越出 Change 目录、不存在或为空文件时，任务状态写入与验收门禁 MUST 非零拒绝。Runtime MUST NOT 仅凭字符串非空即认为证据成立。

**证据在不在，由「这次验证能不能再跑一遍」决定**，见「验证证据 SHALL 按能不能再跑一遍分派」那一条：可重跑的验证 MUST NOT 保存证据路径，此时证据为空是正确形态，MUST NOT 被判为缺证据；不可重跑的验证在完成时 MUST 保存证据路径，随即受本条全部校验约束。

> **本条的沿革**：原措辞是「每条任务的 evidence 项 MUST 被解析为……」，读起来像「每条任务都必须有证据」。
> 在证据规则改成按可否重跑分派之后，这个读法与新规则正面打架——一份没有证据的可重跑任务，按原措辞
> 该被拒，按新规则该被放行。规范同步站按「改写」处置：本条真正管事的是「**证据一旦存在就必须真的
> 指向一份非空文件**」，这一点在两种规则下都成立；变的只是「什么时候该有证据」，而那件事由另一条管。

#### Scenario: 证据路径不存在

- **WHEN** 任务保存的证据指向一个不存在的路径
- **THEN** 任务状态写入 MUST 非零拒绝并报告该路径

#### Scenario: 证据文件为空

- **WHEN** 保存的证据指向的文件存在但内容为空
- **THEN** 验收门禁 MUST 非零拒绝

#### Scenario: 可重跑的验证没有证据

- **WHEN** 某项验证声明为可重跑，因而没有保存任何证据路径
- **THEN** 任务状态写入与验收门禁 MUST 放行，MUST NOT 判为缺证据

#### Scenario: 证据越出 Change 目录

- **WHEN** `evidence` 使用绝对路径或经 `..` 越出 Change 根
- **THEN** Runtime MUST fail closed 并不写入任何状态

### Requirement: 无机器读者的资产必须停止写盘

Runtime MUST NOT 生成没有任何机器读者的状态资产。`change-sources.json` MUST 停止写盘，来源溯源链 MUST 由 `01-原始需求/原始需求索引.md` 单独承载；移除前 MUST 逐项确认该索引覆盖原 `change-sources.json` 的等价信息，包括来源排序在内的任何未被覆盖的信息 MUST 先并入索引。

#### Scenario: 来源溯源仍可回溯

- **WHEN** 查询任一已归档 Change 的需求来源
- **THEN** `01-原始需求/原始需求索引.md` MUST 给出全部来源条目及其相对权威顺序

#### Scenario: 覆盖度未确认时拒绝移除

- **WHEN** 存在只记录在 `change-sources.json` 而未进入索引的信息
- **THEN** 移除 MUST 被拒绝，直到该信息并入索引

### Requirement: 工件合并只减份数，不减校验

把两份或多份必产工件合并成一份时，合并后的那份 MUST 承接原先各份各自参与的全部内容哈希计算与批准门禁，任一原有校验 MUST NOT 因合并而丢失（理由：合并的目的是少产出没人读的文件，不是少一道检查。判断一次合并做得对不对，唯一的尺子是「校验条目一项不减」——它与合并了哪几份、合并到第几版都无关）。

存量 Change MUST 按其自身声明的工件结构版本解析，MUST NOT 因新版本而被判定失效（理由：已归档的交付证据不迁移是既定取向；让新结构去否定旧目录，等于把审计链一次性作废）。

> **本条的沿革**：它最初写于第 6 版那次合并（两份现状并成一份），措辞把不变量绑死在「单一现状
> artifact」这个当时才有的产物上。第 7 版又把现状并进了方案提案、改造方案并进了实施任务，那个产物
> 不再存在，原措辞随之失去指称对象。第 7 版交付的规范同步站按「改写」而不是「撤掉」处置：真正管事
> 的是「合并不得减少校验」这个不变量，撤掉会连它一起丢。原条款附带的「发布计划模板移除恒为空的
> 三节」已在第 6 版执行完毕，属于一次性动作，不再作为长期要求保留。

#### Scenario: 合并后校验条目不减

- **WHEN** 对合并后的工件执行批准与验收门禁
- **THEN** 原先由被合并的各份分别触发的全部校验 MUST 仍然被触发

#### Scenario: 改动被合并进来的那一节同样使批准失效

- **WHEN** 合并后工件中、承接自被合并工件的那一节内容发生改动
- **THEN** 该工件的批准 MUST 失效，且报错 MUST 点名是哪一份工件

#### Scenario: 存量结构仍可读

- **WHEN** 读取按旧版本结构归档的历史 Change
- **THEN** 校验与归档状态 MUST 保持通过，MUST NOT 因新结构而判定历史 Change 失效

### Requirement: 保留的强校验不得削弱

Implementation Review 的 `reviewedPaths` 与 `result` MUST 继续由代码自算且不接受手工缩小；Acceptance State 的四项 digest 新鲜度校验 MUST 继续生效。任何一次流水线修剪 MUST NOT 放宽、绕过或删除这两处校验中的任何一项。

#### Scenario: 修剪后强校验回归

- **WHEN** 流水线修剪完成后重跑既有 Review 与 Acceptance 合同测试
- **THEN** 全部原有 fail-closed 断言 MUST 与修剪前一致通过

### Requirement: 仓内证据路径 SHALL 受可机器校验的长度预算约束

系统 SHALL 对仓内文件的相对路径长度设定一个上限，并以自动校验守住该上限；新增的验收与归档证据超出上限时 SHALL fail-closed 并点名超限文件（理由：证据路径长度在 Windows 上是有限资源，超限的表现不是「报错说太长」，而是干净文件被误判为已修改，症状与真实漂移无法区分；预算必须由机器守，因为人没有办法在起文件名时心算它）。上限的具体取值、以及是否回溯压缩既有归档证据，属实施期裁决，本要求只约束「必须有预算且必须被校验」。

#### Scenario: 新增超长证据路径被拒绝

- **WHEN** 新增的证据文件其仓内相对路径长度超出既定上限
- **THEN** 自动校验失败，并指出超限的文件路径与其长度

#### Scenario: 预算内的证据照常通过

- **WHEN** 全部证据文件的路径长度均在上限内
- **THEN** 自动校验通过，不对既有归档目录产生额外要求

### Requirement: 每一份必产工件 SHALL 有一个说得出名字的读者

流水线要求必须产出的每一份工件，SHALL 满足下列两者之一：**有代码真的打开它、并据其内容放行或拒绝**，或者**有维护者在一个确定的场合真的会读它**。两者都没有的工件，SHALL 停止把它列为必产项。

「有代码算它的摘要」SHALL NOT 单独算作有机器读者（理由：算摘要证明的是「这份文件没被偷改」，不是「这份文件的内容有人看」。第 7 版交付之前，有三份工件属于这种情形——现状、改造方案、测试方案，机器一个字都没读过，只按内容变化让批准失效。这条区分是本次精简工件的判据；不把它写死，精简工件就会退化成凭感觉删文件）。

#### Scenario: 新增必产工件时须指名读者

- **WHEN** 向交付流水线新增一份必须产出的工件
- **THEN** 该工件的定义 SHALL 写明它的读者是哪段代码或哪个人工场合；两者都给不出时，SHALL NOT 把它列为必产项

#### Scenario: 现有工件失去读者后须退出必产清单

- **WHEN** 某份必产工件的机器读者被移除，且没有可指名的人工读者
- **THEN** 该工件 SHALL 退出必产清单；SHALL NOT 以「保留以备将来」为由继续强制产出

### Requirement: 人工批准记录的条数 SHALL 能对上人真实表态的次数

每一条要求维护者出面的批准记录，SHALL 对应他在某一个门口真实说过的一次话。SHALL NOT 把一次表态展开成多条各自独立签发的批准记录（理由：第 7 版交付之前，一句「同意」被展开成 8 条带独立指纹的记录（当时的八份必产工件：原始需求索引、长期规范增量、现状、方案提案、方案决策、改造方案、测试方案、实施任务），读批准链的人无法区分「他表了 8 次态」和「他表了 1 次态、被复制成 8 条」；批准链的全部价值就是让人一眼看出谁按下了哪一次放行，复制会直接摧毁这个价值）。

工件内容变化即让相应批准失效的机制 SHALL 保留，SHALL NOT 因为批准条数减少而削弱：合并后的批准记录 SHALL 覆盖原先各条各自覆盖的全部内容。

门级批准在机械回填之后被刷新时，SHALL 要求显式声明本次刷新哪几份工件，并 SHALL 把实际发生变化的工件集合与声明集合对照；**声明之外还有工件的内容变了，刷新 SHALL 被拒绝**（理由：门级批准是一条覆盖多份工件的记录。若允许整体重签，「回填任务状态」这种每次渲染都会发生的机械改动，就能顺带把一处被篡改的工件一起重新祝福——实测走通过一次：改一处任务状态、篡改一处方案决策，以「证据回填后重批准」的名义重签，全部工件回到已批准、实施门禁放行、篡改毫无提示。按份批准的旧口径不存在这条通道，所以合并批准必须把逐份问责补回来）。

刷新 SHALL NOT 覆写该门最近一次人工表态的表态人与时间，SHALL 以追加方式记录每次刷新的执行者、时间与被刷新的工件（理由：把维护者的原始表态改写成「agent 代笔的机械重批准」，等于用一次回填抹掉一次真实表态的痕迹）。

内容确有语义改动时，正确出口 SHALL 是重新取得人工表态，且该动作 SHALL 覆写表态人与时间、清空刷新记录、并记录重新表态的理由（理由：让「第一次过人」「机械回填」「重新过人」三件事在记录上一眼可分；三者共用一条命令而不可区分，正是第 7 版交付在第一轮评审里被判不通过的形态）。

#### Scenario: 一次表态只产生一条批准

- **WHEN** 维护者在方案门给出一次表态
- **THEN** 系统 SHALL 记录一条批准，并 SHALL 在该条批准中逐份列出被覆盖工件的内容哈希

#### Scenario: 机械回填顺带改了别的工件

- **WHEN** 以刷新名义提交，而声明之外还有工件的内容发生了变化
- **THEN** 刷新 SHALL 被拒绝并点名那几份工件，批准记录 SHALL 逐字节不变，下游门禁 SHALL 继续拦住

#### Scenario: 不声明刷新范围

- **WHEN** 对已有批准的门提交刷新，却没有声明刷新了哪几份
- **THEN** 写入 SHALL 被拒绝

#### Scenario: 刷新不动原表态

- **WHEN** 一次合法刷新完成
- **THEN** 该门最近一次人工表态的表态人与时间 SHALL 保持不变，未被声明的工件的内容哈希 SHALL 保持不变

#### Scenario: 合并后覆盖面不减

- **WHEN** 被合并覆盖的任一工件在批准后发生内容变化
- **THEN** 相应批准 SHALL 失效并拦住下游门禁，行为 SHALL 与合并前一致

### Requirement: 站位清单与批准清单 SHALL 相互一致

「哪些站需要人表态」与「哪些工件需要人工批准才能放行实施」SHALL 由同一份定义推导，SHALL NOT 各自独立维护（理由：第 7 版交付之前，批准模型要求当时那八份工件都持人工批准才能开始实施，站位模型却写着实施站是机器站；测试方案在交付站位里根本没有对应的站，却同样被索取人工表态。两份清单各说各话时，agent 按哪一份都能给自己找到依据，门禁就失去了确定性）。

#### Scenario: 两份清单出现分叉时校验失败

- **WHEN** 站位定义中的人工判断位置与批准清单要求的人工批准工件不能相互对应
- **THEN** 自动校验 SHALL 失败并指出分叉的具体位置

### Requirement: 实现审查的范围 SHALL 覆盖对长期规范目录的直接改动

实现审查自算被审范围时，SHALL 把实施提交中对长期规范目录（`openspec/specs/**`）的直接改动纳入审查范围（理由：长期规范的正常入口是「先在 Change 内写增量、验收后再由规范同步站合入」。实现侧的范围计算此前把该目录整体排除在「实现改动」之外——那是实现的默认行为，本规范从未这样要求过——结果是实施提交里直接向长期规范写入的内容，审查在结构上看不见——`enforce-analysis-line-and-prune-pipeline` 那一单就真的发生过一次：46 行长期规范直接写进实施提交，绕过了整条链路。这不是审查者疏忽，是范围计算把它排除了）。

与此同时，实现审查完成之后由规范同步站写入长期规范目录的内容 SHALL NOT 被判为实现漂移（理由：那是流程自己的收尾动作，发生在审查之后、归档之前，让它使已完成的审查失效会形成死锁——审查完就同步，同步完审查又过期。这一段的完整性另有守卫：归档前会绑定每一对增量与主规范的内容哈希——这份绑定原先叫「归档就绪记录」，本次改动把它并进了验收记录，判据一项不减，见下文「保护性记录」那一条）。

#### Scenario: 实施提交直接改长期规范时被审查看见

- **WHEN** 实施提交中包含对 `openspec/specs/**` 的改动
- **THEN** 该改动 SHALL 出现在实现审查的被审路径中，SHALL NOT 被范围计算静默排除

#### Scenario: 规范同步站事后写入不算漂移

- **WHEN** 实现审查完成后，规范同步站把增量合入 `openspec/specs/**`
- **THEN** 该审查 SHALL 仍然有效

#### Scenario: 放行同步站不得连带放开漂移检查

- **WHEN** 实现审查完成后，实现代码本身发生改动
- **THEN** 该审查 SHALL 失效

### Requirement: 验证证据 SHALL 按「这次验证能不能再跑一遍」分派

每一项验证 SHALL 声明它是否可以重跑，系统 SHALL 按这个声明分派证据规则（理由：维护者原话是「测试日志和验收证据，在 vibe coding 中意义不大……我们只能通过请求去构造场景，走请求去验证。我会觉得单测其实根本不需要记录」。判据因此不是「这份证据重不重要」，而是「丢了还能不能拿回来」）：

- **可以重跑的验证** SHALL NOT 保存任何运行日志（理由：要复核就当场再跑一遍，重跑的结论比存下来的日志更可信——日志无法证明它对应的是当前这版代码。留着它只会让人以为有据可查）。
- **不可重跑的验证** SHALL 保存记录（理由：构造一次请求走一遍场景，做完这一次就没了，不记就永远丢了。这是唯一一次机会）。

「记录验证过程」这个能力 SHALL 保留在通用底盘上，并 SHALL 明确标注其适用场景是不可重跑的验证（理由：本仓的验证恰好全部可重跑，于是这个能力在本仓恒为关闭；但它不能因此被删掉——第二个接入的仓库很可能恰好全部落在另一侧）。

新写入 SHALL 显式声明这一项，SHALL NOT 依赖缺省值（理由：「这次验证能不能重跑」是一个需要人判断的问题，交给默认值回答等于没人回答过）。**缺省值因此只在「读」这一侧存在，写入侧根本走不到它。**缺省值 SHALL 只服务于存量记录的只读兼容，且 SHALL 按记录的实际形态推断，SHALL NOT 一律按某一侧解释（理由：一律按可重跑解释，会让归档目录里那些带着自然语言证据的历史任务集体解析失败，而存量不迁移是既定取向）。

#### Scenario: 可重跑的验证保存了证据路径

- **WHEN** 某项验证声明为可重跑，却保存了证据路径
- **THEN** 写入 SHALL 被拒绝

#### Scenario: 不可重跑的验证没有留下记录

- **WHEN** 某项验证声明为不可重跑，已完成却没有保存任何记录
- **THEN** 写入 SHALL 被拒绝

#### Scenario: 不可重跑的证据仍受原有校验

- **WHEN** 不可重跑的验证保存了证据路径
- **THEN** 原有的越界、软链逃逸与非空校验 SHALL 一条不少地继续生效

#### Scenario: 存量记录仍可读出

- **WHEN** 读取一份没有声明该项的历史任务记录
- **THEN** 解析 SHALL 成功，并按其实际形态推断出取值

### Requirement: 保护性记录 SHALL 保留到「事后能复核当时发生了什么」的程度

评审记录与验收状态 SHALL 完整保留，SHALL NOT 因精简工件而压缩其内容或校验（理由：这两类记录是本仓迄今拦下问题最多的环节留下的证据——历次交付的评审记录累计查出的问题远多于其它任何环节（陌生读者审读也拦下过内容错误，只是它拦的是文字不是实现，两者不是同一条防线），且本仓至今没有发生过一次事后审计，「留到什么程度才够」没有实测下限。裁错的代价不对称——留多了只是持续摩擦，留少了是查无对证且不可追补，所以取中间档：有战果的全留）。

> **一处如实说明**：中间档原本还包含「把归档就绪记录并入验收记录」这一半，第 7 版交付**没有实施**——
> 归档就绪至今仍是一份独立文件，归档条款也仍在把它当独立状态用。一条没有实现的规则写进长期规范，
> 等于自己造一条谎，所以规范同步站把它撤下，只保留已经做到的那一半。取向本身保留在该次交付的方案
> 决策里，并登记为待办 `INT-20260901-032-merge-archive-readiness-into-acceptance`。

#### Scenario: 合并后归档门禁判据不变

- **WHEN** 执行归档门禁
- **THEN** 原先由归档就绪记录提供的全部判据 SHALL 仍然被检查，SHALL NOT 因并入验收记录而丢失任何一项

### Requirement: 测试断言 SHALL 区分「有不变量」与「只是记账」

新增或修改测试断言时，SHALL 说明该断言背后的不变量是什么。背后没有不变量、只是把某一时刻的清单写死的断言，SHALL 改写为对不变量的断言或撤除；背后有不变量的断言 SHALL NOT 因为「形态像快照」而被放宽（理由：本仓有一条锁死在途 Change 目录完整集合的断言，每建一个 Change 要登记、每归档一个要注销，撞红三次（前一个 Change 建立时、它当日归档时、第 7 版交付建立时），三次都没有暴露任何真问题——它只是在为快照缴费。但同族里有一条形态相同的反例：路径长度预算断言要求常量恰好等于仓内实测最长路径，它背后有真不变量，取等号是刻意的棘轮，防止有人为了让某条长路径通过顺手把预算调宽再没人调回来。所以判据是「背后有没有不变量」，不是「像不像快照」）。

#### Scenario: 记账型断言被改写

- **WHEN** 某条断言在没有暴露任何缺陷的情况下，仅因例行操作而反复需要更新
- **THEN** 该断言 SHALL 被判为记账型并改写为对不变量的断言，SHALL NOT 靠继续更新清单维持通过

#### Scenario: 有不变量的严格断言不被误撤

- **WHEN** 某条断言形态上是快照，但能说明其背后的不变量与放宽后的具体后果
- **THEN** 该断言 SHALL 保留原有强度，SHALL NOT 因形态相似而被一并放宽
