# Intake

## 原始问题

维护者原话：「目前这个仓库自己的工作流我觉得不合适，我们生成了大量我不看的文档和文件。需要设计、制作一个适合本仓库的工作流」

> **2026-09-01 已启动分析。** 本条目登记时按维护者指示只做登记、排队等待修小刺批次验收；
> 该批次已于同日验收归档，本条目随即以分析线第二单的身份跑起来。下面各节由那次分析填写，
> 分析产物在 `openspec/intake/analysis/INT-20260901-023-repo-suited-workflow/`。
>
> **分析停在「决定」站，最终裁断留给维护者。** 按维护者当轮追加的边界，本轮只做到候选路线
> 比较为止；机器侧的运行结果是 `blocked`，明确点名还缺「决策报告」与「处置结论」两项输入——
> 这两项正是要由维护者给出的东西，agent 不代填。

## Triage

范围：本仓自己的交付流水线形状——站位数、每站产出哪些文件、哪些文件落盘、哪些环节要维护者出面；
三套流程模板与真正执行门禁的那些代码之间的关系（以及哪一份算数）；按改动对象选流程档位的那张
路由表和它现存的四处路径空白（**具体是**：行尾属性文件 `.gitattributes`、CI 配置目录 `.github/`、
归档目录 `openspec/changes/archive/`、长期规范目录 `openspec/specs/`——这四处不属于路由表里任何
一档，详见「已知事实」第四节）；给维护者摆材料的规则与「说人话」的把关机制；以及六处已挂账、
明确等这一轮一并裁的机器缺陷。另含 AGENTS.md 预置的一个复盘触发点：强制版分析线跑满两单后
裁定它的留、修还是杀——本单就是第二单，条件已满足。

不含：消费仓怎么接入本 Runtime（那是对外的产品面，不是本仓自己的工作流）；已归档目录的迁移
（既有取向是存量不动）；本轮不实施任何改动，也不起草方案提案。

影响：四条候选路线里，最轻的一条只加不减、最重的一条要重写约三分之一的测试断言。共同的影响面是
交付模板、两个控制工具的工件清单、路由表、AGENTS.md 与交互指引。改动本身落在治理合同这一最重档，
必须自己走完整交付流程加分析线，不能自我豁免。

判断：continue——证据已备齐，四条路线与四项正交裁项都摆到了可裁粒度，等维护者在门口取向。
本条目不自行裁决。

### 读这份文件需要先知道的几个词

> 这份文件写完后按维护者提出的办法做了一次预检——交给一个完全没有本仓上下文的空白会话去读，

> 下面这张表就是照它的意见补的。**这件事本身也是一份证据**，见「已知事实」第十节。

| 词 | 意思 |
|---|---|
| **本 Runtime** | 就是本仓库（`delivery-spec-runtime`）。它是一套公开共享的交付工作流，别的仓库可以把它作为 Git 子模块接进去用。 |
| **消费仓** | 接入了本仓这套工作流的下游仓库。目前只有一个，叫 `agent-system`。 |
| **工件** | 走一遍交付流程会产出的那一批文件（方案文档、测试方案、验收记录、各种状态 JSON 等）的统称。 |
| **机器契约** | 规定某类 JSON 文件必须长什么样的校验规则文件，放在 `openspec/contracts/`。 |
| **八层（工件结构）** | 走完整流程的 Change 目录里那八类必备工件，按顺序是：**01 原始需求索引 → 长期规范增量 → 03 现状 → 05 方案提案 → 05 方案决策 → 05 改造方案 → 06 测试方案 → 07 实施任务**。另有两类在后面产生（验收记录、发布计划），不计入这八层。本文说「压成五层」，指的就是把其中几类合并。 |
| **站 / 站位** | 流程里的一个节点。本仓有**两条**流水线，各有各的站，**不要混**：**交付线七站**（方案提案 → 方案决策 → 实施任务 → 实现审查 → 验收 → 规范同步 → 归档），**分析线五站**（捕获 → 澄清 → 核验 → 评估 → 决定）。本文出现「决定站」时指的是分析线的最后一站。 |
| **门** | 流程里必须由人表态才能过的节点。从人的视角只有三道：**立项门**（这事做不做）、**方案门**（走哪条方案）、**验收门**（认不认这个结果）。 |
| **快车道** | 给低风险小改动准备的短流程（三站：登记 → 实施 → 快速验证），与上面那条七站的完整流程并列。 |
| **档 / 档位** | 按「改动对象」给事项定的流程等级。本条目分析时是四档，由重到轻：**治理合同**（改流程规则本身）、**工具代码**、**文档表达**、**纯事项记录**。前两档走完整流程，后两档走快车道。**降档**＝声明成比实际更轻的档；**越档**＝实际改动超出了自己声明的档。（2026-09-01 补充：立项后新增了第五档**流水线自身产物**，档位序在文档表达与工具代码之间，只用来给路径定档、不用来给事项定档，详见本条目「已知事实」第四节所指的那次修表。） |
| **路由表** | 定义上面那四档、以及每档对应哪些文件路径的那份配置（`openspec/profiles/change-routing-v1.json`）。 |
| **事项记录** | `openspec/intake/` 下的一份份 Markdown 记录，每份记一件事的来龙去脉。本文件自己就是一份事项记录。**挂账**＝已登记但还没处理的事项。（本条目写作时这个词还叫另一个名字，后来被列进禁词名单、统一改叫「事项记录」；全仓词表见 `docs/glossary.md`。） |
| **信号 N** | 维护者在使用过程中给出的反馈，按时间编号记在一份专门的事项记录 `INT-20260831-014` 里，目前编到 13 条。本文引用到的：**信号5**＝维护者主动追问事项记录完成度（说明事项记录有真实读者）；**信号7**＝要求必须写进机器检查、写在文档里不算数；**信号10**＝本条目的立论（「大量我不看的文档」）；**信号11**＝写给维护者的文字必须说人话；**信号12**＝耐久文字发出前先请一个不知情的空白会话读一遍。 |
| **说人话（这道关）** | 信号11 和信号12 合起来的那条要求，本文把它当成一项待设计的检查在讨论。判据是维护者定的：**一个没读过本仓任何文件的人，能不能一遍读懂**。 |
| **摘要 / 指纹 / 新鲜度 / 锚点** | 是同一套机制的四个说法，机制本身很简单：每份工件被批准时，把它的内容算一个 sha256 值存下来；以后只要文件内容变了、算出来的值对不上，这条批准就自动失效，流程被拦住。「锚点」指的是这套机制一共钉住了几份文件。 |
| **代笔标注** | 批准记录里的一行字，注明这条批准是维护者亲自签的、还是他口头说了一句由 agent 转录的。 |
| **入口守卫 / 总闸门** | 「总闸门」指 `runtime-entry.ts`，所有消费仓调用本仓功能都得经过它。「入口守卫」指某些脚本里的一段判断——只有当这个文件是被直接运行时才执行主流程；它在路径含软链接时会判错，导致整个脚本静默跳过。 |
| **探针** | 为验证某条规则真的生效而专门写的测试：故意把输入改坏，看检查会不会如期报错。 |
| **AGENTS.md** | 仓库根目录下约束 agent 会话行为的规则文件。 |
| **立法** | 本仓内部的说法，指「把某条要求正式写进规则文件或机器检查」。 |

**五、站位与门的真实数目，以及一处结构不对称**

- 机器上标着「要人表态」的位置一共 **7 处**，分散在三套流程模板里。这 7 处**不在同一条流水线上**，
  所以不能直接相加去跟「3 道门」比。拆开看：

  | 在哪条线上 | 有几处要人表态 | 分别是 |
  |---|---|---|
  | 交付线（七站） | 2 | 方案决策、验收 |
  | 分析线（五站） | 4 | 澄清、核验、评估三站的「再走一轮还是够了」，加最后的决定站 |
  | 快车道（三站） | 1 | 快速验证 |

  **人的视角只有 3 道门**（立项、方案、验收），因为：**立项门**是分析线那 4 处折叠起来的结果——
  分析线跑完才谈得上立项，中间那几轮循环对人只表现为「同意/再走一轮」；**方案门**和**验收门**
  就是交付线那 2 处；**快车道**那 1 处与完整流程二选一，同一件事不会两条都走。归档已于上一轮
  正式摘掉人工门，机器层面也不再给 agent 在归档站补第二个签名的入口。
- **结构不对称**：交付七站根本没跑流程引擎——它跑的是一个控制工具的六种拒绝检查加另一个工具的
  三个前置要求；引擎只服务分析线和快车道。交付模板文件自己写着「本文件不产生约束力，权威在
  代码」，两侧靠一组从真门禁行为侧反推的探针比对。这意味着改站位要同时动两个地方，只改一处
  要么不生效要么分叉。

**六、六处挂账机器缺陷的形态（都已落实到具体位置）**

1. **批准清单与站位清单各说各话**（`INT-20260901-020`）：批准模型要 8 份工件都持人工批准才放行
   实施；站位模型说实施站是机器站；测试方案在交付七站里根本没有对应站位，却同样被索取人工表态。
2. **站位一致性探针强度不足**（`INT-20260901-021` 一）：7 站里只有 3 站做了真负向对照（抹掉该站
   的人表态字段再跑），另 4 站靠「完整样本能通过」。而且「每站抹哪个字段」这个手工选择本身就
   编码了答案，现有的反自证断言抓不到这种形态。
3. **评审看不见对长期规范的直接改动**（`INT-20260901-021` 二）：评审自算范围把长期规范目录和
   Change 目录一并排除在「实现改动」之外。上一单就真的发生过——在实施提交里直接向长期规范写了
   46 行，绕过了「先写增量、验收后再合并」的链路。
4. **入口守卫还剩一处**（`INT-20260901-024`）：`openspec-upgrade.ts` 一处。它有 import 方（测试文件
   引用它的一个校验函数），所以「删守卫、无条件执行」这条路带前置条件，必须先把那个函数挪出入口
   模块。更一般的问题是要不要立一条硬规则：入口模块不得把是否执行主流程系在路径比较上。
5. **路由表四处路径空白**：见上文第四节。
6. **把某一时刻的清单写死成永久判据的断言**：`VC-039` 锁死了在途 Change 目录的完整集合，在
   `fix-thorn-batch` 一单里**撞红两次**（该 Change 建立时要登记、归档时要注销）；另一条锁死
   「归档目录一律按旧版解析」，在第一个新版归档目录出现时撞红。第三次的处置改成按各 Change
   自己声明的版本号取期望键集，**判据没有削弱**——这是「记账 vs 不变量」的分界示范。
   **同族的一个反例说明不能一刀切**：路径长度预算断言要求常量恰好等于仓内实测最长路径，形态上
   也是记账，但它背后有真不变量（Windows 上路径超过 260 字符会把干净文件误报成已修改），取等号
   是刻意的棘轮，防止有人为了让某条长路径通过顺手把预算调宽再没人调回来。所以判据应当是
   **「这条断言背后有没有不变量」，不是「它像不像快照」**。

**七、文档说的和机器做的相反、机器赢的活标本**

事项记录说明文件（`openspec/intake/README.md`）有三处与机器实际行为对不上：

1. **第 66 行**仍写着推进顺序固定为「捕获 → 分流 → 取证 → 候选 → 处置」这五个阶段——**但这五个
   阶段已于 2026-09-01 合并移除**，现在只剩「已登记」和「已处置」两个真实节点。
2. **第 36 行**仍写着一个已废弃的中间状态名 `triaged`（原意是「已理解影响和边界、尚未承诺实施」），
   现在任何命令都不会再写入这个状态。
3. **第 42 行**要求「存在 Issue 时在 intake 中记录 URL」，**而机器根本不让存**：敏感内容检查里有
   一条规则，把「单个字母 + 冒号 + 斜杠」的形式一律当成 Windows 盘符绝对路径拦下（本意是防止把
   本机路径写进这个公开仓库）。网址里协议名的最后一个字母加上后面的冒号斜杠，恰好就是这个形式，
   于是**任何网址都会被一并拦下**。

**本轮实测确认了第 3 条**：把一个以 h-t-t-p-s 开头的网址喂给那条规则，它返回「命中」。
（这里把 h-t-t-p-s 拆成字母写，不是排版失误——**正是为了让这份事项记录自己能存进去**：写成完整形式
就会被同一条规则拦掉。这个细节本身就是问题的现场演示。）

> **2026-09-01 立项时又撞了一次，这次是真的挡住了流程。** 上面这段原本写着协议名后半截那五个
> 字符的字面形式，结果 `intake promote` 的敏感内容检查当场命中、立项被拒——**一份记录该缺陷的
> 事项记录，被它记录的那条缺陷挡在了流水线外面**。处置是把那五个字符改成文字描述（就是现在这句）。
> 顺带暴露出一件更值得记的事：`promote` 自称「写入任何状态之前完成全部判定，任一不满足即两侧
> 文件逐字节不变」，但这次拒绝发生时，目标 Change 的原始需求索引已经被追加了来源行，只有事项记录
> 这一侧没写——**两侧不是逐字节不变，判定顺序与自述不符**。已作为一条待处置缺陷进入本 Change。

三条合起来印证信号7 的通则：要求写在文档里没用，写在机器里才算数；**而两边写反了的时候，机器赢**
——带链接的事项记录条目至今存不进去，而文档还在要求你写链接。

### 未知与假设

- **「保护性记录保留到什么程度才够审计用」没有外部标准可依**，因为本仓至今**没有发生过一次真正的
  事后审计**——没有任何人回头查过任何一份归档证据。所以「够用」的下限只能靠推演，不能靠实测。
  这是本轮最大的一处不确定，也是各条路线差异最大的那一维。裁错的代价不对称：留多了只是持续摩擦，
  留少了是查无对证且不可追补。
- **独立评审的战果能不能在更轻的工件形态下保住**：51 条问题全部来自「另起一个不知情会话逐条复测」
  这个动作，但这个动作与「写了多少份工件」之间**没有已证实的因果**。有可能大部分工件砍掉后战果
  不变（评审者的判据主要来自代码与提交范围），也有可能工件正是评审者能对照的基准。本轮没有取证。
  **取证方式是可行的**：挑一单已完成的，只给评审者代码与提交范围、不给工件，看能不能复现同样的
  问题清单。
- **说人话这道关怎么落成机器能查的东西**：只有一次实践数据，且那次是 agent 自觉发起的。它是本仓
  第一条**没有可校验产物**的要求——其他门禁都是「有文件、有摘要、可重算」，而「确实找过一个不知情
  的会话读过」拿不出这种形状的证据。
- **存量批准记录与旧版结构的处置**：既有取向是存量不迁移，但新旧并存已经在代码里付出了双版本解析
  的代价（两张工件路径表、两套期望键集）。再改一次形状就是第三套。本轮未评估「让存量在改形状时
  自然失效、只保证只读可解析」这条路的代价。
- **指标子系统零使用的成因仍未查**（上一轮就记着未归因）。可能是接入摩擦（状态必须落到仓库外面），
  也可能是单人单仓根本不需要度量。成因不查清就只能按「零消费」处置，无法区分「不需要」和「太难用」。
- **本仓作为对外样板的约束到底有多硬**：现有消费仓只有一个（agent-system）。从两次升级的事项记录记录看，它至今只用到
  版本锁与分发校验这一层，没有留下走交付七站的痕迹；但本仓无法直接观察消费仓内部，**这是推断不是实测**。若样板责任事实上很轻，各条路线的可行性排序会明显改变。**本轮未向维护者
  确认这一点，它是四项正交裁项之外还需要一句话回答的前提。**

## Options

### 候选处置

> **以下四条路线与四项正交裁项，一律由维护者裁决。** 本条目的作者（agent）不对流水线形状作任何
> 裁定。四条路线在「维护者的日常体验、agent 损失了什么保护、迁移成本、可逆性」四个维度上逐条比过；
> 四项正交裁项与路线选择不相干，单列出来是为了**不把不相关的东西捆在一起逼人一起选**。

#### 路线 A｜推倒重来：为「一个人加一个 agent」的仓库从零画一条新流水线

**形状**：丢掉八层工件结构与交付七站，改成三件套——一份事项文件（问题、方案、变更清单写在一处）、
一次独立评审、一次验收。机器侧只保留四样：评审记录、验收状态、一条合并后的批准记录、任务状态。
三套流程模板合并成两套。存量归档目录只做只读兼容，不迁移。

- **维护者的日常体验**：一单出面 **2 次**（方案、验收），每次一页纸；若翻仓库，一单只剩大约
  8 到 10 个文件（现在是 28.5 个）。说的话不变。
- **agent 损失了什么保护**：**四条里损失最大**。其一，批准新鲜度现在有 8 个锚点，任何一份工件被
  事后改动，对应那条批准立刻失效**并能点名是哪份变了**；合并成 1 到 2 个锚点后只知道「方案变了」，
  粒度和定位能力都掉一档。其二，更实质的是「方案提案必须有两个以上真实候选、必须有取舍矩阵、
  必须有推荐和未决问题」这类**内容级检查会失去落点**——而正是这几条在逼 agent 摆出真候选而不是
  走过场。
- **迁移成本**：**最高**。要重写八层结构定义、10 份模板、两个控制工具的工件路径表、21 份契约里
  至少 6 份、90 条断言里估计 30 条以上、9 个命令文档、6 份说明文档、交互指引；存量兼容层会从现在的
  两套变成三套。而且这些改动全部落在治理合同这一最重档，**必须用现在这套重流程去交付「取消这套
  重流程」——一单里会再生产一遍它想消灭的东西**。
- **可逆性**：**低**。不是技术上收不回，而是模板与约三分之一断言一旦重写，回滚等于再做一次同等量
  的工作；兼容层叠到三套后，回退要拆的是三套之间的交叉。

#### 路线 B｜保住骨架，大精简工件面：站位、门数与门禁代码一个不动，只改「每站要写出什么」

**形状**：三道门、六种拒绝检查、三个前置要求、评审自算范围、验收四项新鲜度**全部原样不动**。只改
工件清单——把现状文档与改造方案并进方案文件（两者都是只算摘要、机器从不看内容的）；测试方案保留
（它有真实的人类读者）；发布计划再删掉剩余的空转小节；批准清单从 8 条收缩到 3 条（方案、测试方案、
任务）。八层目录相应压成五层。

- **维护者的日常体验**：一单出面还是 **3 次**（立项、方案、验收），说的话一个字不变。变化在于翻
  仓库时一单从 28 个文件降到大约 **15 个**，批准记录从 8 条降到 3 条——**关键是这 3 条每条都能对上
  他真说过的一句话**，而现在是一句「同意」被展开成 8 条带独立指纹的记录。
- **agent 损失了什么保护**：**损失小且可指名**。锚点从 8 个减到 3 个，粒度变粗但**覆盖面不减**
  （合并后那份文件的摘要涵盖原来几份的全部内容）；内容级检查**全部保留**（它们都挂在方案文件上，
  而方案文件保留）；评审、验收四项新鲜度、越档交叉校验**一处不动**。唯一实质损失是**「现状文档
  独立成件」这道工序**——它本来的作用是逼 agent 先把事实查清楚再动手，并进方案后会不会退化成一段
  套话，没有机器判得出来。
- **迁移成本**：**中**。改 10 份模板里的 3 份、加一张工件路径表（只加不改旧的，沿用已有的「按各
  Change 自己声明的版本取键集」机制，**因此不新增兼容层**）、约 12 条断言、命令文档一份（实测：9 份命令文档里只有归档那一份按名字点到了具体的工件层目录，其余八份只泛指「工件」，所以改层级结构对命令文档的冲击比预想的小）、
  2 份说明文档。
- **可逆性**：**高**。改的都是清单与模板，回滚就是把表改回去，门禁代码一行没动。

#### 路线 C｜只改产出物的形态与可读性，不动流程也不删任何工件

**形状**：一份文件都不删。改两件事——哪些东西会被端到维护者面前（把机器格式的文件从人审路径上
彻底移走，现在只写在指引里、没有机器检查），以及哪些文字必须先过「说人话」这一关（立一份必过清单，
把「发出前先请一个不知情的空白会话读一遍」做成 PR 前的必经步骤）。

- **维护者的日常体验**：出面次数、说话字数、文件数量**全都不变**，唯一的变化是他读到的每一段文字
  都先过了一道陌生读者关。
- **agent 损失了什么保护**：**零**。这条路只加不减。
- **迁移成本**：**最低**。加一份清单、加一道检查、改 AGENTS.md 与交互指引各一条；模板、工件表、
  既有断言一律不动。
- **可逆性**：**最高**。纯加法，去掉即回到今天。
- **但它有一个明显的问题**：**它没有回答维护者的原话**。维护者说的是「生成了大量我不看的文档和
  文件」，这条路的回答是「以后你看的那部分会更好读」，而不看的那部分照旧生成。信号10（不看）与
  信号11（看不懂）在事项记录里是被明确区分开的两件事，只取 C 等于把前者重新解释成后者。

#### 路线 D｜组合：先按 B 精简工件，同时按 C 立说人话这道关

**形状**：B 与 C 改的是不相干的两件事——一个改「写什么」，一个改「怎么写、给谁看」，落点不重叠，
可以并行做。合起来一次交付。

- **维护者的日常体验**：B 的文件数变化加 C 的可读性变化——出面还是 3 次，一单文件从 28 降到 15，
  批准记录 8 条降到 3 条，且所有进他视野的文字都过了陌生读者关。
- **agent 损失了什么保护**：与 B 相同（只有「现状独立成件」那道工序有实质损失），C 侧为零。
- **迁移成本**：B 加 C 的和，但**只付一次交付仪式**。按本仓最近一单实测，一次完整交付仪式的治理
  文档产出约 2000 行，所以合并做省下的不是小数。代价是单次改动面变宽，评审要按两组分开审。
- **可逆性**：与 B 同档，**高**。
- **只取 A 或 B 也不完整**：砍掉文件解决不了「PR 标题和正文不说人话」——那是信号11 单独提出的、
  与文件数量无关的另一件事。这正是把 D 列出来的理由。

#### 四条路线的共同前置条件（不是可选项）

路由表现有四处路径没有归属，其中**归档目录与长期规范目录**这两处，是这条流水线自己最后两站的动作
要触碰的。不先补上，**任何一条路线在实施时都会被声明与事实的交叉校验挡住**。这不是实施期才暴露的
意外，是动手之前必须先裁掉的：要么补前缀行，要么按路由表自述的口径调表。

### 四项与路线选择正交、需要单独裁的事项

**正交裁项一｜分析线的留、修、杀（AGENTS.md 预置的触发点已满足）**

条件是「强制版分析线跑满两单后裁定」，本单即第二单。**两单数据都指向「留」**：第一单在取证站
推翻了一个挂了一整天的错误归因并给出精确阈值；第二单（本单）把散在六七份事项记录里的材料收敛成一份
可比较的路线表；两单的门禁都是全数生效、零误挡。**但两单也都记下了同一批使用成本**（手抄已完成
阶段、请求文件长到人不可能读、说明文档没写清标志名）。所以证据支持的是**「留，但修使用成本」**，
不是「留着不动」，也不是「杀」。最终取向由维护者给。

**正交裁项二｜保护性记录保留到什么档位**

三档可选：(a) 现状不动（评审记录含逐路径指纹、验收状态四项新鲜度、归档就绪记录全套）；
(b) 只留评审记录与验收状态，归档就绪的部分内容并入验收；(c) 连评审记录里的逐路径指纹也压缩成
一条总摘要。**本轮无实测依据可依**——本仓从未发生过一次事后审计。裁错的代价不对称：留多了只是
持续摩擦，留少了是查无对证且不可追补。

**正交裁项三｜说人话这道关的强制形态**

三档可选：(a) 写进指引，靠 agent 自觉（**已有明确反例证明这条不成立**——分析线三单零执行）；
(b) 列一份「必须过这道关」的清单，由 agent 自觉发起但清单本身是硬的；(c) 机器强制。难点在于
它是本仓第一条**没有可校验产物**的要求。另有两个子问题待裁：**哪些文字必须过、哪些可免**（每次
都过会显著拖慢节奏），以及**检查提出问题后是必须改还是可说明理由后照发**。

**本轮已把这道关跑了第二次，且第一次跑在治理文档上**（见「已知事实」第十节）。三条新增依据：

- **它能查出真错误，不只是文风问题。** 34 条意见里有 2 条是内容错误（评审轮次自相矛盾、两单配比
  用了不同分类口径），都是我自查漏掉的。**这一条把它从「润色手段」抬到了「校验手段」**，
  也意味着 (a) 那一档（靠自觉）损失的不只是可读性。
- **治理类文本的出口不是逐词改写，是配一张词表。** 34 条里近六成是内部工作语言，逐个换成大白话
  会让文件长一倍且更难写。本文件的处置是在开头加一张约 20 行的词表，一次写好可被后续事项记录复用。
  **这实际上回答了「过不了怎么办」这个子问题**，可作为立法时的默认出口。
- **成本可量：一次约 5 分钟外加一轮订正。** 这个数字支持 (b) 或 (c)，但不支持「所有文字一律都过」。
  建议的必过范围（供裁决，非结论）：PR 正文与标题、验收记录、长期规范、README 与说明文档、
  方向级事项记录；不必过：机器格式文件、例行站位产物、只有 agent 自己读的过程留痕。

**正交裁项四｜六处挂账机器缺陷各自的处置**

批准清单与站位清单分叉、探针强度不足、评审看不见长期规范改动、入口守卫剩一处、路由表四处空白、
记账型断言。前五处都有明确的最小修法，第六处需要先确立判据（本轮已给出：**看这条断言背后有没有
不变量**，不看它像不像快照）。另有两条从上一单移交、本轮必须进风险表的残余项：受管投影副本的
自校验残余面（实测确认现有机制已兜住，残余面只剩跨版本历史情形），以及升级报告里那个逐字转载
外部输出的文本字段（实跑取值干净，但洁净来自巧合而非机器约束）。
