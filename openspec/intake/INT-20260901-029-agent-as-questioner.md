# Intake

## 原始问题

> 本条目是 `INT-20260901-023-repo-suited-workflow` 的**立论层**，不取代它。023 记的是症状
> （「本仓工作流不合适，生成了大量我不看的文档和文件」），本条目记的是那次症状追下去得到的根因。
> 之所以另开条目而非并入 023：023 已 `promoted`，`promotedTo: slim-workflow-and-plain-language`
> 且各段写满（该 Change 已于 2026-09-01 经 PR #22 合入 main，合并提交 `daaabc4`），硬并会把两套结论
> 搅在一起（与该分支会话协调后的取向，编号 029 由对方避让保留）。两单正交：slim 那一单清的是**产出侧
> 负担**（工件 8 份并 6 份、说人话关、可重跑验证不留日志），本条目补的是**输入侧缺口**（没有提问器）。

## Triage

范围：**「把念头变成该不该做的判断」这一段能力的缺口**，及其承载形态。不含本仓流水线的站位重排与
写盘清单裁剪——那是 023 与 `slim-workflow-and-plain-language` 的范围。**删写盘清单是本条目结论的推论，

023 的重设计取向应从「重排站位」改为「补输入侧的提问能力，产出侧交给 slim 那一单」。

判断：continue（立论已收敛，形态首版已落，等第二次真实使用验证）。

## Evidence

### 已知事实

- **根因（5 Whys 链，2026-09-01 主会话对谈得出）**：文件多 → 17 站每站写盘 → 站数照抄 spec 工具形状
  → 因为市面上唯一现成的答案是这类工具 → 它们第一句都是「描述你要构建的东西」，要求人先说清楚
  → 而**把念头变成判断本来就不是「说出来」的，是「被问出来」的**；那些工具没有一个是提问方。
- **四次尝试同一失败模式**：spec-kit、OpenSpec、BMad、自建 OpenSpec 改造版。维护者评价「都不好用、
  前置需求环节对齐非常困难」。跨四套工具复现，支持结构性缺陷而非选型问题。
- **维护者的真实能力分布（本轮对谈的直接证据）**：同一场对话中，agent 给出的断言式草案被连续纠偏
  五次（「我没理解到全景存在的意义」/「不是这样的，是控制我的 SDLC 工作流」/「不是这样的，公司的
  流程我也能控」等），每次纠偏都显著收敛；而被问开放题时的回答是「我的认知有点不太够了」。
  **判断能力远强于表述能力**——这是形态选择的第一约束。
- **独立复验**：`slim-workflow-and-plain-language` 分支在互不知情的情况下，独立得出「可重跑的验证不留
  运行日志」（理由：存下来的日志无法证明它对应当前这版代码），与本条目侧得出的「本仓没有审计员，
  那些证据是做给不存在的人看的」是同一结论。两条线撞到同一点。
- **当场抓到的重流程样本**：`slim-workflow-and-plain-language` 相对 main 为
  `69 files changed, 7148 insertions(+), 554 deletions(-)`——一个名为「砍纸」的变更净增 6594 行，
  增删比 13:1。原因是流程要求为该变更本身产出提案、决策、测试方案、实施任务、审读记录与 spec delta。
  该分支已确认会把此数字写进其验收记录并标注为复盘素材。
- **本条目验证路径产生的副产品**：2026-09-01 为 `clarify` 跑首轮行为评测时，一条含无主指代的探针让

## Pre-mortem 得出的五条设计约束

（按可信度排，前两条有本仓历史证据）

1. **发起必须零成本、不得有命令名**——防「走过一次再无第二次」。分析线 dogfooding 后零执行即此死法。
2. **问题必须针对当下痒点现生成，不得固化为模板**——防「提问退化成填空」。intake 五站推进时间戳
   0.5～1.0 秒内连点五下即此死法。
3. **不产出需要维护的文件**——防它自己变成第五个负担。
4. **只覆盖「我想建个 X」形状的痒点**，不硬套 bug 类。
5. **只回答「该不该做」，不回答「做成什么样」**——后者是下一段的债，不记在本条目头上。
