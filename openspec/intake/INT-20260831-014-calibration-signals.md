# Intake

## 原始问题

校准期信号台账（AGENTS.md 校准条款的记录位，持续追加，3 事项复盘时统一消费）。信号1（2026-08-31，事项 release-package）：维护者阅读 RA workflow 的 request JSON 时反馈『内容挺好，但 key 不是中文，看起来吃力』——机器 JSON 直接进入人的视野即产生阅读负担；支持『人审摘要层/中文渲染视图』候选（原 INT-007 options），同时提示 agent 摆盘时不应让机器文件出现在人审路径上。

信号2（2026-08-31，事项 release-package 门2）：维护者对 AGENTS.md 既有硬规则（禁止复制投影与第二套 lock）表示『已经忘了它是啥』并质疑其可废性——规则条文未随附理由，立法者数日后即无法复审。改进方向：AGENTS.md 每条硬规则附一句大白话理由（本 Change 修订第 5 条时首次执行）；规则的可审性与资产的可审性同源。

信号3（2026-08-31 主会话观察，事项 INT-015 收尾后的方向选择）：agent 摆出三个候选方向请维护者择一，维护者回『三个都可以，按你推荐的来』——决策授权下放，维护者不愿逐项选择。含义：把「并列候选」摆给人本身即构成审阅负担；对非风险性、非不可逆的岔路，agent 应直接给单一推荐＋理由，只在人有异议时展开候选比较。这与「摆盘须判断导向」的既有约定同向，但更进一步：候选清单不是默认摆法，而是仅在决策不可逆或代价显著时才用。

信号4（2026-08-31 主会话观察，事项 INT-015 验收门）：agent 在验收门摆出一屏材料后，维护者只回『同意』二字，无任何追问、无要求展开细节。含义：当前验收摆盘的粒度对维护者是可接受的（未触发不耐烦），但也未被真正消费到细节层——「零追问」既可解读为摆盘合格，也可解读为还可再压缩。本条为粒度基线记录，复读时应与信号3 合看：维护者的审阅意愿集中在结果与授权，不在过程细节。

信号5（2026-08-31 主会话观察，事项 INT-015 收尾）：维护者主动追问 intake 台账的完成度与归档状态——无人提示，由维护者自己发起。含义有二：其一，维护者对台账整洁度有真实关注，这是审阅面上少数「人主动来找」的位置，不宜裁剪；其二（关键），这条同时是「资产有人消费」的硬证据——intake 台账类资产存在真实的人类下游消费者，在第 2 块「按下游消费实况裁资产写盘清单」的裁决中应据此保留。

信号6（2026-08-31 主会话，3 事项复盘摆盘）：agent 按信号3、4 的读数把复盘裁决摆成高度压缩的一屏，维护者当场指出「摆盘过于精炼，请说明」，要求展开。含义：**信号4 的「零追问＝还可再压缩」这一推断被直接证伪**。维护者对摆盘深度的要求不是单调递减的常量，而是与决策分量挂钩——例行站位产物的一屏是够的，方向级、复盘级的重裁决必须说透，宁可超出一屏。由此确立规则「摆盘深度与决策分量匹配」：例行站位摘要从简甚至只写盘不摆；两道真门（方案门、验收门）保持一屏；方向级与复盘级裁决展开说透，允许超一屏。信号3（不愿逐项选择）与本条不冲突——它约束的是「不要把选择题推给人」，不是「不要把理由讲清楚」。

信号7（2026-08-31 主会话，3 事项复盘对分析线的裁决）：卷宗 INT-019 把分析 5 站三单零执行的成因列为两解（(a) 站位冗余 / (b) agent 绕开），请维护者裁决。维护者取 (b) 并给出原话：「我一直想让你跑，但一直无法对齐，就像你根本不听话一样」。含义：**零执行是对齐失败，不是站位冗余**——维护者的意图一直存在，失效的是传达链路。教训：**要求必须活在门禁里，而非活在文字里**。写在 AGENTS.md、docs 与 profile 描述里的「应当走分析线」对 agent 不构成约束力，只有 fail-closed 的机器检查才构成。凡是维护者反复要求却反复落空的事项，处置方向应当是把它 fail-closed 化，而不是据「没人用」把它裁掉；裁留判断必须推迟到强制执行产生真实消费数据之后。本条同时是 A1 候选（分析 5 站杀/修/留）的裁决依据。

信号8（2026-08-31 主会话，事项 enforce-analysis-line-and-prune-pipeline 方案门）：agent 摆出三个实现路线（候选 A/B/C）与 Trade-off 矩阵请维护者择一，维护者回「我有点不知道你要改什么以及怎么改」。含义：**路线比较不是可判断的材料**——A/B/C 的差异用「权威归代码 vs 归 profile」「单片 vs 两片」这类内部结构词表述时，维护者无法从中读出自己将感知到的变化。摆盘缺的不是深度（信号6 已上调深度），而是**落点**：方案门材料必须附一份「落地后可感知的具体变化清单」——哪些命令会消失、哪些操作以后会被拒绝、哪些文件不再产出、维护者自己的动作有何增减。本轮主会话已当场补摆该清单并据此获得裁定（「我觉得走 A 就行」），规则今后固化：**方案门摆盘 = 路线比较 + 可感知变化清单**，缺后者即为摆盘不合格；变化清单用维护者视角的动作与产物描述，不用模块名与架构词。本条与信号1（机器细节不进人审正文）同向，与信号6（重裁决展开说透）互补——展开的应当是后果，不是内部结构。

信号9（2026-09-01，事项 INT-20260901-022-thorn-batch，**强制版分析线的第一单真实运行**）：这是「先强制、后评判」要收集的头一份数据，按门禁行为、别扭处、缺口三类如实记录。

**门禁行为——全部如设计生效，无一处需要绕过。** 分五阶段逐站推进并刻意做了负向探针，观察到的状态与退出码分别是：capture 无判断即推进（`in_progress`，退出 0）；clarify 缺 `problemFrame` 时 `blocked` 并点名缺哪个输入（退出 1）；补齐输入但不给判断时 `waiting_human_judgment`（退出 1）；给出 `sufficient` 后推进（退出 0）。discover、evaluate、decision 三站的判断门表现完全一致。立项门（`intake promote`）在分析线 `status=completed` 且 `disposition=build` 后放行，并在输出里回显完整的路由判定（`tool-code` → `delivery-change` → `requiresAnalysis: true`）。**结论：强制门本身没有被绕开的空间，也不需要被绕开——本单从头到尾没有一次 fail-closed 是「挡错了」。**

**别扭处三条（都不影响正确性，但确实是使用成本）。** 其一，`completedStages` 要由调用方逐轮手抄回 request，跑满五阶段实际发出十次 `workflow run`；这正是 INT-007 早已记下的「调用方需手工维护状态机」，本单首次在真实事项上体感到——但也正因为手抄，才逼出了上面那组逐站负向探针，副作用是好的。其二，`disposition` 埋在 `outputs.publishedInputs` 下两层，取值时得知道这个位置；代码里已有注释说明为何不上提到顶层，理由成立，但对调用方是一次额外的认知成本。其三，request 是单文件累积增长，写到 decision 站时已是一份很长的 JSON，人不可能直接读——这与信号1 同向（机器 JSON 不该进人审路径），本单的处置是把同一份分析同时写进 intake 台账的中文小节，人读台账、机器读 JSON。

**缺口两条（本单实际撞上，已转入 fix-thorn-batch 的未决问题）。** 其一，**档位交叉校验对未声明条目不生效**：`declaredRoute()` 在条目未声明 `changeObject`、或声明了表外类别时返回 `null`，整个「声明与事实」的核对被跳过。结果是「如实声明的条目被核对，沉默的条目不被核对」。这不构成降档漏洞（未声明本身按未匹配取最重档过立项门），但核对面上确有空洞，且方向上略微惩罚了如实声明的一方。其二，**路由表的路径前缀有三处空白**：`.gitattributes`、`.github/**`、`openspec/changes/archive/**` 不属于任何一行，一律按未匹配取最重档（99）。本单声明 `tool-code`（20），于是「改一行 `.gitattributes`」或「给归档证据改名」都会被交叉校验判成降档而拒绝。路由表自己写着「第一次误挡的处置方式是调这张表，不是关门」——**本单就是第一次误挡**，处置按其自述走（补前缀行），不绕过、不缩小改动面迁就声明。

**缺口第三条（在写盘阶段撞上，不属分析线本身）**：`test/contracts.test.ts` 的 `VC-039` 用 `deepEqual` 钉死了 active Change 目录的完整集合。这不是不变量而是点时快照——**任何人新建任何 Change，这条测试都会立刻转红**。本单是第一个撞上它的：`fix-thorn-batch` 一建立，全量测试即从 79/79 掉到 78/79。已按最小机械改动把新 Change 登记进期望集合并加注说明，断言强度未变；形态是否改为真正的不变量已提交维护者裁。含义与信号7 同向：**门禁要活在机器里，但机器里的断言若把一次性快照写成永久判据，它就会变成阻碍正常流程的绊线**——强制化的副作用需要和强制化本身一起被观察。

**一条与摆盘规则相关的观察。** 本单方案门的三个候选之间，最硬的差别不是工程量而是「是否触发上述档位前置条件」。这意味着信号8 要求的「可感知变化清单」在本单里还得多写一类：不只是「落地后会怎样」，还有「选了这条路，动手之前先得干什么」。已在 `fix-thorn-batch` 的方案提案里按此撰写。

**对 A1 复盘的第一份读数**：分析线在本单是**有产出的**，不是仪式——它把 `INT-20260831-010` 挂了一整天的错误归因（git racy 竞态）在 discover 站用受控探针推翻，改判为 Windows 路径越限误判并给出精确阈值 260，修法方向随之从「加重试」变成「治路径能力与路径长度」。若无 discover 站的强制取证，这一单大概率会照抄旧归因去加重试。**第一单的证据支持「留」，但只有一单，按预置触发点应跑满 2 单后再裁。**
