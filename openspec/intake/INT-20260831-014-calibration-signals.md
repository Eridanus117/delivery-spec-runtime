信号11（2026-09-01 主会话，PR #20 提交前后）：维护者读到 agent 写的汇报与 PR 文字后，先说「这个黑化很严重啊，不说人话了」，随后再次指出「PR 的内容和标题都不说人话」。

clarify、discover、evaluate 三站补齐输入并给出 `sufficient` 后逐站推进（各退出 0）；跑到 decision 站
时按维护者指示**不提供决策报告与处置结论**，机器返回 `blocked` 并**逐项点名缺哪两项输入**
（`decisionReport`、`disposition`），退出 1。这个停靠状态正是「分析做完了、等人裁断」的准确机器表达，
不需要 agent 另写一句话去说明。

**别扭处四条（三条与首单重复，一条新增）。** 重复的三条：其一，已完成阶段仍要由调用方逐轮手抄回
请求文件；其二，请求文件是单文件累积增长，写到评估站时已是一份很长的 JSON，人不可能直接读——本单的
处置与首单相同，把同一份分析同时用中文写进台账，人读台账、机器读 JSON；其三，结论字段埋在输出里两层深。
**新增的一条**：`workflow run` 的标志名在说明面查不到——README 只写「必须同时指定该 Change 根和 request
文件」，没给标志名本身，第一次调用写成 `--request` 被拒。好在错误文案直接点名了正确的 `--request-file`，
一次改对，**属于「文档没写全但机器把话说清楚了」的形态，成本很低**。

**这一单额外撞到的两件事。** 其一，分析线的三份产物里**只有绑定记录与结果记录有机器读者**（立项门读
它们），**请求文件全仓检索没有任何代码读取**——它是纯过程留痕。这与信号1、信号10 是同一个话题：一份
没有机器读者、人也读不动的文件，它的价值只能来自「写它的过程逼 agent 想清楚」，这个价值真实存在
（两单都是在写取证段时才发现关键事实），但**这类资产的正当性理由与「有下游消费」是两回事，重设计时
不应混为一谈**。其二，本单为写取证段做的全仓盘点，第一次量出了产出配比的确切数字——最近一单为改
219 行工具代码写了 2013 行治理文档，约九比一。**这个数字是信号10 那句话的量化版本**，此前只有「大量」
这个体感词。

**对 A1 复盘的第二份读数**：分析线在本单同样**有产出、不是仪式**——它把散在六七份台账里的材料收敛成
一份可比较的路线表，且取证站的强制盘点直接量出了上面那个九比一的配比（若不走这一站，本单大概率会
照着体感写「文档偏多」而拿不出数字）。**两单证据合起来支持「留」，但同样两单都记下了同一批使用成本，
故支持的具体取向是「留，但修使用成本」，不是「留着不动」，也不是「杀」。** 最终裁定由维护者在
`INT-20260901-023` 的门口给出，本条不预判。
