## 选择依据

- 该实现路径与已批准的总体架构 A 一致：一个 Workflow System / Spec 仓承载通用 core 和多个 profile，Change 绑定 profile 身份与版本。
- 通过新增 profile contract、registry/loader、Change binding 和 workflow dispatch，可以先验证多 profile 选择和隔离，而不重写既有 `delivery-change` 生命周期。
- 现有 `runtime-entry.ts`、gitlink、三个相对软链、版本 pin 和 fail-closed 检查属于已验证的稳定边界；增量方案可避免首轮同时改动全部边界。
- 新能力可以通过独立命令分支和合成 profile 测试；新路径失败时，现有 `delivery-change` 仍可运行。
- 上层只保留总体架构决策和链接；profile 解析和执行不依赖任何外部工作台。

## 接受的后果

- 短期同时存在旧 `delivery-change` 路径和新的 profile workflow 路径，需要在入口、文档和结果合同中明确分界。
- 需要新增 profile registry/loader、Change profile binding、版本 pin、冲突检查和 profile 级测试。
- 现有 `delivery-change` 首轮只做兼容识别或 adapter，不重写其 artifact、命令、锁和生命周期门禁。
- V0.1 需要两个合成 profile 证明识别、选择、版本固定和结果隔离，但不实现多个完整业务 profile。
- 本 Change 不实现全局路由、全局扫描、跨仓同步、持久化平台、私有仓迁移或仓库可见性变化。
- 未来若需要统一入口，可以在真实 profile 证据充分后另立 Change，不能在本 Change 中隐式升级为直接重构。

## 拒绝方案

- 候选 B：直接重构统一入口。不选，因为会同时影响 `runtime-entry.ts`、`delivery-control.ts`、manifest、版本校验和既有 delivery lifecycle，首轮回归与回滚风险过高。
- 候选 C：先拆出独立 Workflow System 仓。不选，因为仓库私有化、迁移、权限和 submodule 变更不属于当前多 profile 合同切片，且会在模型尚未真实验证前扩大范围。

## 重新决策触发条件

- 增量 profile 层无法在不复制或污染 `delivery-change` 的情况下实现 Change profile selection。
- profile contract 无法表达至少两个 profile 的身份、版本、阶段或结果隔离。
- 新入口必须修改既有 fail-closed、gitlink、manifest 或版本 pin 才能工作。
- 真实 profile 接入证明旧入口与新 profile 层必须共享不可拆分的状态存储或统一发布节奏。
- 当前公共 Runtime 的私有化或迁移方案改变本 Change 的仓库边界。
