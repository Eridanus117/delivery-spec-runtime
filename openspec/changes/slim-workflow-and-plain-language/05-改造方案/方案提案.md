## 读这份文件需要先知道的词

| 词 | 意思 |
|---|---|
| **本仓** | `delivery-spec-runtime`。它是一套交付工作流，别的仓库可以当 Git 子模块接进去用。 |
| **Change / 一单** | 一次成建制的改动，在仓库里表现为 `openspec/changes/<名字>/` 这样一个目录，里面装着这次改动的全部文档与证据。「一单」就是「一个 Change」的口语说法。 |
| **工件** | 走一遍流程会产出的那批文件（方案文档、测试方案、验收记录、各种状态 JSON）的统称。 |
| **必产工件** | 流程强制要求必须写出来的那几份，不写就过不了门禁。今天是 8 份（见下条）。 |
| **八层** | 那 8 份必产工件的排列顺序：①原始需求索引 ②长期规范增量 ③现状 ④方案提案 ⑤方案决策 ⑥改造方案 ⑦测试方案 ⑧实施任务。**验收记录与发布计划不算在这八层里**（它们在实施完成之后才产生），所以处置它们不改变「层数」。 |
| **门** | 必须由人表态才能过的节点。人的视角只有三道：**立项门**（这事做不做）、**方案门**（走哪条方案）、**验收门**（认不认这个结果）。 |
| **交付线七站** | 完整流程的七个节点：方案提案 → 方案决策 → 实施任务 → 实现审查 → 验收 → 规范同步 → 归档。**它与「八层」是同一件事的两种切法**：八层说的是「要写出哪些文件」，七站说的是「按什么顺序推进」。三道门是这七站里需要人出面的那几处（方案决策、验收）加上开工之前的立项。 |
| **分析线五站** | 立项之前用来把一个模糊需求想清楚的另一条流程：捕获 → 澄清 → 核验 → 评估 → 决定。它跑完才谈得上立项。本单的立项就是这么来的。 |
| **门禁** | 会拒绝执行下一步的机器检查，写在 `openspec/tools/` 的工具代码里。跑的时机是每次调用这些工具时。 |
| **断言** | 测试里的一条检查。本仓现有 91 条测试。**「改 12 条断言」就是「改 12 处测试检查」。** |
| **机器契约** | 规定某类 JSON 文件必须长什么样的校验规则文件，放在 `openspec/contracts/`。 |
| **内容哈希 / 新鲜度** | 工件被批准时，把它的内容算出一个哈希值存进批准记录；以后只要文件内容变了、哈希对不上，这条批准自动失效，流程被拦住。本文说「记录摘要」时，指的一律是**这个哈希值**，不是内容概要。 |
| **批准记录** | 记「哪份工件被谁批准了、当时内容的哈希是多少」的一条条记录，存在 `artifact-approvals.json` 里。今天一单有 8 条，一份工件一条。 |
| **说人话关** | 本文对下面这整套办法的统称，它由三部分组成：**必过清单**（哪些文字必须走这道关）、**陌生读者审读**（把文字交给一个没读过本仓任何东西的会话，请它只圈看不懂的地方）、**审读记录**（把原始意见和每条意见的处置结论存档）。 |
| **台账** | `openspec/intake/` 下的一份份记录，每份记一件事的来龙去脉。**方向级台账**＝其中那些记录方向性裁决的（比如本单的来源 `INT-20260901-023`），区别于只记一个小缺陷的。 |
| **快车道** | 给低风险小改动准备的短流程（登记 → 实施 → 快速验证），与七站的完整流程并列，同一件事只走其中一条。 |
| **评审 / 独立评审** | 另起一个不知道实施过程的会话，让它对着代码改动逐条复查，输出问题清单。 |

## 决策问题

请维护者在三个地方各选一个做法：

1. **工件怎么合并**——八层压到几层，哪几份合进哪几份。
2. **批准记录收到几条**——现在一单 8 条，收到几条、按什么口径收。
3. **「说人话」这道关做成什么形态**——写进规则靠自觉、留一份审读记录由门禁校验、还是做成流程的一站。

**第 1 件和第 3 件互不影响，可以自由组合。第 2 件与第 1 件有一处耦合**：如果批准仍按「一份工件一条」
的口径，条数就跟着层数走，不能自由挑；只有改成「按人表态的次数」这个口径，它才与层数无关。
下面的拆项表会标出这处耦合。

## 约束

以下六条不可违反：

1. **两处强校验不得削弱。** 其一，评审记录里「审查了哪些路径、结论是什么」必须由代码自己算出来，
   不接受人工把这个范围改小；其二，验收状态绑定四样东西（评审记录、任务状态、验收记录、实现提交），
   任一被事后改动，验收状态即失效。
2. **方案提案与方案决策必须是两份文件。** 这是长期规范里的硬要求，理由是提案作者不能代替维护者作
   决定；写在同一份文件里，就没法区分「我建议」和「他同意」。
3. **写进文档的要求对 agent 不构成约束**，只有会拒绝执行的机器检查才构成。本仓已有反例：分析线在
   只写进文档、没写进机器检查的那段时间里，三单一次都没跑。
4. **不得单向解读为「少写资产、取消人工审阅」。** 现行规则要求维护者的反馈双向记账——他要求把材料
   写得更详细、和要求把材料压缩，都要一样记进校准信号台账 `INT-20260831-014`，复盘时一起看。
   本事项属于「要求压缩」的一侧。
5. **已归档的 Change 不迁移。** 代码里为此维护着两张工件路径表（旧结构一张、新结构一张），读旧目录
   走旧表、读新目录走新表。**再改一次工件形状，就要面对「会不会变成第三张表」这个问题**——这是本单
   在成本上要盯住的地方。
6. **本 Change 自己要走完整流程**，不能自我豁免——它改的是流程规则本身，属最重档。

## 一个必须先说清楚的事实：一个 Change 目录里的文件都是些什么

后面三个候选都要谈「砍掉多少文件」，所以先把基数摊开。**最近一单（`fix-thorn-batch`）目录里
一共 39 个文件**，构成如下（全仓 15 个 Change 目录共 427 个文件，平均一单 28.5 个——这是平均值，
不是某一单的实际数）：

| 类别 | 份数 | 具体是什么 | 本单砍纸砍不砍得到 |
|---|---:|---|---|
| 必产工件 | 10 | 八层里的 8 份，其中长期规范增量那一份实际是 3 个文件（改了 3 个能力） | **砍得到** |
| 实施后产出 | 2 | 验收记录、发布计划 | 砍不到（都有机器读者） |
| 状态 JSON | 7 | 批准记录、任务状态、评审记录、评审输入、验收状态、归档就绪、Change 基本信息 | 归档就绪那一份并入验收（已定），其余砍不到 |
| 配置 | 1 | `.openspec.yaml` | 砍不到 |
| 证据日志 | **19** | 实施期跑测输出 9 份、验收 run 的原始输出与追踪 10 份 | **砍不到**——维护者已裁定保护性记录取中间档 |

**结论：合并工件最多能减掉 1 到 3 个文件，再加归档就绪并入验收减 1 个。**「39 减到 15」做不到，
因为 39 里有 19 份是证据日志，而维护者已经裁定证据保留。这一点推翻了台账 `INT-20260901-023` 里
「一单从 28 个文件降到大约 15 个」那个估算——**那个估算只数了工件，没数证据与状态文件**。
本文按实际文件清单重算，见「未决问题 1」。

## 候选 1｜轻合并：只并掉最没争议的一份

- **方案**：
  - 工件：八层压成**七层**——只把「现状」并进方案提案（现状本来就是提案要交代的事实依据）。
  - 批准：口径不变（一份工件一条），条数从 8 条变成 **7 条**。
  - 说人话关：把必过清单写进规则文件，**由 agent 自觉发起审读**，不加任何机器检查。
- **优点**：改动面最小；不碰任何门禁；模板与测试只动一处；想改回来几乎没有成本。
- **缺点**：
  - **基本没有回答维护者的原话。** 一单少 1 个文件（39 → 38），他翻仓库时感觉不到差别。
  - 批准仍是 7 条对应他在方案门说的那一次话。
  - 说人话关靠自觉这一档，本仓有明确反例（约束 3）。
- **成本**：改 1 份模板、1 张工件路径表、约 4 条测试断言、1 份说明文档。
- **风险**：低，但主要风险是「做了等于没做」，下一轮还要再来一次；而每来一次都要付一遍完整交付
  仪式——按最近一单实测，一单要写约 2000 行治理文档。
- **可逆性**：最高。

## 候选 2｜中合并：并掉两份没有任何读者的工件，批准改按「人说了几次话」记

- **方案**：
  - 工件：八层压成**六层**——「现状」并进方案提案；「改造方案」并进实施任务（这两份都在方案决策
    之后产生、都是写给实施者看的，合并不打乱顺序）。测试方案保留，理由见缺点栏下的说明。
  - 批准：口径从「一份工件一条」改成**「人真实表态一次记一条」**，一单 **2 条**：
    - **方案门那一条**，覆盖当时已经写完的全部六份必产工件（原始需求索引、长期规范增量、方案提案、
      方案决策、测试方案、实施任务）。**这条记录里仍逐份列出每一份的内容哈希**，所以「改了哪一份
      就失效、并且能点名是哪一份」的能力一份不丢。
    - **验收门那一条**，即验收裁定。
    - **立项门不产生工件批准记录**——今天也不产生，它的表态记在台账的历史栏里。所以「三道门只有
      两条批准」不是漏了一道，是立项门本来就不在这套记录里。
  - 说人话关：必过清单写进规则文件；**每次审读都要留一份记录**（原始意见原文 + 每条意见的处置
    结论），由门禁校验「清单内的每一项都有对应记录、每条意见都有处置」。审读本身仍由 agent 去找
    一个无上下文会话完成，**工具不代为派发**。
- **优点**：
  - 并掉的两份是全仓仅有的「机器一个字都没读过、也找不出下游引用」的文档。
  - 批准记录从 8 条变 2 条，**每条都能对上他真说过的一次话**——这是现在这套批准链最失真的地方。
  - 说人话关有可校验的产物，不再靠自觉。
- **缺点**：
  - **丢掉「现状独立成件」这道工序。** 它原本的作用不是被人读，而是**逼 agent 在动手前先把事实查
    清楚**——效果来自写它这个动作本身，不是来自有人读它。这正好暴露了「有读者才产出」这把尺子的
    一个边界：**尺子量的是产出物有没有人消费，量不到写作过程的副作用。** 并进提案后会不会退化成
    一段套话，没有任何机器判得出来。
  - 批准口径要动机器契约与相关测试，改动面比候选 1 宽。
  - **审读记录是可以伪造的**——agent 完全可以自己编一份「意见清单」。
  - 保住测试方案的理由需要说清楚：它的编号被任务表与验收覆盖表逐条回引，也就是说**它有下游依赖，
    删了会断链**。至于是否真有人逐字读它，本仓没有证据；这个理由只能支撑「不删」，不能支撑
    「有人在读」。
- **成本**：改 3 份模板、1 张工件路径表、**2 份机器契约**（批准记录一份、审读记录一份）、
  约 12 至 16 条测试断言、1 份命令文档（实测：9 份命令文档里只有归档那一份点到了具体工件层目录，
  其余八份只泛指「工件」）、2 份说明文档。
- **风险**：中。最大的一处是审读记录的伪造面；缓解办法是把「抽查审读记录与文本实际问题是否相符」
  加进独立评审的职责——独立评审是全仓唯一有拦截战果的环节（12 份评审记录共查出 51 条问题）。
- **可逆性**：高。不改动任何现有门禁的判断逻辑，只新增一条校验（审读记录是否齐备），是加法不是改法；
  工件与批准的改动都是清单与模板，回滚就是把表改回去。

## 候选 3｜深合并：连测试方案也并掉，说人话关做成流程的一站

- **方案**：
  - 工件：八层压成**五层**——在候选 2 的基础上，把「测试方案」也并进实施任务。
  - 批准：一单 **1 条**覆盖式记录，方案门与验收门各签它的一个字段。
  - 说人话关：做成流程里的一站，**由工具真的去派发一个无上下文会话**并把原始输出落盘，
    agent 无法自己伪造。
- **优点**：工件份数最低；审读关不可伪造，是三档里唯一真正封死自觉空间的做法。
- **缺点**：
  - 测试方案**有下游依赖**（编号被任务表与验收覆盖表逐条回引），并掉它会断链。
  - 「由工具派发一个会话」在本仓**没有现成能力**，要新造一套调度与落盘机制。这本身就是一个独立
    事项，绑进本单会让改动面失控。
  - 1 条覆盖式批准让方案门与验收门共用一条记录，**定位能力明显变粗**——工件变了只知道「这一单有
    东西变了」，说不清是方案变了还是验收结论变了。
- **成本**：最高。候选 2 的全部成本，另加一套会话派发机制、它的契约与断言。
- **风险**：高。新造的机制没有任何先例；本单是流程改造单，把一个未验证的新能力塞进来会让评审面失控。
- **可逆性**：中。工件与批准可逆，新造的派发机制一旦落地不容易撤。

## 推荐

**推荐候选 2。** 三条理由：

1. **它是唯一一条既回答了原话、又没有砍掉任何有下游依赖的东西的路。** 被并掉的两份（现状、改造
   方案）是全仓仅有的「机器一个字都没读过、也找不出下游引用」的文档；测试方案有引用链，所以留。
   候选 1 不敢并，候选 3 并过了头。
2. **批准口径改成「按人表态的次数」，修的是这套批准链最失真的地方。** 全仓 15 个 Change 累计
   107 条工件批准记录（各单工件份数不同，早期是 9 份结构，所以不是简单地按单数乘 8）；同期维护者
   在三道门内能逐字引用的表态合计约 53 字，其中 6 次是「同意」二字。把一次表态展开成多条独立签发
   的记录，会让读批准链的人分不清「他表了 8 次态」和「他表了 1 次态、被复制成 8 条」。改口径之后，
   每条批准里仍逐份记录被覆盖工件的内容哈希，所以「改了哪一份就失效」的定位能力一份不丢。
3. **它把「说人话」立成了有产物的检查，而没有为此新造机制。** 伪造面交给独立评审抽查——评审是全仓
   唯一有拦截战果的环节，把这件事交给它，比新造一套派发机制更符合本单的分量。

**不推荐候选 1 的原因**是它很可能白做：一单少 1 个文件，维护者感觉不到差别，而下一轮再改要再付一遍
完整交付仪式。

**不推荐候选 3 的原因**是它同时踩了两条本单自己立的判据：砍掉了有下游依赖的东西，以及把一个未经
验证的新能力绑进一个流程改造单。

**本提案不构成决定。** 三件事可以分别取，混搭规则见上面三张表。

## 未决问题

1. **「砍纸」的战果比原先说的小得多，接受吗？** 台账 `INT-20260901-023` 估的是「一单从 28 个文件
   降到大约 15 个」，本文按最近一单的实际文件清单重算后，合并工件只能减 2 到 3 个（39 → 36）。
   差额几乎全在证据日志上——最近一单 39 个文件里有 19 份是跑测输出与验收 run 的原始记录，而维护者
   已经裁定保护性记录取中间档、证据保留。**所以摆在面前的是一个二选一**：接受「砍纸战果就是这么大」，
   或者把证据日志的保留方式也纳入本单（例如只留结论、原始输出压缩或外置）——后者会动到已定的
   「中间档」裁决，需要他重新表态。
2. **要不要先花一次复测去取证「评审战果与工件数量有没有因果」？** 那 51 条评审问题全部来自「另起一个
   不知情会话逐条复查」这个动作，但这个动作与「写了多少份工件」之间**没有已证实的因果**。取证方式
   是可行的：挑一单已完成的，只给评审者代码与提交范围、不给工件，看能不能复现同样的问题清单。
   代价是多花一次复测的时间（约等于一轮评审）。
3. **审读记录的伪造面用什么兜？** 本文建议交给独立评审抽查，但这是把一个新职责加到评审身上，而评审
   本身已经不轻——最近两单各跑了三轮、前两轮都判不通过。是否接受？
4. **指标子系统怎么处置？** 315 行代码、一份机器契约、118 行测试，另有四处说明文档提到它；至今零使用、
   零事件，统一入口里没有任何转发，消费仓根本拿不到。零使用的成因未查——可能是接入太麻烦，也可能
   单人单仓根本不需要度量。成因不查清就只能按「没人用」处置，无法区分「不需要」和「太难用」。
5. **指标子系统对应的那个 Change 目录怎么办？** `establish-runtime-metrics-baseline` 从 2026-08-30
   建立至今仍是在途状态，目录里还是旧版的工件结构（现状分成业务、技术两份），批准记录里一条都没有，
   而它的台账条目 `INT-20260830-005` 里「已立项到」那一栏填的目标已经对不上任何现存对象。
6. **「通用核心 vs 本仓特有」这张表要不要落成机器约束？** 本文的取向是不落（只有一个仓的证据），
   但这意味着第二个仓接入时没有任何机器帮忙区分哪些该改、哪些不该改。
7. **新形状生效之后，要不要为本单自己补一次迁移？** 新的工件形状要在本单验收之后才生效，所以本单只能
   按旧形状交付——也就是说，本单会再生产一遍它想消灭的那两份文档。两个做法：接受这一次，让下一单
   自然用上新形状；或者在本单收尾时额外做一次自我迁移。后者会让本单的改动面变宽。
