## 第 4 条：证据记录的新原则（这是本次最重要的一处改动）

维护者原话：

> 「测试日志和验收证据，在 vibe coding 中意义不大……我们只能通过请求去构造场景，走请求去验证。
> 我会觉得单测其实根本不需要记录。」

**判据不是「证据重不重要」，是「这次验证能不能再跑一遍」：**

- **可重跑的验证**（本仓的自动化单元测试就是）——**不留任何运行日志**。要验证就当场再跑一遍，
  跑出来的结果比存下来的日志更可信，因为存下来的日志无法证明它对应的是当前这版代码。
- **不可重跑的验证**——**必须记录，而且这是唯一的一次机会**。维护者公司里的事项属于这一类：
  没法写单元测试，只能构造请求走一遍场景，做完这一次就没了，不记就永远丢了。

**对本仓的具体后果**：每个任务附带的证据日志整体取消，相关的机器校验同步调整；验收记录保留
结论性的数字（跑了多少项、过了多少项），不保留原始输出。

**这一条必须写进「通用核心 vs 本仓特有」清单**，它是未来公司仓接入时最关键的一处差异：
底盘要保留「记录验证过程」这个能力，但要明确标注它的适用场景是不可重跑的验证；本仓因为验证全部
可重跑，所以在本仓这个能力恒为关闭。

**这一条也修正了提案里的一处判断。** 提案的未决问题 1 说「39 个文件里 19 份是证据日志，而证据
保留是已定裁决，所以只能砍到 36」。维护者的这条纠正推翻了那个前提：证据日志不是保护性记录，
**因此本单的精简战果比提案说的大得多。按最近一单的 39 个文件重算：合并工件减 2 份、归档就绪并入验收减 1 份、
证据日志整体取消减 19 份，落到约 17 个文件。** 提案里那张变化清单写的是 39 → 36，按本条裁定已失效，
已在提案中就地标注并给出新数字。

## 第 5 条：禁词单

维护者原话：

> 「对于黑话，我是不是可以通过黑名单的问题来解决」

- 复用仓内已有的禁词检查形态，建一份「人话禁词单」。
- **首批两个词写在名单里**，不在这里复述——这份文件自己就在必过清单上，写出来会被自己的检查拦下。
  名单位置：`openspec/profiles/plain-language-v1.json` 的 `bannedWords` 段，每条都带替代词与理由。
  一个是 agent 自造、维护者不认得的说法，替代词是「精简工件」；一个是维护者明确表示不喜欢的常用词，替代词是「事项记录」。
- 作用范围与说人话关的必过清单一致：PR 的正文与标题、验收记录、README 与说明文档、长期规范、
  方向级事项记录。
- **只作用于今后产出的文字**，存量文件不做大规模改写，碰到时顺手更新。
- 维护者每嫌弃一个词就往里加一条，名单只增不减。

**本 Change 的显示名因此改为「精简工件与说人话」**——原名里那个词正是首批禁词之一。

## 第 6 条：摆材料要附路径

维护者原话：

> 「我现在只能审阅你的三件事，我有地方可以审吗」

含义：他在门口只看到了 agent 摆出来的那一屏，不知道这一屏背后的东西存在哪、想细看该去翻哪个文件。
**今后每次摆材料必须附上底层文件的存放位置**，写进交互指引。

## 拒绝方案

| 被拒的 | 为什么 |
|---|---|
| 候选 1（轻合并） | 只并掉一份，维护者翻仓库时感觉不到差别；下一轮还要再来一次，而每来一次都要付一遍完整交付仪式 |
| 候选 3（深合并）中「并掉测试方案」那一半 | 维护者当场否掉：「测试方案不并」。它有下游依赖，编号被任务表与验收覆盖表逐条回引 |
| 候选 3 中「1 条覆盖式批准」 | 两道门共用一条记录，出问题时说不清是方案变了还是验收结论变了 |
| 候选 3 中「工具真的派发无上下文会话」 | 本仓没有这个能力，要新造一套调度与落盘机制；把未验证的新能力绑进一个流程改造单会让改动面失控 |
| 提案里证据记录的三个选项（全留 / 部分留 / 压成一条摘要） | **整组被维护者的新原则取代**。三个选项都建立在「证据按重要程度分档」这个前提上，而真正的判据是「能不能再跑一遍」 |
| 推倒重来 | 立项门已裁定推迟，触发条件是「第二个仓接入、第一个非代码事项跑过之后」 |

## 接受的后果

1. **丢掉「现状独立成件」这道工序。** 它原本的作用不是被人读，而是逼 agent 在动手前先把事实查清楚。
   并进方案提案后会不会退化成一段套话，没有任何机器判得出来。**接受这个风险**，观察点是：三单之内
   若出现「现状那一段写成套话」的实例，就把这道工序加回来。
2. **审读记录可以被伪造。** agent 完全可以自己编一份意见清单。**接受这个风险**，缓解办法是把
   「抽查审读记录与文本实际问题是否相符」加进独立评审的职责。
3. **取消证据日志之后，历史无法回溯「当时那一版代码跑测是什么输出」。** 接受——因为要复核就当场
   重跑，而重跑的结论比历史日志更可信。已归档 Change 里的证据日志不删、不迁移。
4. **工件路径表会多出一张（第三张）。** 旧结构一张、当前结构一张、新结构一张。接受，因为已归档的
   Change 不迁移是既定取向；沿用「按各 Change 自己声明的版本取键集」这个已有机制，不新增兼容层。
5. **本单自己仍按现行结构走完。** 新结构要在本单验收之后才生效，所以本单会再生产一遍它要消灭的
   那两份文档（现状、改造方案）。**本单是最后一单旧结构。** 这个事实写进改造方案。
6. **禁词单只管今后。** 存量文件里那两个词仍然到处都是，包括本 Change 自己的方案提案。不回溯改写，
   碰到顺手更新。
7. **批准记录改口径后，早期 Change 的批准记录仍按旧口径解析。** 与工件路径表同理。

| 5 | 指标子系统那个挂着的在途 Change 目录怎么办 | **本单不处置**，与第 4 条一并留到那次裁决 |
| 6 | 「通用核心 vs 本仓特有」要不要落成机器约束 | **不落**。只有一个接入方，写死等于把猜测当结论；第二个仓接入时再议 |
| 7 | 新形状生效后要不要为本单自己补一次迁移 | **不补**。本单按旧结构走完，下一单自然用上新结构 |

## 重新决策的触发条件

- 三单之内出现「现状那一段写成套话」的实例 → 重新考虑第 1 条。
- 出现一次审读记录与文本实际问题明显不符、且未被评审抽查发现 → 重新考虑第 3 条的形态。
- 第二个仓接入、或第一个不可重跑验证的事项跑起来 → 重新审视第 4 条在通用底盘上的表达是否够用。
- 禁词单增补到需要维护者反复回忆「这个词为什么被禁」时 → 给每条禁词补上替代词与理由。
