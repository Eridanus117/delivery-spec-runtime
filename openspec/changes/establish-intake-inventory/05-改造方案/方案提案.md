# 方案提案

## 决策问题

如何让 Workflow 在处理 Intake backlog 前，可靠识别当前条目、legacy 条目、重复身份和不可解析文件，同时不替维护者决定业务归属、不修改历史资产。

## 约束

- 只处理调用方指定项目根下的 `openspec/intake/`。
- 不读取或写入 Desk、其他仓库、Runtime submodule 或未授权路径。
- 不把 legacy 静默转换为新状态，不自动删除、合并、重命名或 Promote。
- 输出必须确定性排序、机器可读，并保留人工判断所需的全部冲突文件。
- 保持当前单文件 Intake 命令和 `delivery-change` 生命周期兼容。
- 只提交公共、合成或审查后脱敏资产。

## 候选 A：仅增加目录清单命令

- 方案：新增 `intake list`，扫描 `INT-*.md`，返回文件路径、ID 和粗略格式分类；重复 ID 由调用方自行判断，`inspect` 保持现状。
- 优点：实现范围最小，几乎不改变既有单文件行为。
- 缺点：重复身份和 legacy 缺口仍需调用方二次解析；无法直接满足自动化分流的最小输入。
- 成本：低。
- 风险：调用方可能把多个同 ID 文件或无法解析文件当成正常事项。
- 可逆性：高，可删除 list 入口，不影响已有文件。

## 候选 B：清单、重复诊断与 legacy inspect 一体化

- 方案：新增只读 `intake list`；输出确定性条目、重复 ID 分组和 legacy 缺失字段；同时让单文件 `inspect` 对 legacy 返回结构化报告，而不是直接失败。任何冲突只报告，不作归属决定。
- 优点：一次提供 Workflow 所需的完整输入；身份冲突显式可见；符合 Intake spec 的 legacy 迁移路径；不改变资产内容。
- 缺点：需要定义输出合同、兼容旧 parser 和补充负向测试。
- 成本：中低。
- 风险：旧调用方若依赖失败文本，可能需要适配结构化结果；错误分类必须避免伪造当前状态。
- 可逆性：高，新增命令和报告分支不改变成功的新格式写入路径。

## Trade-off 矩阵

| 维度 | 候选 A | 候选 B |
|---|---|---|
| 最小实现成本 | 更低 | 低 |
| 自动分流完整性 | 弱 | 强 |
| 重复 ID 可见性 | 需调用方处理 | 直接报告全部冲突文件 |
| legacy 兼容 | 不足 | 符合 spec |
| 对既有写入行为影响 | 极低 | 低，inspect 输出新增 legacy 分支 |
| 数据安全 | 只读，但边界需重复实现 | 统一复用受控根和文件过滤 |
| 回滚 | 删除 list | 删除 list 和 legacy 报告分支 |

## 推荐

推荐候选 B。当前主要阻塞不是“有没有文件列表”，而是“能否安全知道哪些文件可以交给 Workflow”。如果不同时报告重复 ID 和 legacy 缺口，自动分流仍会把身份冲突和旧格式错误推给 Agent，违背 fail-closed 边界。

## 未决问题

- 业务优先级排序暂不在本 Change 中决定；清单只提供确定性文件顺序和诊断，后续由 Workflow/维护者判断。
- legacy 文件是否迁移、两个重复 ID 文件最终保留谁，暂不自动决定。
