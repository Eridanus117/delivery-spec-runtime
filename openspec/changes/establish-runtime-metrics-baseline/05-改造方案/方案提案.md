# 方案提案

## 先看结论

这次不是要马上提高并发，而是先决定“以后由谁负责把运行过程记录下来”：

- **候选 A：手工记录**。马上可以开始，但容易漏记，之后很难证明 C 和 C+1 是按同一口径记录的。
- **候选 B：Runtime 提供一个小型本地记录器**。需要一次正式实现，但字段、敏感内容边界、重复事件和汇总公式都能由机器检查。

我的建议是 **候选 B**。它不做远程 telemetry、不自动调度 Agent、不自动提高并发，只负责本地记录和汇总。

维护者审阅时只需要回答：接受候选 B，还是选择成本更低但更依赖人工的候选 A？

## 决策问题

在不直接提高 Agent 并发度、不建设远程 telemetry 的前提下，如何建立可信的当前并发 `C` 基线，并为后续 `C+1` 对照提供可比较数据？

## 约束

- 标准化优先：事件字段、枚举、时间和指标公式必须固定；脱敏负责隐私边界。
- 原始事件只存本地私有 state 目录，不写项目仓库、Runtime submodule 或远程服务。
- 不能把合成运行当作真实基线，不能猜测 Agent 调度器的实际 `activeCount`。
- `C+1` 只能改变并发槽位，不自动修改长期配置。
- Runtime 变更必须经过本 Change 的完整生命周期；本提案不直接修改源码。

## 候选 A：运行者手工记录模板

- 方案：提供固定事件字段、JSONL 模板和汇总表，由运行者在每次真实运行的边界手工追加事件并计算 C 基线。
- 优点：最快、改动最小、不依赖 Agent 调度器接口；可立即验证指标口径。
- 缺点：容易漏记、时间不准确、不同运行者执行不一致；无法自动确认事件完整性。
- 成本：低；主要是文档、模板和人工记录成本。
- 风险：数据完整率和时间精度不足，可能使 C+1 对照失去解释力。
- 可逆性：高；删除模板即可停止，不影响 Runtime 行为。

## 候选 B：Runtime 受控本地事件记录与汇总

- 方案：在 Runtime 增加标准化事件 schema、本地追加写入器、敏感内容/路径守卫、重复事件拒绝、损坏检测和 C/C+1 汇总 CLI；Agent 调度器通过显式接口提供 `slotCount`/`activeCount`，未提供时报告缺失，不猜测。
- 优点：字段和枚举由机器合同强制；可重复计算、检查完整率和拒绝越界数据；后续可接入不同调用方。
- 缺点：需要新增 Runtime 代码和合同测试；仍依赖调用方提供真实事件和并发上下文，不能自动观测没有接口的调度器。
- 成本：中等；包含 schema、工具、测试、文档和 Change 生命周期成本。
- 风险：若接口设计过宽，可能演变为 telemetry 平台或意外保存业务内容；必须保持低频和本地边界。
- 可逆性：中高；移除采集入口即可停止，原始本地文件可清理，公共合同可按版本保留。

## Trade-off 矩阵

| 维度 | 候选 A：手工模板 | 候选 B：Runtime 本地记录与汇总 |
|---|---|---|
| 启动速度 | 高 | 中 |
| 标准化强度 | 中 | 高 |
| 数据完整性 | 低至中 | 高 |
| 对 Agent 调度器依赖 | 低 | 中，需显式上下文接口 |
| 隐私边界可验证性 | 依赖人工 | 可由合同和路径守卫验证 |
| 初始实现成本 | 低 | 中 |
| 长期重复使用成本 | 高 | 低至中 |
| 回滚难度 | 低 | 中 |
| 远程 telemetry 风险 | 低 | 中，可通过非目标和 fail-closed 控制 |
| 适合作为 C+1 证据 | 试运行 | 正式基线 |

## 推荐

推荐候选 B，但限定为“本地、低频、受控事件记录与汇总”，不实现远程上传、自动调度或长期并发修改。

原因：当前工作的核心问题是标准化和可比性。手工模板适合一次性试跑，但无法稳定保证事件完整性、重复处理和敏感内容边界；Runtime 受控记录器可以把这些约束变成可测试合同，同时仍保持本地和可逆。

实施上先交付事件 schema、路径边界和合成测试，再接入一个真实 workflow 调用边界；只有真实 `C` 数据完整后，才考虑 `C+1`。

## 执行范围

- 所有可观测 workflow 均纳入采集，但按 Profile 分别汇总，不混合成单一基线；
- 每个 Profile 使用 10 个满足资格的事项，最长 5 个工作日，至少 8 个可计算完成事项；
- 先完成当前并发 `C` 基线，再由人工依据门槛决定是否执行 `C+1`。

## 未决问题

- 真实基线运行后是否达到最低样本和质量门槛，属于验收阶段的实验判断，不改变本 Change 的实现范围。
