# 方案提案

## 目标

把 Profile 的机器真源直接变成人可读 catalog，并为需求分析 Profile 增加最小结构和轮次合同，同时保持 Runtime 与 Desk 解耦。

## 候选方案

### A：Profile 元数据与内容合同内聚（推荐）

在 Profile 文件中增加用途、适用范围、不适用范围、handoff 和阶段 description/exitCondition；增加 declarative `inputContracts`，由通用 core 检查对象字段、数组和枚举。请求增加 `analysisRounds`，由 Profile 声明并由通用检查器验证。新增 `workflow catalog` 和 `workflow describe`，直接从 registry/profile 生成输出。

优点：单一真源、可生成目录、适合不同 Profile；不把 Desk 策略写进 Runtime。风险：通用合同表达能力有限，需要以后扩展。

### B：每个 Profile 编写独立 TypeScript 校验器

优点：表达能力强。缺点：校验逻辑与 Profile JSON 分裂，新增 Profile 需要代码分支，容易恢复“delivery-change 特判”。不选。

### C：Runtime 读取 Desk 提案并自动路由

优点：使用体验集中。缺点：违反 Workflow System 独立调用边界，引入跨仓扫描、权限和状态同步问题。不选。

## 推荐设计

- 保留现有 3 个 Profile 和阶段顺序。
- catalog/describe 只展示 Profile 文件中的声明，不自动推断适用性。
- 内容合同只验证结构，不判断事实真伪；证据质量和主人是否满意仍由人工决定。
- `analysisRounds` 是调用方累积的审计输入，Runtime 验证每项最小字段并回显；Runtime 不负责持久化文件。
- `disposition` 使用枚举；`candidateProfileId` 只作为建议输出，不自动绑定。
