# 方案提案

## 候选 A：扩展通用 stage 合同并新增 requirement-analysis profile

- 在既有 stage 合同上增加可选 `judgmentOptions`、`repeatOnJudgments` 和 `outputInputs`。
- `repeatOnJudgments` 只允许当前阶段重复；调用方以累积报告和未完成阶段前缀驱动下一轮。
- 新 profile 采用 `capture → clarify → discover → evaluate → decision` 五阶段；三个分析阶段均可在人工判断为 `continue-analysis` 时重复。
- 决策结果通过 `publishedInputs` 输出，不自动创建 Change。

优点：复用现有 Workflow System，保留独立调用和版本固定；能表达 Desk 已裁决的分析循环；对既有 profile 向后兼容。

## 候选 B：为需求分析编写独立脚本

不选。会复制 profile 解析、binding、状态和错误合同，造成第二套 Workflow System。

## 候选 C：让 Runtime 直接读取 Desk

不选。会破坏 Workflow System 独立性，把个人存储和策略耦合进公共 Runtime。

## 首版 Profile

- `capture`：输入原始需求陈述。
- `clarify`：输入问题框架，覆盖真实问题、目标、范围和约束。
- `discover`：输入现有能力核验报告，区分已知、未知、证据状态和置信度。
- `evaluate`：输入候选方案比较，覆盖投入、风险和可逆性。
- `decision`：输入决策报告、处置和可选候选 profile；人工判断为 `build`、`use-existing`、`defer` 或 `reject`。

首版不实现门 C、跨仓路由、自动创建 Change 和 Desk 双向同步。
 
## Trade-off 矩阵

| 维度 | 候选 A：通用 stage 扩展 | 候选 B：独立脚本 | 候选 C：读取 Desk |
|---|---|---|---|
| 复用现有合同 | 高：沿用 profile、binding 和状态机 | 低：需要复制合同 | 低：需要额外耦合协议 |
| 维护成本 | 中：增加可选 stage 字段 | 高：维护第二套执行路径 | 高：维护跨系统集成 |
| 独立执行 | 高：只依赖显式 request | 高：可独立执行 | 低：依赖 Desk 环境 |
| 失败隔离 | 高：复用既有 fail-closed 入口 | 中：需重复实现门禁 | 低：外部存储故障会影响执行 |
| 首版范围风险 | 中：需要扩展 schema、CLI 和测试 | 高：行为容易分叉 | 高：引入跨仓和私人数据边界 |

## 推荐

推荐候选 A：它在复用既有执行合同、保持 Runtime 独立性和控制首版边界之间更合适；实现仅增加可选能力，不改变既有 profile 的阶段和结果。

## 未决问题

1. 后续是否需要为 `candidateProfileId` 增加 registry 存在性校验；首版保留为调用方提供的候选标识。
2. 后续是否需要把分析报告持久化格式纳入 Runtime；首版只返回 `publishedInputs`，由调用方保存。
3. 后续是否需要支持更多分析循环判断；首版固定为 `continue-analysis` 和 `sufficient`。
