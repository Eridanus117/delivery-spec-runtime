# 方案提案

## 决策问题

如何在不让 Workflow System 依赖外部工作台、也不把 `delivery-change` 强行改成总流程的前提下，落地首批四项 V0.1 能力：阶段合同、事项身份、独立调用和结果返回。

## 约束

- Workflow System 必须能够脱离外部工作台独立运行；上层系统只能作为按需调用方。
- 当前 `delivery-change` 是已有的重型交付 profile；本 Change 不把它改造成所有事项的总流程。
- 首轮不实现自动扫描、全局索引、双向同步和多个完整 workflow profile。
- 结果必须可机器读取；失败和阻塞不得伪装成成功。
- 公共仓库内容不得包含个人日记、真实业务、凭据或第三方未授权材料。
- 保留当前 Runtime 的 Windows、gitlink、版本 pin 和 fail-closed 合同。

## 候选 A：在现有 delivery-control 上增量扩展

- 方案：直接在 `delivery-control.ts` 和现有 Change 状态合同中增加通用事项标识、阶段字段、profile 参数和机器结果输出；继续使用现有 `delivery-change` 入口。
- 优点：改动路径短；复用现有锁、JSON 解析、命令分发和测试；不需要新增核心模块。
- 缺点：通用工作流语义会与 delivery-change 生命周期耦合；未来轻量 profile 仍会被重型 Change 结构牵引；容易把现有工具继续误认为总流程。
- 成本：低到中；主要是现有工具、合同和测试的增量修改。
- 风险：中到高；接口表面简单，但会扩大当前 `delivery-change` 的隐含职责，后续拆分成本高。
- 可逆性：中；可以回滚新增字段，但已经进入调用方的参数和状态会形成兼容负担。

## 候选 B：增加独立 workflow core，保留 delivery-change 为 profile

- 方案：增加与 `delivery-control.ts` 平行的最小 workflow core/entrypoint，定义事项身份、阶段合同和机器结果合同；`delivery-change` 暂时保持原样，后续作为一个 profile 适配到 core。
- 优点：保留现有交付流程稳定性；下层工作流不依赖外部工作台；阶段合同和结果合同可以被轻量 profile 复用；边界清晰。
- 缺点：短期存在两个入口；需要明确 core 与 delivery-control 的边界；首轮要增加少量新的合同和测试。
- 成本：中；需要新入口、JSON 合同、最小执行状态和聚焦测试。
- 风险：中；主要风险是过早抽象 core，或两个入口职责重叠。
- 可逆性：高；core 可以在未接入现有 profile 前独立试运行，失败时不影响 delivery-change。

## 候选 C：先创建独立 Workflow System 仓，再迁移 Runtime

- 方案：创建私有 `Workflow System` 仓，先在那里定义完整工作流模型和 V0.1 合同；当前 `delivery-spec-runtime` 只保留旧 Runtime 或作为迁移源。
- 优点：仓库身份从一开始清晰；个人工作流上下文可以放在私有中心仓；不会在当前仓中同时承载旧公共定位和新模型。
- 缺点：需要迁移历史、submodule、文档、Windows 修复和现有合同；在模型尚未稳定前增加仓库迁移成本；短期维护两个实现来源。
- 成本：高；包括新仓、访问权限、迁移、接入和回归验证。
- 风险：高；迁移过程可能掩盖真正的 workflow contract 缺口，并产生两个 Runtime 来源。
- 可逆性：低到中；迁移后再回退会重新处理 gitlink 和消费者。

## Trade-off 矩阵

| 维度 | 候选 A | 候选 B | 候选 C |
|---|---|---|---|
| 首轮投入 | 低 | 中 | 高 |
| delivery-change 隔离 | 弱 | 强 | 强 |
| 独立运行能力 | 中 | 强 | 强 |
| 对未来 profile 的支持 | 弱 | 强 | 强 |
| 当前稳定性 | 中 | 强 | 中 |
| 迁移风险 | 低 | 低 | 高 |
| 可逆性 | 中 | 高 | 低到中 |

## 推荐

推荐候选 B，但只实现最小 core，不提前设计完整平台：先建立独立的阶段/事项/结果合同和一个可直接调用的入口，保持 `delivery-change` 不变。这样能够验证四项首批需求，同时避免继续向现有重型交付工具堆叠总流程语义；Workflow System 仓库迁移和私有化作为独立决策处理。

## 未决问题

- core 的具体命令名和 JSON 合同字段需要在 `改造方案` 中定稿。
- 首轮是否只支持一个示例 profile，还是先只支持无持久化的合同探针，需要根据实现成本决定。
- 当前仓直接转为 Workflow System，还是新建私有仓迁移，不能在本 Change 中静默决定。
