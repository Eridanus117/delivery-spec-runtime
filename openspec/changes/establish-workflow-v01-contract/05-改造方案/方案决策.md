## 选择依据

- 保持 `delivery-change` 的现有项目交付边界，不把它扩展为所有事项的总流程。
- 将阶段合同、事项身份、独立调用和结果返回放进独立 core，满足首轮四项已确认需求。
- 保持 Workflow System 不依赖外部工作台；上层按需调用仍属于调用方责任。
- 采用可逆的垂直切片：core 可以先独立验证，未接入其他 profile 前不影响现有 `delivery-change`。
- 避免候选 A 对现有 `delivery-control.ts` 继续增加通用语义，也避免候选 C 在模型未稳定前引入仓库迁移负担。

## 接受的后果

- 短期存在独立 workflow core 与现有 `delivery-control.ts` 两个入口，需要清楚划分职责。
- 需要新增最小的机器可读调用和结果合同，以及对应合同测试。
- `delivery-change` 不会立即获得多 profile 路由能力；上层系统也不会由本 Change 实现。
- 当前仓库仍需后续单独决策是否私有化并迁移为 `Workflow System`；本决策不自动改变仓库可见性或消费方式。

## 拒绝方案

- 候选 A：不选择，因为会把通用工作流语义耦合进 `delivery-control.ts` 和重型 `delivery-change` 生命周期，增加后续拆分成本。
- 候选 C：不选择，因为仓库迁移、私有化、submodule 和访问权限不属于首轮合同切片，当前会放大变更范围和迁移风险。

## 重新决策触发条件

- 独立 core 与 `delivery-change` 的职责无法通过实际调用清晰分离。
- 首轮合同验证证明独立入口不能覆盖阶段状态、事项追踪或结果返回。
- 出现必须共享统一状态存储、统一发布节奏或统一兼容合同的事实。
- 仓库私有化或迁移方案改变了本 Change 的代码边界。
- 新增 profile 的真实需求证明当前 core 抽象不足，或候选 A/C 的成本与风险判断发生变化。
