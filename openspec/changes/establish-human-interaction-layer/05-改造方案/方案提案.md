# 方案提案

## 决策问题

如何把已确认的人机交互合同（一句话发起、三动词、门口一屏摆盘、单事项在线、在途提醒）作为 Runtime 资产交付给 Claude Code 载体，同时不改变既有机器合同、不增加人的记忆负担。

## 约束

- 人侧零命令记忆：交互资产必须由 agent 按话题自动发现，不引入要人输入的命令名。
- 追加式交付：不修改既有 workflow profile、delivery 生命周期、intake 合同与九条 opsx 命令语义；既有渲染检查与合同测试保持通过。
- 随版本锁分发：资产必须进 Runtime 仓并经消费仓 gitlink 锁定，不靠各仓手工复制。
- 公共仓边界：资产只含通用交互合同，不含维护者个人流程内容（desk 语境）。
- 流水线形状不在本 Change 内改动（3 事项复盘检查点已另行记录于 INT-007）。

## 候选 A：静态 skill 资产 + 第四条受管软链

- 方案：在 Runtime 仓新增 `.claude/skills/<name>/SKILL.md` 静态源文件，正文承载交互合同并指引 agent 驱动 `runtime-entry.ts` 底层 CLI；`runtime-manifest.json` links 增加一条指向该目录的受管软链，`runtime-link.ts`/`runtime-check` 合同同步扩展，并对既有消费仓保持向后兼容（缺第四链时按明确策略提示而非静默）。
- 优点：改动面最小；skill 是 Claude Code 原生发现机制，满足零记忆约束；纯追加、不触碰渲染管线。
- 缺点：skill 源文件在渲染检查体系之外，内容完整性需要单独的合同校验；links 合同从三条变四条涉及消费仓兼容设计。
- 成本：低到中——一份 skill 文档、link 合同扩展、内容完整性校验、聚焦测试与文档更新。
- 风险：低到中；主要风险点是 links 合同变更的消费仓兼容语义。
- 可逆性：高；删除软链与资产即可回退，不影响任何既有合同。

## 候选 B：渲染管线扩展为多目标

- 方案：扩展 `.omp/command-sources` 的 manifest 合同支持多渲染目标，同一源渲染出 OMP 命令与 Claude Code skill 两种产物，`render-commands.ts check` 统一覆盖。
- 优点：单一真源、渲染检查天然覆盖内容完整性；未来资产增多时扩展性最好。
- 缺点：manifest 合同与渲染器改动面大；skill 与 opsx 命令的正文结构并不同源（一份是九段命令说明书、一份是交互合同），强行同源反而造作；首个 skill 就上多目标架构属于过早抽象。
- 成本：中；风险：中（合同变更面大、测试面大）；可逆性：中到高。

## 候选 C：不动 Runtime，指引写入消费仓文档或用户全局配置

- 方案：Runtime 不新增资产，把交互指引写进各消费仓的接入文档或维护者的用户级 CLAUDE.md。
- 优点：零 Runtime 变更、当天可用。
- 缺点：不随版本锁分发，各仓复制必然漂移；资产不在仓内，agent 在新环境无从发现；不满足 spec「随 Runtime 分发」的需求，等于放弃把交互合同当作公共资产治理。
- 成本：最低；风险：中（漂移与不可发现）；可逆性：高。

## Trade-off 矩阵

| 维度 | 候选 A | 候选 B | 候选 C |
|---|---|---|---|
| 首轮投入 | 低到中 | 中 | 最低 |
| 人侧零记忆 | 满足 | 满足 | 部分（依赖各仓自觉） |
| 随版本锁分发 | 满足 | 满足 | 不满足 |
| 内容完整性校验 | 需单独校验 | 渲染检查天然覆盖 | 无 |
| 合同变更面 | links 三→四 | manifest+渲染器 | 无 |
| 过早抽象风险 | 低 | 中到高 | 无 |
| 可逆性 | 高 | 中到高 | 高 |

## 推荐

推荐候选 A：静态 skill 资产加第四条受管软链，内容完整性用一个聚焦校验（检查 skill 正文含五项合同要素）补足，不上渲染架构。理由：满足全部硬约束（零记忆、追加式、随版本锁分发）且改动面最小；候选 B 的单一真源收益在只有一份 skill 时不成立，等 Claude Code 资产增多再作为独立 Change 重构；候选 C 不满足「随版本分发」需求，仅可作为过渡措施。

## 未决问题

- skill 的命名与触发描述措辞（影响 agent 发现率）——`改造方案` 定稿。
- 在途提醒的落点：首版拟仅写入 skill 指引（会话内约定），不加机器机制；是否足够待 3 事项复盘检查点评估。
