## 原文冲突与缺口

- **两份互不引用的交付 7 站定义（RAW-001 结构事实 1）**：`openspec/profiles/delivery-change-v1.json` 无 `inputContracts` 字段，跑 `workflow run` 只做 request JSON 键存在性检查、全程不碰 Change 目录；真门禁在 `delivery-control.ts guard` 与 `delivery-lifecycle.ts`，代码中没有任何一处把 `stage.id === "review"` 关联到 `lifecycle review write`。维护者裁定本 Change 必须裁定权威归属，但**未指定取哪一份为权威**——该裁决进入方案层。
- **AGENTS.md 校准条款自述与本次结论冲突**：现行末条写「维护者的不耐烦反馈即为『该站取消人工审阅』的裁剪信号」，把维护者反馈单向解读为「减」。信号6 证明该解读不成立（维护者当场要求「说明」，即要求「增」）。条款措辞须随本 Change 改写，不在本层裁决改写后的确切文字。
- **信号4 与信号6 的表面冲突**：信号4 记「零追问，可解读为还可再压缩」，信号6 直接证伪该推断。二者不是矛盾而是分层——例行门的一屏够用，重裁决必须展开。原文两条一并保留，不做归一化删改。
- **缺口：`change-mode.json` 与 `.delivery-update-snapshot.json` 的全历史写盘实况未终局核实**。RAW-001 记「三单零写盘」「全仓无任何实例」，但维护者裁定要求的是「若确证全历史无写盘」——「三单窗口」与「全历史」不是同一判据，核实动作留到实施层，核实结果决定处置分支。
- **缺口：`change-sources.json` 与 `01-原始需求索引.md` 的信息覆盖关系未逐单验证**。RAW-001 判为「信息完全重复」，但维护者裁定要求「移除前确认索引行覆盖同等信息」——本 Change 自身即为一个反例样本：本文件的材料索引有 6 行 RAW，而 `intake promote` 只会追加被 promote 的条目的来源行，覆盖度并非天然相等。该核实是移除的前置条件。
