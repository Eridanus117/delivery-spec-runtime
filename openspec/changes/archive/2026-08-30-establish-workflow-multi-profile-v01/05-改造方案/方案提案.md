# 方案提案

## 决策问题

在已确认“单个 Workflow System / Spec 仓支持多套 workflow profile、每个 Change 绑定固定 profile”的总体架构下，如何在当前公共 `delivery-spec-runtime` 中增量落地，既提供多 profile 合同和选择能力，又不破坏现有 `delivery-change` 入口、gitlink、软链和 fail-closed 约束？

## 约束

- 总体架构已由维护者确认：一个仓承载通用 core 和多个 profile，Change 绑定 `profileId` 与 `profileVersion`。
- `delivery-change` 必须保留现有命令、artifact、锁、版本 pin、消费方式和失败语义。
- Runtime 不得读取或写入未授权的外部资产，不得扫描全局目录；调用方必须显式提供 profile 选择和 Change 上下文。
- 当前 `runtime-manifest.json` 只声明三个相对软链；本 Change 不增加第二套 manifest 或 lock/hash pin。
- 当前仓是公共 Runtime；不得保存私人业务、真实项目材料、凭据或私有迁移资产。
- V0.1 需要证明至少两个 profile 可以被稳定识别和选择，但不一次性实现多个完整业务流程。
- 现有 `runtime-entry.ts`、`delivery-control.ts` 和 `delivery-lifecycle.ts` 是稳定边界；新能力失败时旧入口仍必须可运行。

## 候选 A：在同一 Runtime 内增量增加 profile 层（推荐）

- 方案：新增通用 profile contract、profile registry/loader、Change profile binding 和 workflow dispatch；通过现有 Runtime 入口增加明确的 workflow 命令分支。现有 `delivery-change` 路径先保持原样，并以 adapter 形式逐步接入；测试使用两个合成 profile 验证选择和隔离。
- 优点：符合已确认的单仓多 profile 架构；旧 delivery 路径可先不动；可以先锁定合同，再逐个接入真实 profile；回滚边界清晰。
- 缺点：短期存在旧 delivery 路径和新 workflow 路径；需要 profile 版本 pin、定义冲突检查和 adapter 边界。
- 成本：中等；新增合同、解析器、入口分支、测试和文档，避免重写现有生命周期。
- 风险：core 与 profile 责任逐渐混杂；profile registry 可能过早变成平台；旧入口和新入口行为不一致。
- 可逆性：高；删除新 profile 层即可恢复旧 delivery 路径，旧 Change 状态不需要迁移。

## 候选 B：直接重构现有 Runtime 入口为 profile dispatcher

- 方案：改造 `runtime-entry.ts`、`delivery-control.ts` 和 manifest，使所有命令先解析 profile，再由 profile dispatcher 处理 `delivery-change` 和后续 profile。
- 优点：最终入口统一；调用方只需记住一个 dispatcher；长期可减少两个入口的表面差异。
- 缺点：首轮同时改动最稳定的入口、manifest、版本检查和 delivery lifecycle；旧 profile 与新 core 的边界会在一次大改中确定。
- 成本：中到高；需要迁移现有命令、回归所有 consumer fixture 和重新处理旧状态合同。
- 风险：现有 `delivery-change` 回归、submodule/manifest 漂移或 fail-closed 语义被意外放宽；错误难以隔离。
- 可逆性：低到中；重构后的调用方可能依赖新的统一入口，回滚需要恢复多个合同。

## 候选 C：先拆出独立 Workflow System 仓，再接入当前 Runtime

- 方案：先建立独立或私有 Workflow System 仓，在其中实现 core、profile 和 Change selection，再迁移当前 Runtime。
- 优点：仓库身份和最终边界一开始清楚；不需要在公共 Runtime 中暂时承载新旧两套语义。
- 缺点：引入仓库迁移、权限、submodule、版本和历史搬迁；模型尚未经过真实 profile 使用前就承担迁移成本。
- 成本：高；包括新仓、接入、迁移、消费仓回归和权限治理。
- 风险：迁移工作掩盖合同缺口，形成两个 Runtime 来源；超出当前 Change 的公共 Runtime 范围。
- 可逆性：低；迁移后回到当前仓需要再次处理 gitlink、软链和消费者。

## Trade-off 矩阵

| 维度 | 候选 A：增量 profile 层 | 候选 B：直接重构入口 | 候选 C：先拆新仓 |
|---|---|---|---|
| 与已确认单仓多 profile 架构一致性 | 强 | 强 | 弱（属于后续迁移） |
| 现有 delivery-change 回归风险 | 低 | 高 | 中 |
| 首轮投入 | 中 | 中到高 | 高 |
| profile 边界可验证性 | 强 | 中 | 中 |
| 旧入口可回滚性 | 高 | 低到中 | 低 |
| 独立调用边界 | 强 | 强 | 取决于新仓设计 |
| 版本与发布复杂度 | 中 | 中到高 | 高 |
| 是否适合本 Change | 是 | 谨慎 | 否 |

## 推荐

推荐候选 A：在当前 Runtime 内以增量方式增加 profile 层，同时保留旧 `delivery-change` 路径。

推荐原因：它实现的是已确认的目标架构，而不是继续把 `delivery-change` 扩大成总流程；它把高风险的入口重构和仓库迁移延后到有真实 profile 证据之后；任何新能力失败都可以停在新入口，不影响现有消费仓。

V0.1 的最小落地边界：

- 定义 profile、Change binding、版本 pin、执行结果和失败语义合同；
- 提供显式 profile registry/loader 和 profile selection，不根据外部目录、事项标题或未声明上下文猜测；
- 用两个公共合成 profile 验证同仓识别、Change 绑定、版本固定和结果隔离；
- 为现有 `delivery-change` 提供兼容识别，不重写其既有 lifecycle；
- 保留现有 `runtime-manifest.json` 的三个软链和旧入口；
- 不实现全局路由、全局扫描、跨仓同步、持久化平台或私有仓迁移。

## 未决问题

- profile 合同是否同时拥有 artifact/schema、命令和门禁，还是通过 adapter 引用现有 delivery contracts；本 Change 先要求边界可声明和可校验，不重构全部旧 artifact。
- Change 的 profile binding 保存在哪个 Change 资产中，需与现有 Change metadata 合同协调；不能依赖目录命名或隐式默认值。
- profile 状态是由 Change 根保存、由调用方显式传入，还是由 Runtime 维护，需在改造计划中选定一个 V0.1 方案；首轮不建设跨仓数据库。
- 当前公共 Runtime 是否最终迁移为私有 Workflow System，独立于本 Change 另行决策。
