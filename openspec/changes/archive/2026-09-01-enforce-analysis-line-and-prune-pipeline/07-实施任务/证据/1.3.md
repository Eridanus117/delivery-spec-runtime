# 任务 1.3 验证证据

## 交付物

新建 `test/station-authority.test.ts`：

- `prepare(repo)`：7 站共用的最小 Change fixture 工厂。在临时 git 仓内建出能一路走到 archive 的完整 Change——9 份工件齐备并全部批准、实现已提交、`08-验收/验收记录.md` 与 cleanup 证据为 PASS、`09-发布/发布计划.md` 存在、delta 与长期 spec 已同步。每个探针独占一个 `mkdtempSync` 临时仓，用例结束即 `rmSync`，不在仓内留残留。
- `probes`：7 个逐站探针。每个探针先抹掉**该站的维护者表态字段**，再运行**该站的真实收口命令**，返回该进程的退出码。

| 站位 | 抹掉的维护者表态字段 | 真实收口命令 |
|---|---|---|
| proposal | 无（提案结构由 agent 产出，门禁不读人工裁决） | `delivery-control guard --operation apply` |
| decision | `方案决策.md` 的 `- 状态：APPROVED` 与 `- 决策人：`（抹后重新批准以刷新 digest） | `delivery-control guard --operation apply` |
| implementation | 无 | `delivery-control guard --operation verify` |
| review | 无（`result` 由 findings 计算，review-input 无裁决键） | `delivery-lifecycle review write` |
| acceptance | `acceptance-input` 的 `acceptedBy` | `delivery-lifecycle acceptance write` |
| sync | 无（specSync 全是摘要比对） | `delivery-control guard --operation sync` |
| archive | `readiness-input` 的 `attestedBy` | `delivery-lifecycle readiness write` |

decision 探针刻意在抹掉表态后**重新执行 approval set**，使失败原因只可能来自内容侧的「缺表态」，而不是「批准 digest 过期」——否则探针会把批准机制的噪音误读成站位属性。

## 验证

`node --experimental-strip-types --test test/station-authority.test.ts` → 2 passed / 0 failed。

### VC-001（逐站探针结论与 profile humanJudgment 全等）

观测结果（全部来自真门禁进程退出码）：

```
proposal=false decision=true implementation=false review=false acceptance=true sync=false archive=false
```

与 `delivery-change-v1.json` 的 `humanJudgment` 逐站 `deepEqual` 通过，`mismatchedStations` 返回空数组。同时断言探针站位数等于 profile 站位数，防止漏站导致的假绿。

非空洞性佐证：`decision` 与 `acceptance` 两个探针确实返回非零（否则 deepEqual 无法与 profile 的两个 `true` 相等），说明「拒绝⇒人工站」这条分支真的被走到过，不是全 false 撞上全 false。

### VC-003（禁止两侧互抄）

对本文件源码做结构检查，检查范围限定在「取值区」（文件头到 `mismatchedStations` 之前，即观测值的全部产生路径）：

- 逐个站位名断言取值区内不存在 `<station>: true|false` 形式的硬编码映射。
- 取值区内不存在 `humanJudgment = true|false` 赋值。
- `probes` 定义段内不出现 `profile` 标识符——探针不得从被比对方反读期望值。
- 断言判定语句确为 `observed[station] = probe(prepare(repo)) !== 0`，即唯一取值来源是退出码。
- 断言 probe 条目数等于站位数，且每个条目都真的调用了 `runTool(` 或 `writeReview/writeAcceptance/writeReadiness`，不得凭空返回常量。

VC-002 段落里刻意构造的「humanJudgment 被单边改动的 profile」是负向对照输入，不属于取值来源，故显式排除在取值区之外并在注释中写明理由。
