## 选择依据

### 对路线维度的选择

1. **权威判据与本 Change 的立论同构**（对应方案提案「推荐」第 1 条）。本次复盘的总结论是「要求必须活在门禁里，而非活在文字里」。把交付 7 站的权威判给「能拒绝你的那段代码」，而不是「描述你应该怎么做的那份 JSON」，是同一条原则在架构层的应用。候选 B 方向相反：先把权威判给声明，再赌一次重写能把描述变成约束。
2. **不触碰约束 2 的保护区**（对应方案提案「约束」第 2 条、RAW-001 裁定 A5）。`implementation-review` 的自算 `reviewedPaths` / `result` 与 `acceptance-state` 的四 digest 新鲜度是本轮明令不得削弱的两处强校验，而它们正落在 `guard` 引擎的调用路径上。候选 B 要求重写该引擎，风险最高的一段恰好是最不该动的一段。
3. **不制造第二笔推迟**（对应方案提案「推荐」第 3 条）。本次要清理的两个早期目录（`establish-intake-inventory`、`establish-workflow-v01-contract`）都是「先做一片、剩下的下次再说」的产物。在一次以清理推迟性技术债为主题的变更里再拆一片（候选 C），与主题自相矛盾，且候选 C 会留下「A6 权威已定、A3 两侧仍不一致」的窗口。
4. **结构债一次根除**。候选 A 附带的一致性合同测试逐站锁定 profile 的 `humanJudgment` 标记与真门禁的人工表态索取行为；两侧任一单边修改即非零拒绝，结构债不会以第二种形态复发。这条是候选 A 与「把 profile 直接删掉」之间的关键差别：profile 不被废弃，而是降级为人读元数据并被机器钉住。

## 接受的后果

1. **放弃声明式流程定义的长期价值**。`delivery-change-v1.json` 从「定义」降为「人读元数据」（用途、阶段说明、退出条件、交接动作）；`workflow run` 对 `delivery-change` 仍只做 request 键存在性检查，不会获得对交付流程的实际约束力。未来新增交付档位仍需改代码而非改 JSON。这一后果被明确接受，不作为遗留问题登记；若日后确需声明式定义，路径是把它作为强制版分析线的第二单试验品（第一单已定为指标方向），用分析结论决定是否值得做候选 B 的重写。
2. **单片改动面大，一次评审覆盖 20+ 任务**。`implementation-review` 的 `reviewedPaths` 由代码自算、不接受手工缩小，是该风险的机器缓解；但人工侧的评审负担确实一次性发生，不再摊薄。
3. **中途受阻会整片阻塞**。若某项裁决在实施中被证明不可行，本 Change 需回到方案层重开，而不是让其余部分先行归档。
4. **schema v6 带来新旧并存**。归档的 10 个 Change 与本 Change 自身持有 v5 结构（两份现状文档、`change-sources.json`），新建 Change 用 v6 结构（一份现状文档、无 `change-sources.json`）。仓内长期存在两种 Change 目录形状，读者需要知道分界线是「2026-08-31 之后创建」。
5. **`change-mode.json` / `.delivery-update-snapshot.json` 概念消失，`/opsx-update` 的 snapshot 与 diagnose 两个命令一并移除**。rehearsal 演练模式随 `change-mode.json` 一并退场，本仓此后只有 delivery 一种模式；若将来需要演练模式，须重新立法而非恢复旧文件。两类资产全历史零实例，无数据迁移负担。
6. **立项门变严，可能误挡**。`intake promote` 此后 fail-closed 检查分析线产物，路由表未命中的事项一律按最重档处理。上线后第一次误挡的处置方式是**调路由表，不是关门**——这一点是接受该后果的前提。
7. **`AGENTS.md` 校准期不终止**。条款被改写为「摆盘深度与决策分量匹配」三档规则并附新的复盘触发点，信号台账 `INT-20260831-014` 保持开放继续追加。即维护者继续承担「被观察」的成本。
8. **两个早期目录归档后不可撤回地失去 active 身份**。`establish-workflow-v01-contract` 以 superseded 归档且不补验收，其 task-state 中长期 `planned` 的条目将永久保持未完成状态作为历史记录；`establish-intake-inventory` 的 4 条需求并入 `intake-workflow` capability 后，delta 目录名与能力名不一致（本仓已有先例）。

## 拒绝方案

### 候选 B（单片交付，权威归 `delivery-change-v1.json`）

- **不选原因**：它要求把 `guard` 的六个 operation、`validateDecisionArtifacts` 的内容正则、`requireApproved` 的工件清单全部重写为 profile 驱动，直接触碰约束 2 明令保护的两处强校验的调用路径。为一个尚无需求驱动的架构收益（本仓目前只有一个真在跑的交付档位），拿治理链本身做赌注，成本与风险都不成比例（估计多出 8–12 个任务，外加一整组「新旧行为逐项等价」的回归断言）。
- **保留的入口**：若日后确有多档位需求，按「接受的后果」第 1 条的路径重新评估，不在本 Change 内做。

### 候选 C（两片交付，权威归真门禁代码）

- **不选原因**：第一片只裁定权威而不动 profile、第二片才摘 `humanJudgment`，两片之间存在「权威已定但两侧仍不一致」的窗口，与 RAW-001 裁定 A6「不允许把这条结构债留到下一轮」直接冲突。且第二片存在被无限期推迟的现实风险——本仓的两个早期未归档目录就是这种推迟的产物，而它们正是本次要清理的对象。此外 spec delta 需拆成两份，`intake-workflow` 与 `delivery-lifecycle-governance` 的修改跨两个 Change，sync 复杂度上升。

### 未决问题 1 的补法 (b)「判定排序信息无消费者、随文件一并丢弃」

- **不选原因**：与裁定 B2 的字面要求「移除前必须逐单确认索引行覆盖同等信息；若某类信息只在 `change-sources.json` 里有，先并入索引再移除」直接冲突。省下的是一次文档语义定义，赌上的是裁定的可信度。

### 未决问题 2 的「引入 `disposed` 值 + 另一字段记出口」

- **不选原因**：把一个四元枚举拆成「二元状态 + 三元出口」两个字段，读者要读两个字段才知道条目去向，且需要迁移 19 条存量。语义没有变清楚，成本却实打实。

### 未决问题 3 的「按预估工作量分类」

- **不选原因**：工作量只能由 agent 自估，而 agent 自估正是分析线三单零执行的直接机制（信号7：对齐失败）。把新门禁的判据建在同一个不可信输入上，等于给强制门留一个自助豁免开关。

## 重新决策触发条件

1. **一致性合同测试无法真正从行为侧取值**。若实施中发现「真门禁是否索取人工表态」无法从代码行为侧稳定判定，只能靠在两侧各写一份清单再比对（即「两侧互抄」），则 A6 的权威裁定失去机器保障，须回到方案层重选（候选 B 重新进入视野）。
2. **立项门在真跑中被证明不可实现为 fail-closed**。若 `intake promote` 无法在不引入第二套状态的前提下定位分析线产物（`workflow-binding.json` 与分析结果按 intake `id` 可寻址），则 A1 的落地方式需重新设计。
3. **合并 03/04 会丢失门禁**。若无法让合并后的单一现状 artifact 承接原两份各自参与的全部 digest 与批准校验，则 B4 退回「保留两份」，并在本文件追加修订记录。
4. **强制版分析线跑满 2 单后的复盘结论**。按未决问题 4 的裁定，届时复盘 A1 的留/修/杀；若结论是「杀」或「改形状」，本决策中与 A1 相关的部分（立项门、路由表、workflow 全族保留）需整体重开。
5. **出现第二个真实交付档位**。若本仓或消费仓出现第二个需要独立站位定义的交付档位，「权威归代码」的成本结构改变，候选 B 的声明式路线须重新评估。
6. **约束 2 的两处强校验在实施中被迫削弱**。任何为了完成本 Change 而放宽 `implementation-review` 自算或 `acceptance-state` 四 digest 的提议，都必须先回到本文件重开决策，不得在实施层自行处置。
