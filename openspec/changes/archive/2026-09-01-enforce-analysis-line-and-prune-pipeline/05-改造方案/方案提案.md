# 方案提案

## 决策问题

八条处置包的**内容**已由维护者在 2026-08-31 复盘中裁定完毕，本提案不重开那些裁决。本次需要维护者选择的是**实现路线**，具体两个维度：

1. **交付切片**：把「立强制门」与「修剪流水线」放在同一个 Change 一次落地，还是拆成先后两片？
2. **A6 权威归属**（维护者已裁定「必须裁定」但未指定取哪一份）：交付 7 站的权威定义是取 `openspec/profiles/delivery-change-v1.json`（声明式 profile），还是取 `delivery-control.ts guard` + `delivery-lifecycle.ts`（真门禁代码）？

三个候选是这两个维度的三种一致组合。除此之外，`change-mode.json` 与 `.delivery-update-snapshot.json` 的核实结果已在本提案给出（见「约束」第 6 条），不再作为选项。

## 约束

1. **不得偏离八条处置包**。裁决内容是输入，不是候选。
2. **不得削弱两处强校验**：`implementation-review` 的自算 `reviewedPaths` / `result`（不接受手工缩小），`acceptance-state` 的四 digest 新鲜度。任何修剪动作波及这两处即判失败。
3. **不得抢跑**。本 Change 自身的工件按现行模板产出（本 Change 已写 `change-sources.json`、已产出两份现状文档），新模板只对本 Change 之后创建的 Change 生效。
4. **存量不得被判失效**。`openspec/changes/archive/` 下 10 个已归档 Change 与 3 个未归档早期目录今天全部通过 `openspec validate --all --strict`（11/11）与 `node --test`，改造后必须仍然通过（或按 C2 / C4 正常归档）。
5. **fail-closed 优先于便利**。本次改造的立论就是「要求必须活在门禁里」；任何为了少改代码而把新规则只写进文档的做法，与本 Change 的目的直接冲突。
6. **两项核实已完成，结论确定**（`git log --all --diff-filter=A --name-only` 全历史检索，2026-08-31）：`change-mode.json` 与 `.delivery-update-snapshot.json` **全历史零实例**。故按裁定 B3：`change-mode.json` 默认值 `delivery` 显式化并移除该文件概念；`.delivery-update-snapshot.json` 同样移除，`update snapshot` / `update diagnose` 两个命令一并移除。
7. **B2 的前置条件尚未满足**（新发现，见「未决问题」1）：`change-sources.json` 的 `authority` 是一个必须从 1 连续递增的**全序排名**，而 `01-原始需求索引.md` 的 `- Intake 来源：` 行不携带该排序。移除前必须先让索引承载等价信息。
8. 单人单仓、Windows 主环境、Node `--experimental-strip-types`、`node:test`，不新增 shell runner。

## 候选 A：单片交付，权威归真门禁代码

- 方案：一个 Change 内落全八条。A6 裁定 `delivery-control.ts guard` + `delivery-lifecycle.ts` 为交付 7 站的**唯一权威**；`delivery-change-v1.json` 降级为人读元数据（用途、阶段说明、退出条件、交接动作），其 `humanJudgment` 标记不再是独立事实，而是由新增合同测试对照真门禁**逐站校验一致**——profile 标某站为人工判断，真门禁必须确实索取人工表态；反之亦然。archive 的 `humanJudgment` 因此自然摘除（真门禁本就不索取第二次表态）。A1 的立项门写在 `intake-control.ts promote` 中，读取路由表 JSON 与分析线产物。
- 优点：与代码现状一致，改动量最小且集中；「真源是能拒绝你的那段代码」这一判据与本 Change 的立论（要求活在门禁里）同构；一致性合同测试把两侧永久锁死，不会再产生第二次结构债。
- 缺点：profile 从「定义」降为「说明」，`workflow run` 对 `delivery-change` 依然只是键存在性检查，声明式流程定义的长期价值被放弃；未来若要新增交付档位，仍需改代码而非改 JSON。
- 成本：中。工具 6 个文件、schema 与 4 份模板、2 份合同、2 个 profile、2 份命令源、4 份 docs、`AGENTS.md`、`SKILL.md`、`public-allowlist.json`、9 个测试文件，加两个早期目录归档。估计单次实施 20-26 个任务。
- 风险：单片改动面大，review 一次要覆盖全部；若中途发现某项裁决实施不可行，整片阻塞。
- 可逆性：高。全部改动在一个功能分支内，未合并前 `git reset` 即可；已移除的资产全历史零实例，无数据需要恢复；`change-sources.json` 的移除有 10 份归档副本作为历史留存。

## 候选 B：单片交付，权威归 profile JSON

- 方案：一个 Change 内落全八条。A6 裁定 `delivery-change-v1.json` 为权威：给它补 `inputContracts` 字段，把每站所需的 Change 目录工件、内容校验规则与人工判断标记声明化；`delivery-control.ts guard` 改为从 profile 派生站位集合与门禁清单，代码只保留执行引擎。其余七条与候选 A 相同。
- 优点：交付流程变成真正的声明式定义，新增档位（INT-002 的路由表要用到 `light-change`）只需加 profile 而不必改代码；`workflow run` 从此对 `delivery-change` 有实际约束力，两套机制真正合流。
- 缺点：改动面显著大于候选 A——`guard` 的六个 operation、`validateDecisionArtifacts` 的内容正则、`requireApproved` 的工件清单都要重写为 profile 驱动；重写门禁代码直接触碰约束 2 保护的两处强校验的调用路径，风险最高的一段恰好是最不该动的一段。
- 成本：高。在候选 A 基础上再加一次门禁引擎重写，估计多出 8-12 个任务，且需要为「profile 驱动的门禁与旧行为逐项等价」补一整组回归断言。
- 风险：高。本 Change 的主要目的是立强制门与修剪，重写门禁引擎会让主目的被一次架构改造淹没；一旦回归不完全，代价是治理链本身失效。
- 可逆性：中。门禁引擎重写后回退需要整体还原，且已按新格式产出的 Change 需要迁移。

## 候选 C：两片交付，权威归真门禁代码

- 方案：A6 权威归属与候选 A 相同，但拆成两个 Change 先后交付。第一片（本 Change）只做「让规则长出牙齿」：A1 立项门 fail-closed、INT-002 路由表、分析线产物按 `id` 可定位、A6 权威裁定与一致性合同测试、C1 摆盘三档条款（`AGENTS.md` + `SKILL.md`）。第二片（另立 Change）做修剪：A2 并站、A3 摘 ◆、B1/B2/B3 移除资产、B4 现状合并、B5 模板删节、B8 evidence 校验、C2/C4 早期目录归档。
- 优点：第一片小而聚焦，评审负担低；第二片的修剪可以在强制门真跑过一两单之后再做，届时对「哪些资产真被消费」的判断有新数据；符合「先强制、后评判」的字面顺序。
- 缺点：与维护者裁定的 A6 落地要求冲突——A3（archive 摘 ◆）落在 profile 侧，若第一片只裁定权威而不动 profile，第二片才摘 ◆，则两片之间存在一个「权威已定但两侧仍不一致」的窗口；三个早期目录的处置被推迟，悬挂引用与占位继续存在；本 Change 的 spec delta 需要拆成两份，`intake-workflow` 与 `delivery-lifecycle-governance` 的修改会跨两个 Change，spec sync 复杂度上升。
- 成本：中偏高。两次完整交付闭环（各一轮 review / acceptance / sync / archive）的流程开销大于一次单片，实施总量不变但门禁开销翻倍。
- 风险：中。第二片存在被无限期推迟的现实风险——本仓已有三个早期目录就是「推迟到下一次」的产物，这正是本次复盘要清理的东西。
- 可逆性：高，与候选 A 同。

## 推荐

推荐**候选 A**。三条理由：

1. **权威判据与本 Change 的立论同构**。本次复盘的总结论是「要求必须活在门禁里，而非活在文字里」。把权威判给「能拒绝你的那段代码」而不是「描述你应该怎么做的那份 JSON」，是同一条原则在架构层的应用。候选 B 恰好反向——它把权威判给声明，再要求代码去实现声明，等于赌一次重写能把描述变成约束。
2. **候选 B 的风险落在最不该动的地方**。约束 2 明确保护 `implementation-review` 自算与 `acceptance-state` 四 digest 两处强校验，而它们正是 `guard` 引擎的调用路径。为了获得声明式流程定义而重写这段代码，是用治理链本身去赌一个尚无需求驱动的架构收益（本仓目前只有一个真在跑的交付档位）。
3. **候选 C 的第二片有现成的失败先例**。本次要清理的三个早期目录，全都是「先做一片、剩下的下次再说」的产物。在一次以「清理推迟性技术债」为主题的变更里，再制造一笔推迟，说不过去。

若维护者认为声明式流程定义值得追求，建议路径是：本 Change 先按候选 A 落地并让强制版分析线跑起来，把「profile 声明化」作为分析线的第二单试验品（第一单已定为指标方向），用分析结论决定是否值得做候选 B 的重写。

以下四段是候选 A 被选中后的落地要点，供门口一并审阅；正式内容在方案决策批准后进入 `05-改造方案/改造方案.md`。

### 测试方案要点

- **fail-closed 正向与负向成对**：缺分析线产物 → promote 拒绝；产物齐备 → promote 放行；产物存在但 `id` 不匹配 → 拒绝；调用方自述豁免而路由表未给 → 拒绝。
- **路由表默认取最重档**：未匹配任何行的事项判为 `delivery-change` 且不豁免；门禁失败后请求降档 → 拒绝。
- **并站的负向断言**：请求 `advance` 到 `triage` / `evidence` / `options` → 非零且条目内容与状态不变；缺多个小节时一次返回全部缺失项。
- **一致性合同测试（A6）**：构造 profile 与真门禁人工判断标记不一致的 fixture → 检查非零并列出不一致站位。这是防止结构债复发的核心断言。
- **evidence 可校验**：路径不存在 / 空文件 / 绝对路径 / `..` 越界四种负向；正向为存在且非空。
- **不得削弱回归**：`implementation-review` 自算路径与 `acceptance-state` 四 digest 的既有断言逐条重跑，结果必须与改造前一致。
- **存量兼容回归**：改造后重跑 `openspec validate --all --strict` 必须仍为通过，`node --test` 13 个测试文件全绿，`intake list` 对 19 条存量条目仍全部返回 `current` 且零重复。
- **渲染面回归**：`.omp/commands` 渲染产物与命令源一致（`command-renderer.test.ts`），`public-allowlist.json` 与实际文件集合一致。

### 风险与可逆性

| 风险 | 触发条件 | 缓解 | 可逆性 |
|---|---|---|---|
| 立项门过严，把正常小改动也挡在门外 | 路由表豁免规则覆盖不足 | 路由表与门同批交付并附至少一条豁免行；上线后第一次误挡即调表而非关门 | 高，改 JSON |
| 一致性合同测试写成「两侧互抄」而非真校验 | 断言只比较 profile 自身 | 断言必须从真门禁的行为侧取值（是否索取人工表态），不得从 profile 反读 | 高 |
| evidence 校验波及归档目录 | 校验被接到全仓扫描路径上 | 明确只作用于 active Change 写入路径，并补一条「归档目录不受新校验影响」的断言 | 高 |
| 03/04 合并丢门禁 | 合并后 digest 只算一份 | 合并后 artifact 必须承接原两份的全部 digest 与批准校验，并补断言比对门禁数量 | 中，需回滚 schema 与模板 |
| 分析线真跑后暴露 DEP0190 噪音与 run 入口语义不一致 | 强制执行后高频触发 | 已登记在台账（`INT-20260831-007`），不纳入本 Change，按痛感优先级另行处置 | 不适用 |
| 单片改动面大导致 review 覆盖不全 | 一次 review 覆盖 20+ 任务 | `implementation-review` 的 `reviewedPaths` 由代码自算、不接受手工缩小，本身即为该风险的机器缓解 | 高 |

整体可逆性：**高**。全部改动在功能分支内，归档前未创建 PR；被移除的四类资产（`change-sources.json`、`reopen-state.json`、`lifecycle-history`、`change-mode.json` / `.delivery-update-snapshot.json`）中，后三类全历史零实例，第一类在 10 个归档目录中留有历史副本。唯一不易回退的是 schema 版本号推进（`delivery-change` v5 → v6）带来的 artifact 结构变化，但它只影响新建 Change。

## 未决问题

1. **B2 的前置条件未满足，需要维护者裁定补法**。`change-sources.json` 的 `authority` 是从 1 连续递增的**全序排名**（`delivery-control.ts:136-138` 强制唯一且连续），而 `01-原始需求索引.md` 的 `- Intake 来源：` 行只有路径、没有排序。三种补法：(a) 在 01 索引的材料索引表中把 RAW 编号顺序正式定义为权威顺序（改文档语义，零代码）；(b) 判定该排序信息本身无消费者、随文件一并丢弃（最省，但与「移除前确认覆盖同等信息」的裁定字面冲突）；(c) 在 01 索引新增一列显式记录权威序。**推荐 (a)**，但这属于对裁定前置条件的解释，需维护者确认。
2. **并站后 `state` 的取值集合**。裁定是「只留『已登记』『已处置』两个真实节点」。`已处置` 在实现上仍需区分 `promoted` / `held` / `closed`（三个出口的语义不同且都有下游）。请确认：`state` 保持现有五元枚举但取消 `triaged` 这一中间态（即 `captured` / `promoted` / `held` / `closed` 四元），还是引入一个新的 `disposed` 值再用另一字段记出口？**倾向前者**（四元，零迁移成本，语义即两节点）。
3. **路由表的分类维度**。原始材料只给了「哪类事项必须走分析线、哪类走快车道豁免」一句话，没有分类维度。倾向按「改动对象」分类（治理合同 / 工具代码 / 文档表达 / 纯台账）而非按「预估工作量」分类，因为前者可由机器从事项声明中读取、后者只能靠 agent 自估——而自估正是本次要根治的绕开路径。请确认分类维度。
4. **`AGENTS.md` 校准条款改写后是否终止校准期**。裁定是「改写而非终止」，但未说明改写后的条款是否仍带有「N 事项后复盘」的自我了断条款。建议保留一个新的复盘触发条件（例如强制版分析线跑满 2 单后复盘 A1 的留/修/杀），否则「先强制、后评判」的「后评判」将没有触发点。
5. **schema 版本号推进方式**。`delivery-change` schema 当前 version 5，03/04 合并与 09 删节会改变 artifact 结构。是直接推进到 v6 并让新旧 Change 按各自版本解析，还是需要一次显式迁移？倾向前者（新版本只对新建 Change 生效，存量不迁移），请确认。
