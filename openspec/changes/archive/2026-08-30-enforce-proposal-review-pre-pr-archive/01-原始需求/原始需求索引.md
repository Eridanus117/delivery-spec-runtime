# 原始需求索引

## Change 意图

把 `delivery-change` 从“规划、测试、验收文件存在即可交付”升级为有明确方案选择、实现审查、规格同步和先归档后 PR 的闭环机器合同。

## 原始来源

### RAW-001 维护者发现流程缺口

- 来源：`maintainer-session`
- 原文口径：当前流程缺少方案提案、trade-off、方案决策、实现后的 review，归档也没有执行。
- 权威结论：不能再用同一份改造方案和同一次 digest 批准隐式代替提案与决策；测试验收不能代替实现 Review。

### RAW-002 维护者选择归档解耦方案 B

- 来源：`maintainer-session`
- 维护者决定：Runtime Change 不等待消费仓 gitlink 升级；消费仓各自在独立 Change 中处理采用。
- 维护者纠偏：Runtime Change 必须在功能分支完成 Review、Acceptance、Spec Sync 和 Archive，之后才创建最终 PR。PR 是已完成归档 Change 的交付载体，不是归档前置。

### RAW-003 当前 delivery-change schema

- 来源：`runtime-repository`
- `openspec/schemas/delivery-change/schema.yaml` 当前版本为 v4，05 只有 `change-plan`，没有独立 `solution-proposal` 和 `solution-decision`。
- `artifact-approvals.json` 只记录文件 digest 批准，不能证明候选、trade-off、决策人和决策后果齐全。

### RAW-004 当前 Review 与验收门禁

- 来源：`runtime-repository`
- `/opsx-verify` 只在聊天输出 Markdown，不保存绑定源码 commit/digest 的实现审查状态。
- `delivery-control guard acceptance/verify` 只检查 01-07 approvals 和 task projection；不检查实现 Review、critical finding 或 review stale。

### RAW-005 当前归档门禁冲突

- 来源：`runtime-repository`
- `guard archive` 只在 release guard 后匹配 09 中 `release-id` 或 `release-not-required` 文本。
- 它不检查 Spec Sync、Review、PR 是否尚未创建、未勾选人工门禁或归档准备状态，可能在文档明确“不得归档”时错误放行。

### RAW-006 已合并历史 Change

- 来源：`runtime-repository`
- `prevent-live-runtime-update-mutation` 与 `establish-controlled-openspec-upgrades` 已经通过 PR 合并但仍为 active；`openspec/specs` 尚无对应长期 capability spec。
- 新流程不得伪造它们曾遵守“先归档后 PR”；后续只能以明确 migration exception 补 Review、Sync 和 Archive。

## 边界

- 本 Change 只治理 Runtime 的 `delivery-change` schema、Commands、TypeScript 控制器、合同测试和 Runtime 自身历史迁移。
- 不更新三个消费仓 gitlink，不保存消费仓业务 Change。
- 不把 GitHub PR Review 当作 Change 内部实现 Review；两者职责不同。
- 不允许靠 Markdown 正则或未绑定 commit 的声明通过关键门禁。
