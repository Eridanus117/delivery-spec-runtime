# 方案决策

## 决策状态

- 状态：APPROVED
- 选择：候选 B——独立 Artifact 与内容寻址状态链
- 决策人：Runtime 仓库维护者（当前会话）
- 决策时间：2026-08-30
- 权威来源：维护者先选择归档解耦方案 B，随后明确“应该归档之后再去走 PR”，并确认同意据此整改流程。

## 选择依据

1. Proposal 和 Decision 必须分离，避免同一作者直接把推荐写成既定决策。
2. 测试和验收不能替代实现 Review；Review 必须绑定实际实现 commit 和路径摘要。
3. PR 是完整、已归档 Change 的交付载体，不应成为 Change 内部验收或归档的前置条件。
4. Runtime 与消费仓采用节奏应解耦，避免跨仓无限阻塞。
5. 严格 JSON 状态链可以在本地、CI 和公开候选中确定执行，不依赖 GitHub 在线状态。

## 接受的后果

- delivery-change schema 升级并增加 artifact 与状态合同。
- 实施者需要显式写 Review、Acceptance 和 Archive Readiness 状态。
- PR 反馈若要求行为或规格变化，必须 reopen、重新 Review/Acceptance/Sync/Archive。
- 两个已合并 active Change 只能按 migration exception 补治理，不能声称原本遵守新顺序。

## 拒绝方案

- 候选 A：无法可靠证明 stale、Review 覆盖和归档准备，不满足 fail-closed。
- 候选 C：违反“先归档后 PR”，继续把 GitHub 交付与 Change 内部生命周期耦合。

## 重新决策触发条件

- OpenSpec 原生提供等价的 commit-bound Review、Sync 和 Archive 状态合同；
- 文件化摘要在大型仓库出现不可接受的性能成本；
- 离线 `PR-not-started` attestation 被证明无法满足治理需要；
- 维护者要求 PR 成为内部 Review 的强制载体。
