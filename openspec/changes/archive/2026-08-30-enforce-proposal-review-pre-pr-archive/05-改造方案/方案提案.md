# 方案提案

## 决策问题

如何在保持 `delivery-change` 01-09 阅读结构和纯仓库文件模型的前提下，强制方案选择、实现 Review、Spec Sync、Archive 和 PR 的正确顺序？

## 约束

1. 维护者作最终方案决定，Agent 只能推荐。
2. Runtime Change 必须在创建最终 PR 前归档。
3. 消费仓升级不阻塞 Runtime 归档。
4. 关键门禁必须是严格机器状态，不能依赖 Markdown 关键词或人工复选框。
5. 任何实现变化必须使旧 Review/Acceptance/Readiness stale。
6. 不引入数据库、服务端状态或 shell runner。
7. 保留现有 01-09 顶层目录，降低迁移和阅读成本。

## 候选 A：强化现有 Markdown

在 `改造方案.md` 增加 trade-off 小节，在验收和发布模板增加 Review/Archive 复选框，guard 使用更多 regex。

优点：改动最小、迁移简单。

缺点：仍然不能绑定 commit、路径和摘要；复选框与正文可漂移；不能可靠处理 stale 和 reopen；继续 fail-open。

## 候选 B：独立 Artifact 与内容寻址状态链

在 05 内增加 `方案提案.md` 和 `方案决策.md`，DAG 为 Proposal→Decision→Plan。实现完成后使用严格 JSON 建立：

```text
implementation-review.json
→ acceptance-state.json
→ archive-readiness.json
→ OpenSpec archive
→ final validation
→ PR
```

所有状态绑定前一步 digest 和当前源码路径摘要。Archive 前确认 Spec Sync、cleanup 和 PR-not-started。归档后若 PR 反馈要求修改行为或规格，使用受控 reopen 保存旧证据并使状态失效。

优点：门禁可执行、可审计、可检测 stale；保持文件化和现有目录结构；职责清楚。

缺点：schema、模板、控制器、Commands 和测试均需迁移；历史 Change 需要 migration exception。

## 候选 C：依赖 GitHub PR Review 与合并后归档

先创建 PR，用 GitHub Review 作为实现审查，合并后再同步和归档。

优点：天然获得独立 Reviewer 和 GitHub 审计记录。

缺点：PR 成为 Change 内部完成的前置；未归档 Change 进入默认分支；消费仓与 Runtime 状态长期悬挂；与维护者明确要求“先归档后 PR”冲突。

## Trade-off 矩阵

| 维度 | A Markdown 强化 | B 状态链 | C PR 驱动 |
|---|---:|---:|---:|
| 提案与决策分离 | 部分 | 完整 | 部分 |
| Review 绑定源码 | 否 | 是 | 绑定 PR head，但归档过晚 |
| stale 检测 | 弱 | 强 | PR 内强、Change 内弱 |
| 先归档后 PR | 可声明、难证明 | 可机器证明 | 不满足 |
| Reopen 审计 | 无 | 完整 | 依赖人工 |
| 实施成本 | 低 | 中 | 中 |
| 迁移成本 | 低 | 中 | 高 |
| 长期维护性 | 低 | 高 | 中 |

## 推荐

推荐候选 B。它是唯一同时满足维护者生命周期决定、机器门禁、stale 检测和仓库文件化约束的方案。

## 未决问题

- Review 是否强制不同于实施者：本 Change 建议合同记录 reviewer，但暂不强制身份不同；关键改动由流程规范推荐第二 Reviewer。
- PR 创建事实如何证明：归档前只要求维护者作 `PR-not-started` attestation；Runtime 不通过网络查询 GitHub，因为离线合同测试必须可执行。
- 历史 Change 如何迁移：采用显式 migration exception，不伪造原流程顺序。
