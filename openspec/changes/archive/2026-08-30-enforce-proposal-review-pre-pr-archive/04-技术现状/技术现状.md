# 技术现状

## Schema v4

`openspec/schemas/delivery-change/schema.yaml` 当前 artifact 顺序：

```text
raw-requirements
specs
business-current
technical-current
change-plan
test-plan
tasks
acceptance
release
```

05 只有 `change-plan`。`acceptance` 和 `release` 是 OpenSpec artifact，但不在 `artifact-approvals.json` 的七项批准集合中。

## 控制器现状

`openspec/tools/delivery-control.ts`：

- `artifactPaths` 只包含 01-07 七项。
- `guard apply` 检查七项批准。
- `guard verify` 检查七项批准和 task projection。
- `guard acceptance` 再要求 delivery 的全部 task 为 verified。
- `guard release` 用 `结论: PASS` Markdown regex。
- `guard archive` 只检查 release guard 和 09 中 `release-id`/`release-not-required` 文本。

这些检查不能建立 Review、Acceptance、Spec Sync 和 Archive 之间的内容寻址关系。

## Commands 现状

- `opsx-propose` 按 OpenSpec 通用 artifact 指令推进，但自定义 DAG 没有 proposal/decision。
- `opsx-verify` 生成聊天报告，不写严格状态文件。
- `opsx-archive` 先运行薄弱 guard，随后才询问是否 sync specs，并允许跳过。
- `opsx-archive` 没有 reopen 对称操作，也不证明 PR 尚未创建。

## 可复用能力

| 能力 | 位置 | 用法 |
|---|---|---|
| exact keys/严格 JSON | `runtime-lib.ts`、`delivery-control.ts` | 新状态合同 fail closed |
| 文件和 glob 摘要 | `hash.ts` 及 control 测试 fixture | Review 路径摘要与 stale 检测 |
| 原子 JSON 写入与锁 | `runtime-lib.ts` | Review/Acceptance/Readiness 状态更新 |
| OpenSpec artifact DAG | `schema.yaml` | Proposal→Decision→Plan 依赖 |
| 结构化 task state | `task-state.json` | 保持任务真源，不再把 PR 作为内部任务 |
| 公开候选审计 | `public-candidate.ts` | 新模板、合同和工具进入 allowlist |

## 技术约束

- 所有关键状态 exact keys，未知字段拒绝。
- 摘要只覆盖仓库相对路径，不允许绝对路径、`..` 或逃逸软链。
- Review 必须覆盖 baseline→reviewed commit 中除当前 Change 目录、历史归档证据和长期 specs 之外的全部实现路径；遗漏即拒绝。
- Acceptance/Readiness 必须引用上一步 SHA-256；任何上游变化自动 stale。
- Archive 不能通过解析人工复选框或搜索任意关键词判断。
- Reopen 必须保留旧生命周期证据，不能覆盖历史 PASS。
