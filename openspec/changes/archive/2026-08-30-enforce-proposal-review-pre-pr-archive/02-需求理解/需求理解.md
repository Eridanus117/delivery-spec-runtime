# 需求理解

## 目标

建立可执行的生命周期：提案先呈现选择，维护者再作决策；实现完成后由持久化 Review 审查当前源码；验收绑定 Review；Spec Sync 和归档准备全部完成后在功能分支归档，最后才创建 PR。

## 本 Change 范围

1. 在 05 内新增独立 `solution-proposal`、`solution-decision`，再进入 `change-plan`。
2. 为三个 artifact 分别建立模板、依赖、内容质量检查和 digest 批准。
3. 增加绑定 baseline、reviewed commit、实现路径集合与摘要的 `implementation-review.json`。
4. 增加绑定 Review、任务状态和验收正文摘要的 `acceptance-state.json`。
5. 增加声明 Spec Sync、清理和 `PR-not-started` 的 `archive-readiness.json`。
6. 使 archive guard 只接受当前、完整、未 stale 的 READY 状态。
7. 增加受控 reopen，使归档后因 PR 反馈产生的代码/规格修改重新进入 Review→Acceptance→Sync→Archive。
8. 更新 `/opsx-propose`、`/opsx-verify`、`/opsx-archive`、README、公开允许清单和合同测试。

## 不在范围

- 不要求 Runtime 等待消费仓升级后才能归档。
- 不在 Change 内保存 PR URL 或合并 commit；GitHub 是该事实的权威源。
- 不用 GitHub Review 替代内部 implementation review。
- 不自动选择业务方案；机器只验证提案和决策结构，最终决定由维护者批准。
- 不在本 Change 内直接补归档两个历史 Change；先交付可靠门禁，再以 migration exception 清理历史。

## 关键术语

- **Proposal**：陈述约束、候选、trade-off、推荐和未决问题，不产生最终选择。
- **Decision**：维护者选择候选并接受其后果的权威记录。
- **Implementation Review**：对 baseline→reviewed commit 的实现路径进行完整性、正确性、安全性和可维护性审查。
- **Stale**：Review、Acceptance 或 Archive Readiness 所绑定的路径/摘要不再等于当前仓库状态。
- **Pre-PR Archive**：功能分支在创建最终 PR 前已完成 Spec Sync 与 OpenSpec Archive。
- **Reopen**：PR 创建后若行为或规格需变更，将 archived Change 受控恢复为 active，并使旧 Review/Acceptance/Readiness 失效。

## 目标顺序

```mermaid
flowchart LR
    R[Raw and Specs] --> P[Solution Proposal]
    P --> D[Maintainer Decision]
    D --> C[Change Plan]
    C --> I[Implementation]
    I --> V[Implementation Review]
    V --> A[Acceptance]
    A --> S[Spec Sync]
    S --> G[Archive Readiness]
    G --> AR[Archive]
    AR --> F[Final Validation]
    F --> PR[Create PR]
```
