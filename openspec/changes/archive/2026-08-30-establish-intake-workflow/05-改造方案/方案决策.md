# 方案决策

## 决策状态

- 状态：APPROVED
- 选择：候选 B：Runtime-owned 轻量 Intake contract
- 决策人：Runtime 维护者授权的 Agent
- 决策时间：2026-08-30
- 权威来源：当前 Change 创建会话中的明确全权授权

## 选择依据

1. Intake 是尚未承诺实施的项目事项，不能强行套入 `delivery-change` 的正式交付 DAG。
2. Intake 需要精确表达 `hold`、`close`、`reopen` 和 Promote 双向引用，这些不是现有 OpenSpec schema 的直接能力。
3. Runtime 已有严格 JSON、路径、原子写入和 fail-closed 基础工具，可减少重复实现。
4. 不把 Intake 注册成普通 Workflow Profile，避免把文件持久化、人工判断和正式 workflow 状态混成一套过度通用的合同。
5. 保持 OpenSpec 只负责正式 Change；Intake 可以在 OpenSpec 之外独立完成前置分流。

## 具体决策

- 新增 Runtime-owned Intake contract、模板、阶段 DAG、状态工具和合同测试。
- Intake 阶段固定为 `capture → triage → evidence → options → disposition`。
- `disposition` 只允许人工选择 `promote`、`hold` 或 `close`。
- `promote` 只接受已经存在的 Change slug；Runtime 不在 Promote 操作中隐藏创建 Change。
- Promote 建立 Intake → Change 和 Change → Intake 的来源关系；Promote 后 Intake 作为只读来源索引，Change 成为后续正式工作的真源。
- `hold` 和 `closed` 均保留历史；显式 reopen 后重新从 `triage` 开始。
- legacy Intake 只提供 inspect 缺口报告；不自动改写旧文件，不静默迁移。
- `evidence` 和 `options` 支持多轮追加，但推进阶段仍必须满足最小输入合同。
- 只复用现有 Runtime 基础工具；不新增通用 workflow engine，不处理 npm、CLI 分发、软链接迁移或 OpenSpec 替换。

## 接受的后果

- Runtime 将维护一套 Intake 专用合同、工具和测试，增加少量维护面。
- 既有 Intake 条目需要经过显式规范化后才能参与完整 DAG。
- Promote 需要调用方先创建目标 Change，调用步骤比隐藏式自动创建更明确但更长。
- OpenSpec 不会提供 Intake 的原生 `status/instructions/validate` 能力；Runtime 需要提供自己的 inspect/advance/promote/close 入口。

## 拒绝方案

- 候选 A：拒绝把 Intake 建模为 OpenSpec schema，避免把前置分流与正式 Change 耦合。
- 候选 C：拒绝把 Intake 注册为普通 Workflow Profile，避免两套状态模型和持久化语义重叠。

## 重新决策触发条件

- 现有 Intake 合同被证明无法覆盖多个消费仓的前置分流语义；
- OpenSpec 原生支持了不增加耦合的 Intake provider；
- 真实使用数据证明独立 Intake contract 的维护成本高于其审计和边界收益；
- Promote 需要跨仓自动创建或同步 Change，且能够建立明确的安全和回滚合同。
