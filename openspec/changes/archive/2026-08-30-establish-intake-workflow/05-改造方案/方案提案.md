# 方案提案

## 决策问题

如何在不重复实现 `delivery-change`、不强迫需求提前承诺实施、且不把项目分析写入个人 Desk 的前提下，把 `openspec/intake/` 变成可验证的轻量前置工作流。

## 约束

- Intake 只处理“是否值得投入、需要补什么事实、候选如何比较”；正式交付仍由 `delivery-change` 负责。
- 人工决定是不可替代的门；Runtime 只能验证判断已记录，不能自动决定 Promote、Hold 或 Close。
- 公共 Runtime 不保存工作或私人业务正文、凭据、环境和真实交付证据。
- 必须保留现有 Runtime 入口、TypeScript 执行方式、Node `node:test` 合同测试和 fail-closed 习惯。
- Promote 后 Change 是 Requirement、方案、任务和证据的工作真源；Intake 只保留来源索引。
- 旧的 frontmatter/status-only Intake 需要可识别并报告迁移缺口，不得静默升级。
- 本 Change 不处理 npm、CLI 分发、软链接迁移或 OpenSpec 替换。

## 候选 A：OpenSpec schema 扩展

- 方案：为 Intake 增加一个 OpenSpec schema，复用 `openspec new/status/instructions/validate` 和 Artifact DAG；Promote 时转入 `delivery-change`。
- 优点：复用 OpenSpec 的目录、模板、DAG 和 CLI；长期可以获得统一的 schema 工具链。
- 缺点：需要把尚未承诺实施的 Intake 语义映射到 OpenSpec Change 模型；Promote、Hold、Close、Reopen 和跨目录来源关系仍需 Runtime 自己补齐。
- 成本：中高；需要 schema、CLI 行为、迁移、Runtime 合同和消费仓验证。
- 风险：把前置分流与正式交付耦合；OpenSpec 版本变化可能改变 Intake 语义。
- 可逆性：中；保留旧 Markdown 兼容需要长期双路径。

## 候选 B：Runtime-owned 轻量 Intake contract

- 方案：在 Runtime 内定义 Intake schema、模板和小型状态机；使用现有 `runtime-lib.ts` 的严格 JSON/路径工具，新增 Intake control 入口。阶段为 `capture → triage → evidence → options → disposition`，出口为 `promote/hold/close`。
- 优点：语义与正式 Change 分离；可以精确实现人工判断、Promote 双向引用、Hold/Close/Reopen 和 legacy 检查；不要求 OpenSpec 参与前置分流。
- 缺点：Runtime 需要维护一套新的合同、命令和测试；与现有 Workflow Profile 有部分通用状态校验需求。
- 成本：中；新增一组小型 schema、工具、模板、命令和合同测试，不复制 `delivery-change` 全部 Artifact。
- 风险：如果抽象过度，可能形成第二套通用 workflow engine；如果与现有工具重复，维护成本上升。
- 可逆性：高；Intake 输出仍是项目仓文件，正式 Change 入口保持不变。

## 候选 C：扩展现有 Workflow Profile

- 方案：把 Intake 注册为新的 Workflow Profile，复用 `workflow-core.ts` 的 request/result、阶段推进和人工判断机制；另外补充 Intake 文件读写和 Promote/Close。
- 优点：复用已有 Profile registry、binding、request/result 和阶段执行；运行时行为风格一致。
- 缺点：现有 Profile 设计偏向一次请求/响应 workflow，不天然表达 Intake 文件的来源、证据追加、跨轮历史和 Change 双向引用；容易把 Intake 语义塞进过于通用的合同。
- 成本：中；Profile 合同扩展、文件持久化和 Promote 仍需新增。
- 风险：Workflow Profile 与 Intake asset 两套状态模型重叠；未来修改一方可能破坏另一方兼容性。
- 可逆性：中高；可以撤销 Profile 注册，但调用方可能已经依赖其 JSON 结构。

## Trade-off 矩阵

| 维度 | 候选 A：OpenSpec schema | 候选 B：Runtime contract | 候选 C：Workflow Profile |
|---|---|---|---|
| Intake/Change 边界 | 中 | 高 | 中 |
| OpenSpec 依赖 | 高 | 低 | 低 |
| 复用现有代码 | 高 | 中 | 高 |
| Promote/Close 精确性 | 中 | 高 | 中 |
| 实现复杂度 | 高 | 中 | 中 |
| 兼容风险 | 中高 | 低 | 中 |
| 可逆性 | 中 | 高 | 中高 |
| 形成第二套引擎风险 | 低 | 中 | 中高 |
| 适合当前 Change | 中 | 高 | 中 |

## 推荐

推荐候选 B，但只复用现有 Runtime 的 JSON、路径、哈希和原子写入基础工具，不新建通用 Workflow Engine。Intake 应保持自己的领域合同，因为它的核心对象是“尚未承诺的项目事项”，而不是已经进入 Change 的执行 workflow。

候选 C 的通用阶段推进逻辑可以在实现时择取纯函数级能力，但不把 Intake 注册成普通 delivery Profile。候选 A 暂不采用，除非后续事实证明 OpenSpec 原生 schema 能直接表达 Intake 的生命周期且不会提高升级耦合。

## 未决问题

- `promote` 是否由 Runtime 创建目标 Change，还是只接受已存在的 Change slug；本 Change 倾向后者，避免隐藏创建和错误承诺。
- legacy Intake 是否提供自动迁移命令，还是只提供 inspect 报告；本 Change 倾向先报告、后显式迁移。
- `evidence` 和 `options` 是否允许多轮追加；本 Change 倾向允许追加，但每次推进仍需满足最小合同。
