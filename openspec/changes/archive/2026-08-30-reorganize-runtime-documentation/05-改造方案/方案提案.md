# 方案提案

## 决策问题

如何在不改变 Runtime 行为、不引入第二真源的前提下，让不同读者按任务快速找到当前文档。

## 约束

- 本次唯一实现范围是文档及其 OpenSpec 治理证据。
- 保留现有命令、路径、安全语义和机器合同。
- README 必须仍可完成最短接入。
- 不引入文档站、生成器、依赖或自动发布。
- Implementation Review 由 fresh session 只读完成。

## 候选 A：保留单 README 并重排

- 方案：不新增文档，只重排章节、增加目录和读者标签。
- 优点：链接和维护文件数量最少。
- 缺点：不同受众仍共享一个持续增长的文件；专项 runbook 继续占据入口。
- 成本：低。
- 风险：短期清晰，后续再次混杂。
- 可逆性：高。

## 候选 B：入口 README 加五份专题文档

- 方案：README 保留定位、范围、架构摘要、最短接入、不变量、任务导航和最终验证；架构、消费仓、维护、升级、治理分别进入五份 `docs/*.md`。
- 优点：按读者任务分层；现有内容可迁移；不引入工具；权威边界可集中说明。
- 缺点：需要维护仓库内链接；读者执行专项任务时会跳转一次。
- 成本：中。
- 风险：迁移时遗漏命令或重复定义规则。
- 可逆性：高，可通过 Git 恢复或重新合并文档。

## 候选 C：引入文档站和生成器

- 方案：采用静态站点、导航配置和自动链接检查。
- 优点：大规模文档导航和搜索能力最好。
- 缺点：当前内容规模不足以抵消依赖、构建和发布维护成本。
- 成本：高。
- 风险：形成与 Runtime 本体无关的新交付面。
- 可逆性：中。

## Trade-off 矩阵

| 维度 | 候选 A | 候选 B | 候选 C |
|---|---|---|---|
| 按任务可发现性 | 中 | 高 | 高 |
| 真源边界 | 中 | 高 | 高 |
| 维护成本 | 低 | 低 | 高 |
| 当前规模适配 | 中 | 高 | 低 |
| 引入依赖 | 无 | 无 | 有 |
| 长期可扩展性 | 低 | 高 | 高 |

## 推荐

推荐候选 B。它直接解决职责混杂，同时保持仓库内纯 Markdown、现有工具链和可逆性；五份专题文档足够覆盖当前任务，不建立过度层级。

## 未决问题

无。维护者已在当前会话确认采用 README 入口加专题文档的信息架构，并将文档整理设为唯一任务。
