# 方案提案

## 目标

把 Profile 的机器真源直接变成人可读 catalog，并为需求分析 Profile 增加最小结构和轮次合同，同时保持 Runtime 与 Desk 解耦。

## 候选 A

Profile 元数据与内容合同内聚（推荐）。在 Profile 文件中增加用途、适用范围、不适用范围、handoff 和阶段 description/exitCondition；增加 declarative `inputContracts`，由通用 core 检查对象字段、数组和枚举。请求增加 `analysisRounds`，由 Profile 声明并由通用检查器验证。新增 `workflow catalog` 和 `workflow describe`，直接从 registry/profile 生成输出。

优点：单一真源、可生成目录、适合不同 Profile；不把 Desk 策略写进 Runtime。风险：通用合同表达能力有限，需要以后扩展。

## 候选 B

每个 Profile 编写独立 TypeScript 校验器。优点：表达能力强。缺点：校验逻辑与 Profile JSON 分裂，新增 Profile 需要代码分支，容易恢复“delivery-change 特判”。不选。

## 候选 C

Runtime 读取 Desk 提案并自动路由。优点：使用体验集中。缺点：违反 Workflow System 独立调用边界，引入跨仓扫描、权限和状态同步问题。不选。

## Trade-off 矩阵

| 维度 | 候选 A：内聚合同 | 候选 B：独立校验器 | 候选 C：Desk 自动路由 |
|---|---|---|---|
| Profile 可扩展性 | 高 | 中 | 低 |
| Runtime 与外部系统耦合 | 低 | 低 | 高 |
| 机器可校验性 | 中高 | 高 | 中 |
| 维护成本 | 低 | 中高 | 高 |

## 推荐

选择候选 A。Profile 文件作为阶段与说明的真源，registry 只负责身份和路径索引；通用 core 只验证声明式结构，不替主人判断事实或自动路由。

## 未决问题

- 后续是否需要支持更复杂的嵌套 input contract，留待实际 Profile 需求出现后评估。
- 是否需要增加更多 Profile，由新的独立 Change 依据实际使用场景决定。
