# 业务现状

## 参与者与职责

| 参与者 | 当前职责 | 当前约束 |
|---|---|---|
| Runtime 维护者 | 维护 schema、Commands、工具、合同与版本 pin | 必须通过仓内 Change、功能分支和 PR |
| OpenSpec 上游 | 发布 CLI 与官方集成模板 | 是升级输入，不自动覆盖 Runtime 定制 |
| 消费仓维护者 | 通过 gitlink 选择 Runtime commit | 不能在 dirty submodule 或漂移软链上运行 |
| Change 审阅者 | 批准规划、核对 delta、验收和发布 | 需要机器证据而不是人工猜测整文件差异 |

## 当前升级流程

前置安全 Change 已把实时仓 `runtime-update` 改为稳定拒绝，因此当前流程只有“禁止原地更新”，尚无可执行的安全替代：

```text
发现上游版本
→ 人工阅读 release note
→ 缺少 current/candidate 隔离生成
→ 缺少 upstream/local 三类 delta
→ 缺少机器 JSON 合同和消费仓候选 smoke
→ 无法客观决定是否提升 Runtime pin
```

## 当前对象

| 对象 | 当前状态 | 风险 |
|---|---|---|
| `runtime-manifest.json` | pin OpenSpec `1.10.0` | 无标准化候选提升门禁 |
| 九个 `.omp/commands` | 可运行、已提交、整文件定制 | 重复 preamble 难以一致维护；上游变化难审 |
| `runtime-entry.ts` | 实时升级 fail closed | 没有 Runtime 仓内安全评估入口 |
| `public-candidate.ts` | allowlist 公开候选 | 尚不知道 renderer/evaluator/fragments/合同 |
| 三消费仓 | 各自 gitlink 锁定 Runtime | 真实仓不能承担候选试验写入 |

## 已知候选 1.11

隔离探针显示 1.10 与 1.11 的 OMP 文件集合相同，只有上游 `opsx-explore.md` 变化。变化本身值得吸收，但“文件少”不能绕过门禁：Runtime Commands 相对上游是大幅整文件定制，仍需结构化合并、确定性渲染和完整验证。

## 失败与处置现状

- 上游生成写入实时仓：已由前置 Change 阻止。
- 上游与本地差异无法审阅：当前只能人工整文件比较。
- CLI JSON 漂移：当前合同测试只验证 Runtime 自己，没有 current/candidate 对称 probe。
- 消费仓兼容性：当前只能对真实仓运行已锁定 Runtime 的 `runtime-check`，不能注入候选版本。
- 候选失败：没有统一报告结构，无法保留失败证据并复用下次评估。

## 目标业务流程

```text
维护者声明 current/candidate
→ 隔离生成两套上游 Commands
→ 确定性渲染 Runtime current/candidate
→ 生成三类 delta 与 SHA
→ 执行 current/candidate JSON probes
→ 执行空白 fixture 和三消费仓临时副本 smoke
→ 全部门禁通过才更新 fragments 与 pin
→ Runtime 完整合同、验收、PR
```
