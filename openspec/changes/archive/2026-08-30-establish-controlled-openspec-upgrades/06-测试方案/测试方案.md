# 测试方案

## 测试目标

证明升级框架具备四个核心性质：

1. Commands 只有一个结构化真源且渲染确定；
2. current/candidate 官方生成只能发生在临时根；
3. delta、CLI probes 与报告合同稳定、严格、可重放；
4. 空白项目和消费仓候选验证不写真实仓、不泄露业务正文。

## 永久合同测试

### T-01 Commands 迁移保持行为

- runner：`node:test`
- fixture：合并前九个 rendered Commands 的已提交基线。
- 步骤：从 manifest + preamble + bodies 渲染到临时目录。
- 断言：首次迁移时九个文件逐字节一致；文件集合固定；重复渲染 SHA 相同；换行固定为 LF 和单个 EOF newline。
- 缺陷防护：防止拆分 sources 时静默丢失 Runtime 防护或改写中文说明。

### T-02 Renderer check 与恶意 manifest

- 缺失、额外、手工修改 rendered Command 分别使 check 非零并报告路径。
- 重复 ID、未知字段、绝对 body、`..`、逃逸软链、缺失 body、非法 description 在写入前拒绝。
- 拒绝路径不得改动 `.omp/commands` 摘要。

### T-03 升级请求严格解析

- 非精确 SemVer、current=candidate、未知字段、重复消费者、非法仓名、缺失仓、evidenceRoot 越界、runtimeRoot 冲突分别拒绝。
- PATH 中 fake npm 写 invocation sentinel；非法请求时 sentinel 必须不存在，证明未启动子进程。
- 子进程始终使用 executable + argv，参数中的空格和元字符不得变为 shell 行为。

### T-04 隔离生成与三类 delta

- fake npm 根据请求版本生成确定的九 Commands 和 JSON probe 输出。
- 1.10/1.11 fixture 只改变 `opsx-explore.md`。
- 断言 upstream/current-local/candidate-local 都包含九个规范化 POSIX 路径、changeType、两侧 SHA、additions/deletions。
- 临时生成根必须位于工具创建的 OS temp root；Runtime source 摘要不变。
- 成功和失败路径均清理临时根，失败报告不得覆盖成功报告。

### T-05 CLI JSON probes

- current/candidate 对称执行稳定 probes；candidate-only probe 只在声明版本范围运行。
- 缺字段、字段类型变化、stdout 非 JSON、退出码变化分别 fail closed。
- 报告只保存 probe ID、argv、退出状态、required field 类型和结构签名，不保存 artifact 正文。

### T-06 空白 candidate Runtime fixture

- 构造临时 Runtime Git 仓、父仓、gitlink 和三条相对软链。
- 用临时 PATH 注入 candidate OpenSpec `--version` 与 CLI。
- 断言 `runtime-check` 成功；错误版本、dirty candidate、错误 gitlink、漂移软链继续 fail closed。
- 更新现有 submodule fixture：从 manifest 读取 required version 并使用临时 fake `openspec --version`，避免永久测试依赖全局 CLI 版本或网络。

### T-07 消费仓临时副本与脱敏

- 为三个最小 Git 仓建立 fixture；内容放入敏感哨兵字符串。
- clone 到临时根，注入 candidate Runtime 临时 commit 和 candidate CLI，运行 runtime-check/probes。
- 断言真实仓 HEAD、status、受管路径摘要不变。
- 断言报告不含敏感哨兵、文件正文、环境值和凭据，只含仓名与合同字段。
- 任一仓失败时总体结论失败，但保留其他仓独立结果。

### T-08 Public candidate 完整性

- public allowlist 包含 `.omp/command-sources`、三个 upgrade contracts、renderer 和 evaluator。
- 禁用路径、秘密哨兵和外部副作用测试继续通过。
- 公开候选执行 renderer check 和 Runtime 完整合同。

### T-09 README 与 Mermaid 合同

- README 必须包含准确 Mermaid 架构图、消费仓接入、三条受管软链、不变量、renderer、升级 request JSON、三类 delta、验证和 PR 自治理。
- README 不得声称本仓不保存任何真实 Change；只禁止保存消费仓/业务 Change，本仓 Runtime 自治理 Change 合法。
- `opsx-explore` 必须包含 `mermaid` fenced block、写入前单独确认和配置文件写入范围；不得包含 Unicode 线框字符。
- OMP Command 不要求 plain ASCII 主图；只有不支持 Mermaid 的外部目标才允许 ASCII 降级。

## 正式 1.10.0 → 1.11.0 验收运行

该运行使用真实 npm/OpenSpec 包，不进入永久离线测试套件；结果保存在当前 Change 的唯一 run 目录。

### 输入

- current：`1.10.0`
- candidate：`1.11.0`

- Runtime：当前功能分支锁定 commit
- consumers：`agent-system`、`webcoding-spec`、`work-spec` 的显式绝对路径
- evidenceRoot：`08-验收/runs/<run-id>/upgrade-evaluation/`

### 必需断言

1. 实际 `--version` 分别为 `1.10.0` 和 `1.11.0`。
2. 两侧生成文件集合均为九 Commands。
3. upstream delta 只有 `opsx-explore.md` modified；若不符立即停止审阅。
4. renderer check 通过。
5. 1.10/1.11 稳定 JSON probes 通过；1.11 candidate-only probes 通过。
6. 空白 candidate fixture 的 runtime-check 通过。
7. 三消费仓临时副本 smoke 通过。
8. 三个真实消费仓和 Runtime checkout 前后 status/摘要不变。
9. report schema 校验通过且不含业务正文。

## 提升后验证

若正式 run 全部通过并提升 pin：

1. renderer write 后只允许预期的 `opsx-explore.md` 语义变化：写入确认、配置文件范围和 OMP Mermaid 图示策略；
2. `runtime-manifest.json` 和合同断言均为 `1.11.0`；
3. 使用 candidate CLI 注入执行全部 Runtime tests；
4. `openspec validate establish-controlled-openspec-upgrades --strict` 通过；
5. public candidate 验证通过；
6. 新的 08 验收 run 保存完整原始输出和清理证据。

## 运行命令

```bash
node --experimental-strip-types --test test/*.test.ts
node --experimental-strip-types openspec/tools/render-commands.ts check --runtime-root .
node --experimental-strip-types openspec/tools/openspec-upgrade.ts evaluate --request <request.json>
openspec validate establish-controlled-openspec-upgrades --strict
```

## 清理

- 所有永久测试 fixture 使用 `mkdtemp`，在 `finally` 递归删除。
- 正式评估器清理 package/generator/consumer 临时根，仅保留 evidenceRoot 中的白名单报告。
- 不删除或修改真实消费仓文件；任何前后摘要变化都是验收 critical。
