# 方案提案

> 历史迁移：本 Artifact 根据已合并 PR #2 的原始需求、技术方案、实现和验收证据回填，用于把 v4 Change 纳入 v5 生命周期合同；不改写原决策语义。

## 候选 A：在实时 Runtime 仓直接执行 OpenSpec Update

直接以 Runtime checkout 为生成器 cwd，再人工修复本地定制。路径短，但会把上游生成副作用带入实时仓，无法证明消费仓零写入，也无法稳定区分 upstream/current-local/candidate-local 差异。

## 候选 B：隔离生成并以结构化真源受控提升

在 OS 临时目录生成 current/candidate，机器化记录三类 delta、CLI probes、fixture 和消费仓 smoke；九个 Commands 由 manifest、公共 preamble 和 bodies 确定性渲染。全部门禁通过后才提升 pin。

## 候选 C：人工复制上游 Commands

人工比较并复制上游文件，再凭审阅记录决定保留本地差异。实现成本低于完整评估器，但不可重复、易漏文件，无法形成稳定升级合同。

## Trade-off 矩阵

| 维度 | 候选 A | 候选 B | 候选 C |
|---|---|---|---|
| 真实仓零写入 | 差 | 优 | 中 |
| 差异可审计 | 中 | 优 | 差 |
| 可重复性 | 中 | 优 | 差 |
| 初始实现成本 | 低 | 高 | 低 |
| 长期维护成本 | 高 | 低 | 高 |

## 推荐

推荐候选 B。它是唯一同时满足真实 Runtime/消费仓零写入、机器差异、确定性 Commands 和版本提升 fail-closed 的方案。PR #2 已按该方案实现并验收。

## 未决问题

无。OpenSpec 1.11.0 提升、九 Commands 渲染、三类 delta、JSON probes、空白 fixture、三消费仓隔离 smoke 和公开候选审计均已有 PASS 证据。
