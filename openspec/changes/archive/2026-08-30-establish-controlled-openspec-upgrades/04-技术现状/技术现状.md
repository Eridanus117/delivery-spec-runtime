- 链接：`.omp/commands`、`openspec/schemas/delivery-change`、`openspec/tools/runtime-entry.ts` 三条 manifest 托管相对软链。
- 测试：Node `node:test`，当前完整合同 15 项。

## 当前 Commands 结构

九个 `.omp/commands/opsx-*.md` 每个都包含：

1. YAML frontmatter；
2. 重复的 Runtime 入口与 fail-closed preamble；
3. 命令独有的 OpenSpec 工作流正文；
4. Runtime 的审批、来源、task-state、路径与发布防护。

重复内容直接嵌在九个整文件中。上游版本变化时无法分别回答：

- 上游改了什么；
- Runtime 相对当前上游定制了什么；
- 候选 Runtime 相对候选上游保留了什么。

## 官方写入路径

OpenSpec v1.11.0 的 `src/core/update.ts` 调用命令生成适配器并写入生成文件；OMP adapter 的目标固定为：

```text
.omp/commands/opsx-<command-id>.md
```

目录软链会被文件系统正常追随，因此任何以真实消费仓为 cwd 的官方生成都会写入 Runtime submodule。前置 Change 的拒绝必须保持，新的评估器只能使用自己创建的临时根。

## 缺口

1. 没有 Commands manifest、公共 preamble、body fragments 或 renderer check。
2. 没有隔离安装/执行两个精确 OpenSpec 版本的工具。
3. 没有稳定的升级 request/report JSON schema。
4. 没有三类 delta 和结构化文件摘要。
5. 没有声明式 CLI JSON probes。
6. 没有候选 Runtime 注入消费仓临时副本的 smoke runner。
7. public candidate allowlist 不包含上述新资产。

## 1.11 探针事实

- 1.10 与 1.11 生成文件集合均为九个 Commands。
- upstream delta 只有 `opsx-explore.md`。
- 1.11 新规则：写入前单独明确确认；图必须 plain ASCII；配置文件也算写入范围。
- 两个版本的 `status --change --json` 在最小 `delivery-change` fixture 上均成功，观测结构一致。
- 这些事实来自临时根，不构成提升 pin 的充分条件；正式工具和正式 run 仍必须重放。

## 兼容与事务边界

- 评估请求必须先完整解析再产生临时目录或包执行副作用。
- 临时目录必须在成功、失败和中断路径清理；Change run 目录只保存明确允许的证据。
- 所有子进程使用 executable + argv，禁止 shell command 字符串。
- 报告不得保存消费仓文件正文；只保存路径类别、结构字段、摘要和状态。
- Runtime rendered Commands 的写入使用同目录临时文件与原子替换，check 模式零写入。
