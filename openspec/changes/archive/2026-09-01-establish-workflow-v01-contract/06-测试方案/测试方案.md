# 测试计划

## 验证范围与层级

| 层级 | 目标 | 工具/入口 | 通过标准 |
|---|---|---|---|
| 合同验证 | 证明 workflow request、profile、matter、result 的 `schemaVersion: 1`、必填字段、枚举和禁止额外字段稳定 | `openspec validate --all --strict`；Node `node:test` 合同探针 | 合法 fixture 通过；每个非法 fixture 在预期字段处失败 |
| Core 单测 | 证明阶段输入、人工判断、阶段顺序和下一阶段计算是确定的 | `workflow-core.ts` 导出的 `executeWorkflow(request)`；Node `node:test` | 成功、末阶段、缺输入、缺人工判断、非法阶段/profile 均得到预期 result，不访问文件系统 |
| CLI 行为探针 | 证明真实 standalone CLI 从显式 `--input` 读取并返回单个机器 JSON | `node --experimental-strip-types openspec/tools/workflow-entry.ts run --input <fixture>` | stdout 可解析且只有一个结果对象；成功为 `completed`，阻塞/拒绝为显式状态和非零退出码 |
| 边界与兼容回归 | 证明不读取未授权外部资产、不写调用方仓库、不污染 submodule，且旧 delivery-change 入口不变 | 临时 consumer repo、git status、现有 `test/submodule.test.ts` 与全量合同测试 | consumer 父仓和 Runtime submodule 均 clean；旧测试全通过；无隐式全局路径依赖 |
| 交付级 smoke | 证明从当前仓根直接执行新入口和既有 Runtime 命令都可用 | Windows Node 命令行 | workflow CLI 可独立运行；`runtime-check` 与既有 lifecycle probe 无新增失败 |

## 测试环境与数据

| 资产 | 位置 | 生命周期 | 清理责任 |
|---|---|---|---|
| 合成成功请求 | `06-测试方案/fixtures/workflow-success.json` | 版本化、只含公共合成内容 | 随 Change 回滚删除 |
| 合成阻塞请求 | `06-测试方案/fixtures/workflow-missing-input.json` | 版本化、只含公共合成内容 | 随 Change 回滚删除 |
| 合成等待人工判断请求 | `06-测试方案/fixtures/workflow-awaiting-judgment.json` | 版本化、只含公共合成内容 | 随 Change 回滚删除 |
| 合成非法请求 | `06-测试方案/fixtures/workflow-invalid.json` | 版本化、只含公共合成内容 | 随 Change 回滚删除 |
| CLI/consumer 临时目录 | `os.tmpdir()` 下每次测试新建 | 单测试 | `t.after()` 删除；不得写入未授权外部资产或当前仓 |
| Runtime submodule fixture | 复用 `test/submodule.test.ts` 的临时 gitlink/软链构造方式 | 单测试 | 测试结束删除临时仓；不得修改工作树 `.delivery-spec-runtime` |
| 测试 runner | `test/workflow.test.ts` | 与源码同 Change 提交 | 由全量 Node test 命令运行 |

所有 fixture 均为合成 profile、合成事项 id、合成路径和合成 artifact ref。不得保存个人日记、真实业务需求、凭据、账号、环境变量、请求响应、trace、run-id 或 release-id。

## 场景与 Requirement 覆盖

| 场景 ID | Requirement | 前置 | 输入 | 断言 | 清理 |
|---|---|---|---|---|---|
| WF-001 | 阶段合同 | 合法两阶段声明式 profile | `workflow-success.json`，输入满足当前 stage | `status=completed`；回显 `matterId`/`profileId`/`stageId`；`nextStageId` 为下一阶段；artifact refs 保持稳定 | 删除临时输出 |
| WF-002 | 阶段合同 | 当前 stage 声明必需输入 | `workflow-missing-input.json` | `status=blocked`；`reason.code=missing_input`；不推进 `nextStageId`；退出码非零 | 删除临时目录 |
| WF-003 | 阶段合同与人工判断 | 当前 stage `humanJudgment.required=true` | `workflow-awaiting-judgment.json`，不带判断 | `status=waiting_human_judgment`；不伪造判断；退出码非零 | 删除临时目录 |
| WF-004 | 阶段合同与结果返回 | 当前 stage 需要判断且提供明确批准 | 在 WF-003 请求中增加 `humanJudgment.decision=approved` 和理由 | `status=completed`；结果包含判断摘要；进入声明的下一 stage | 删除临时目录 |
| WF-005 | 事项身份 | 合法请求包含稳定事项 id | 任意合法 fixture | `matter.id` 原样回显为 `matterId`；空字符串、缺失或非字符串被拒绝；core 不自动生成 id | 无持久化数据 |
| WF-006 | 独立调用 | 临时 cwd 无全局索引、无项目配置 | 通过绝对路径执行 `workflow-entry.ts`，只给 `--input` | 命令成功或按输入显式阻塞；结果不依赖 cwd、外部环境或隐式扫描；当前仓文件摘要不变 | 删除临时 cwd |
| WF-007 | 独立调用与仓库边界 | 临时 consumer repo 含 Runtime gitlink | 在 consumer cwd 执行 workflow CLI | consumer `git status --porcelain` 为空；`.delivery-spec-runtime` submodule status 为空；没有新文件、锁文件或软链改写 | 删除临时 consumer repo |
| WF-008 | 结果返回 | 合法 profile 的末阶段 | 末阶段成功请求 | `status=completed`；`nextStageId=null`；结果 JSON 可被第二次调用方直接消费 | 删除临时输出 |
| WF-009 | 结果返回与拒绝 | profile 不存在、stage id 不存在、阶段顺序非法或额外字段存在 | `workflow-invalid.json` 及参数变体 | `status=rejected`；稳定 `reason.code`；非零退出码；stdout 仍是可解析结果或参数错误明确落 stderr | 删除临时目录 |
| WF-010 | 兼容约束 | 当前 delivery-change 合同测试集 | 运行既有 `delivery-control`、lifecycle、submodule 和全量 tests | 既有测试通过；新 core 不改变旧 task/artifact/lock 行为；既有 Runtime manifest 三个软链声明不变 | 无；测试负责临时资源 |

## 自动化资产

```text
06-测试方案/
├── fixtures/
│   ├── workflow-success.json
│   ├── workflow-missing-input.json
│   ├── workflow-awaiting-judgment.json
│   └── workflow-invalid.json
├── scenarios/
│   └── workflow-boundary.json
├── runtime/
│   └── consumer-fixture-notes.txt
└── runner/
    └── workflow-cli-probe.ts
```

实现测试时，源码测试仍放在仓库现有 `test/workflow.test.ts`，上述 Change 目录只保存合成输入与场景定义，避免重复保存同一份完整请求。若测试 helper 需要扩展，复用 `test/helpers.ts` 的 `runTool` 和临时目录风格。

- TypeScript runner 使用 `node --experimental-strip-types`，测试使用 Node 内置 `node:test` 与 `node:assert/strict`。
- 不新增 shell runner、网络依赖或外部账号；子进程使用 `process.execPath` 调用真实 CLI。
- consumer 边界测试必须在临时 git 仓运行，并在调用前后分别记录父仓和 submodule 的 `git status --porcelain`；任一非空立即失败。
- 外部资产非依赖验证通过临时 `cwd`、清空专用环境变量和不挂载外部路径完成；测试不得读取工作区外的业务或流程资产。
- 所有临时目录在 `t.after()` 清理；清理失败视为测试失败，不以残留文件掩盖问题。

## 断言与停止条件

- 任何结果缺少 `schemaVersion`、`matterId`、`profileId`、`stageId`、`status`、`nextStageId`、`artifacts` 或 `reason` 时停止该 Change 验证。
- 任何阻塞、等待人工判断或拒绝结果被标为 `completed` 时停止，不继续迁移或接入调用方。
- 任何 CLI 读取未指定路径、写入 cwd/consumer repo/未授权外部资产、改变 Runtime submodule 状态或创建第二套 lock/hash 文件时停止。
- 任一旧 `delivery-change` 测试回归失败时停止；不得通过放宽旧断言或修改旧合同来消除失败。
- Windows 下路径、退出码、stdout/stderr 与 POSIX 行为不一致时，以本仓既有 Windows fail-closed 约束为准，先修复再执行交付验收。

## 运行命令

```bash
node --experimental-strip-types --test test/workflow.test.ts
node --experimental-strip-types --test test/*.test.ts
node --experimental-strip-types openspec/tools/render-commands.ts check --runtime-root .
openspec validate --all --strict
```

本文件只定义测试依据，不记录实际运行结论；实际命令输出和完整字段应在后续 `08-验收/runs/` 中按一次运行一次保存。
