## 选择依据

- 三项硬约束（人侧零命令记忆、追加式交付、随版本锁分发）只有候选 A 全部满足且改动面最小。
- skill 是 Claude Code 原生的按话题发现机制，直接实现「人不记命令、agent 自动发现指引」的交互合同。
- runtime-link 与 runtime-check 对 links 均为泛化解析，新增第四条软链是数据级变更，机器合同自动覆盖。
- 内容完整性用聚焦合同测试补足，避免为一份 skill 扩展渲染管线（候选 B 的过早抽象）。

## 接受的后果

- skill 源文件位于渲染检查体系之外，其完整性由独立合同测试保障，形成两套内容校验入口。
- links 合同从三条变为四条：升级 gitlink 的消费仓必须重跑 `runtime-link.ts apply`，否则 `runtime-check` fail-closed；此为既有升级合同的自然延伸，需在消费仓文档写明。
- 在途提醒首版仅为 skill 内行为约定，无机器强制；效果留待 3 事项复盘检查点评估。
- OMP 载体维持九条命令不变，两载体指引形态暂不统一；渲染整合留待 Claude Code 资产增多后另立 Change。

## 拒绝方案

- 候选 B：不选择，单一真源收益在仅有一份 skill 时不成立，manifest 与渲染器合同改动面大，属过早抽象。
- 候选 C：不选择，不随版本锁分发、各仓复制必然漂移、新环境不可发现，不满足 spec「随 Runtime 分发」需求。

## 重新决策触发条件

- Claude Code 资产增多（≥3 份）导致静态维护成本超过渲染整合成本时，重议候选 B。
- links 合同扩展在真实消费仓升级中造成不可接受的兼容破坏。
- 3 事项复盘检查点证明 skill 约定不足以承载在途提醒或单事项约束，需要机器机制。
- Claude Code skill 机制本身的发现语义发生不兼容变化。
