# 方案提案

## 决策问题

在保留 gitlink 为唯一版本锁的前提下，用什么机制替换四条受管软链，使消费仓获得普通文件、防漂移不弱于现状、迁移对旧消费仓安全。

## 约束

- gitlink 是唯一版本锁；不得在任何资产中固化第二份哈希清单或版本号。
- fail-closed 不退让：副本缺失、多余、内容漂移都必须被拒绝。
- 旧消费仓（软链形态）升级后必须有安全迁移路径。
- 不改变 manifest links 的数据形状（link→source 四条），少动合同面。
- 公共仓边界与既有测试哲学保持。

## 候选 A：实时哈希对照 pinned submodule（副本无独立真源）

- 方案：apply 把 links 源**复制**为消费仓普通文件（目录递归、staged+rename 原子替换）；runtime-check 每次运行对每条投影逐文件计算 sha256，与 pinned submodule 工作树对应文件实时比对（文件集合与内容都必须一致）。不新增任何锁文件。
- 优点：submodule 仍是唯一真源与唯一锁，与既有裁决冲突最小；校验强度等价于软链（且能发现软链方案发现不了的「目标内部被改」）；哈希与复制基础设施仓内现成。
- 缺点：runtime-check 成本从 O(链数) 变为 O(文件数) 哈希计算（当前约 30 个小文本文件，毫秒级，可接受）；副本使消费仓 git 历史里真实存储这些文件（体积极小）。
- 成本：中——改 runtime-link/verifyLinks、6 个测试文件断言、docs 措辞、AGENTS.md 第 5 条修订。
- 风险：中低；语义简单，全套合同测试兜底。
- 可逆性：高；恢复 symlinkSync 分支即可回退。

## 候选 B：manifest 固化哈希清单

- 方案：发布时把每条投影的期望哈希写进 manifest 或伴随锁文件，runtime-check 对照固化清单。
- 优点：校验不依赖 submodule 工作树状态。
- 缺点：**构成第二套锁**（哈希清单与 gitlink 可能分叉），正面违反唯一锁约束；发布流程多一步生成环节。
- 成本：中；风险：中高（锁分叉）；可逆性：中。

## 候选 C：保留软链，只修局部痛点

- 方案：不换机制；以 .gitattributes、长路径指引、文档强化缓解四项痛点。
- 优点：改动最小。
- 缺点：与维护者门1方向裁决直接相悖；四项痛点中 symlink 权限与升级漏跑 apply 无法根治。
- 成本：低；风险：低；可逆性：高。

## Trade-off 矩阵

| 维度 | 候选 A | 候选 B | 候选 C |
|---|---|---|---|
| 唯一锁原则 | 保持 | **违反** | 保持 |
| 软链痛点消除 | 全部 | 全部 | 部分 |
| 防漂移强度 | ≥现状（含内容级） | ≥现状 | =现状 |
| 合同改动面 | 中 | 中大 | 小 |
| 与门1方向一致 | 一致 | 一致 | 相悖 |
| 为第二阶段（Release 制品）铺路 | 是（副本语义先行验证） | 部分 | 否 |

## 推荐

推荐候选 A。它是门1 两阶段路线的忠实第一步：消费仓自此只见普通文件，防漂移由「实时对照唯一真源」承接，不引入第二套锁；副本+哈希语义得到真实验证后，第二阶段把「真源」从 submodule 换成 Release 制品时，校验骨架可以直接沿用。AGENTS.md 第 5 条在本 Change 中修订为「禁止无校验的复制投影与第二套 lock」，保留原则、更新手段。
