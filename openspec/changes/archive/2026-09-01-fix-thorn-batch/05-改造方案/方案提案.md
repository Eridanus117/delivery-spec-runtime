# 方案提案

## 决策问题

九类小刺已经查清、归因已修正，剩下的不是「修不修」，而是**这一批修到哪一层**。三个候选的差别集中在三件事上：

1. 是只让本地测试稳定绿（止血），还是连路径预算与行尾产生面一起根治；
2. 受管投影里的 `runtime-entry.ts` 副本**到底算不算一个可调用入口**——这是个定位裁决，两条修法方向相反，不先裁就没法写代码；
3. 愿不愿意为了后两件事**先调一次路由表**——现行路由表对 `.gitattributes`、`.github/**`、`openspec/changes/archive/**` 三处没有任何路径前缀命中，本 Change 一旦触碰就会被档位交叉校验当场拒绝。

## 约束

- 路由表判定 `changeObject: tool-code` 走完整 `delivery-change` 档，不可自述豁免或降档。
- **档位交叉校验是硬约束**：`guard --operation verify` 会把实际 diff 按路径前缀归类，实际档位高于声明即 fail-closed。按现行表，`.omp/**` 归治理合同（档位序 30）、`.gitattributes` 与 `.github/**` 与 `openspec/changes/archive/**` 均无前缀命中而按未匹配取最重档（99），三者都高于本条目声明的 `tool-code`（20）。处置方式只有两条：本批次不碰，或按路由表自述的口径「第一次误挡就调这张表」先补前缀行。缩小改动面去迁就声明是被明文禁止的。
- CI 只在 ubuntu 上跑，四条 Windows 刺在 CI 上不可见。验收判据必须是**可复现的确定阈值**，不得退化为「重跑几次都过」。
- 本 Change 自己产出的验收证据不得再踩路径长度预算——被修的正是这条预算。
- 本轮止于方案提案。方案决策、改造方案、测试方案、实施任务在维护者表态之后才产出。

## 候选 A：最小止血包

- 方案：只做落在 `openspec/tools/**` 与 `test/**` 内、且不触碰任何合同或配置文件的九项改动——
  1. 给 `runtime-entry.ts` 的 `git()` 在 win32 上补 `-c core.longpaths=true`，与 `openspec-upgrade.ts` 已有做法对齐（治读侧误判，10、11 同时受益）；
  2. 把 `consumerSmoke` 丢弃的 `runtimeCheck.stderr` 写进 upgrade report（治「失败不可归因」）；
  3. 加一条**防增长断言**：仓内任何路径长度不得超过当前最长值（155），新增归档证据超长即测试失败——冻结预算但不改名存量；
  4. `runtime-check` 对 manifest 声明的四条受管投影跑 `git check-ignore` 断言，命中即 fail-closed（16）；
  5. `runtime-check` 断言受管投影在 git index 中的模式不得为 `120000`（17）；
  6. `sourceRootFromScript()` 找不到 manifest 时回落 `findConsumerRoot()`，让投影副本在消费仓侧可作入口（18 走路线甲）；
  7. 临时目录清理加有限退避重试（12）；
  8. 去掉版本探测的 `shell` 选项，改用平台相应可执行名直调（DEP0190）；
  9. 删除五个未用导入；`runtime-lib.ts` 的三个零调用导出**暂不删**，列为未决问题。
- 优点：全部改动落在已声明档位内，不触发任何档位前置条件，方案门当场就能进实施；一次拿掉本地测试不稳定与三处分发盲区这两个主要痛点；Review 面可按刺分组，每组都小。
- 缺点：不缩小 CRLF 的产生面（`.gitattributes` 照旧只管 `*.json`）；不缩短既有超长归档路径，只是冻结在当前值。
- 成本：九处小改动加配套断言，加一次本地全量验收。绝大部分改动在十行以内。
- 风险：入口回落若不加边界断言，真正的「未初始化」场景会被回落掩盖成另一种错误——须同批加断言钉死回落边界。
- 可逆性：高。每一项都可以单独回退，无历史改写。

## 候选 B：根治包

- 方案：候选 A 全部，再加两项——
  1. `.gitattributes` 从 `*.json` 扩展到覆盖 `.md` 与 `.ts`，从源头缩小 CRLF 进入受管投影的机会（9 尚未完成的那一半；另一半「把行尾归一化升格为 spec 显式要求」经核查已经落地，见 `03-现状/现状.md`）；
  2. 给归档证据定真正的路径长度预算（如 120 字符）并**缩名存量**，把 155 压到预算内（11）。
- 优点：真正根治。CRLF 少一个产生源；路径预算恢复有余量，未来别处再超长也不会重演。
- 缺点：三项全部触发档位前置条件——`.gitattributes` 与 `openspec/changes/archive/**` 在现行路由表中无前缀命中，必须先补表（或改条目声明并补更重档分析线）才动得了。`.gitattributes` 扩展还会在 `core.autocrlf=true` 的工作树上触发一次大面积形式化 diff，可能淹没同批次的实质改动。缩名存量归档等于改写已归档的治理证据，与「存量不迁移」的既有取向相抵。
- 成本：候选 A 加上一次路由表修订、一次行尾重写提交、一轮归档证据改名与随之而来的引用修正。
- 风险：行尾重写的 diff 面未测算；缩名存量归档可能打断既有工件里对证据路径的引用，需逐条核。
- 可逆性：中。代码可回退，但行尾重写与归档改名会在历史里各留一个大提交。

## 候选 C：收缩合同包

- 方案：候选 A 的第 1～5、7～9 项，但第 6 项改走 18 的**路线乙**——显式声明受管投影里的 `runtime-entry.ts` 副本不是可调用入口（只是给 IDE 与人看的引用副本），并把九个 `opsx-*.md` 里那 17 条写死源仓形态的命令行统一改成消费仓形态路径。
- 优点：入口定位逻辑保持单一，不引入回落分支，语义最干净；opsx 文档正文与真实可用路径一致，消费仓侧不再有「照抄即失败」的命令行。
- 缺点：改动落在 `.omp/**`，属治理合同档（30），高于本条目声明的 `tool-code`（20），必然被档位交叉校验拒绝——须先修正 `changeObject` 声明并补治理合同档的分析线，等于把本批次的立项门重走一遍。且需要为「既然不可执行，为什么还要把它投影到消费仓」给出一句明确的合同表述，否则这条投影就变成了没有理由的存在。
- 成本：候选 A 加上一次重档分析线、17 处文档改写、一条合同表述的立法。
- 风险：合同表述若写不清，下一个人会重新把它当入口调用，问题原地复发。
- 可逆性：中。文档改写可回退，但合同表述一旦立法就进入了 AGENTS.md 或 spec，撤销要再走一次立法。

## Trade-off 矩阵

| 维度 | 候选 A 最小止血包 | 候选 B 根治包 | 候选 C 收缩合同包 |
|---|---|---|---|
| 本地测试稳定绿 | 是 | 是 | 是 |
| 三处分发盲区消除 | 是 | 是 | 是（18 以收缩合同的方式消除） |
| CRLF 产生面缩小 | 否 | 是 | 否 |
| 路径预算恢复余量 | 否（冻结在 155） | 是（压到 120） | 否 |
| 是否触发档位前置条件 | 否 | 是（`.gitattributes`、归档目录） | 是（`.omp/**`，须重走重档分析线） |
| 是否改写历史治理证据 | 否 | 是（归档证据改名） | 否 |
| Review 面 | 小，可按刺分组 | 大，含一次大面积形式化 diff | 中，含 17 处文档改写 |
| 前置成本 | 无 | 一次路由表修订 | 一次路由表口径确认 + 一次重档分析线 |
| 可逆性 | 高 | 中 | 中 |
| 预计改动规模 | 九处小改动 | 九处小改动 + 两次批量重写 | 八处小改动 + 17 处文档改写 + 一条立法 |

## 推荐

**推荐候选 A，并把候选 B 的两项拆出来单独排期。** 三条理由：

一、A 已经吃掉本批次的全部主要收益。九类刺里让人真正难受的是两件事——本地测试不稳定绿、投影分发有三处静默盲区——A 全部解决，且解决方式是确定阈值而非重试玄学：`longpaths` 那一项已由受控探针验明「259 干净 / 260 报 M / 加参数恒净」，可以直接转成断言。

二、B 的两项额外收益，代价与收益不对称。`.gitattributes` 扩展的收益是「未来少一个 CRLF 产生源」，代价是一次淹没实质改动的大面积 diff 加一次路由表修订；缩名存量归档的收益是「预算恢复余量」，代价是改写已归档的治理证据。A 里的防增长断言已经能挡住「预算继续恶化」，这是当前真正需要的那一半。两项都值得做，但不值得挤在同一批里做——挤进来会让这一批的 Review 从「九个小修」变成「九个小修加两次批量重写」。

三、C 与 A 的分歧不是工程分歧，是定位裁决，而这个裁决**应当由维护者作，不该由推荐替代**。故此处只推荐 A 的工程包，18 的路线归入未决问题第 1 条；若维护者裁定「投影副本不算入口」，A 的第 6 项直接替换为 C 的做法，其余八项不受影响。

推荐不构成决定。以下未决问题任一项的裁定，都可能改变上面的推荐。

## 落地后可感知的具体变化清单

按候选 A 落地后，维护者会感知到的变化如下（按「会发生什么」而不是「改了哪个模块」描述）：

**动作变少的**

- 本地跑全量测试从「跑三次可能挂一次、挂了要重跑」变成稳定绿。「复跑两次全绿即视为通过」这条口头判据不再需要，完成标准回到「一次跑绿」。
- 升级消费仓时，不再需要手工核对四条受管投影有没有被 `.gitignore` 或本机 `.git/info/exclude` 吞掉——机器会查。
- 在消费仓里照抄 opsx 文档的命令行，不再报「Runtime 源仓缺少 runtime-manifest.json」，不需要再手工换成 `.delivery-spec-runtime/` 前缀形态。（若改裁 C，则变成另一种形态：文档正文里的命令行本身就写成 `.delivery-spec-runtime/` 前缀，同样不需要手工换。）
- bootstrap 测试不再偶发 EPERM，不需要为它重跑。

**输出变干净的**

- 每条 Runtime CLI 命令的 stderr 不再多出 DEP0190 那两行告警，JSON 输出可以直接管道给下一个命令。
- 升级冒烟失败时，报告里会多出一段具体的失败原因文本（当前只有 `runtimeStatus: 1`），不再需要靠猜或复现。

**以后会被拒绝的（新增的门）**

- 新增的归档证据文件如果路径过长（超过当前最长值 155 字符），测试会失败并点名是哪个文件。以后起 run-id 与日志名要短一点，这是维护者动作上唯一的净增负担。
- 消费仓里如果某条受管投影被 ignore 规则吞掉，`runtime-check` 当场拒绝并点名是哪条规则吞了哪条投影；以前是本机 PASS、他人 clone 才炸。
- 消费仓里如果受管投影被写成软链模式坏账（Windows `core.symlinks=false` 下的典型形态），`runtime-check` 当场拒绝；以前能带病提交。

**不会变的**

- 没有任何命令消失，没有任何工件不再产出，三道门与三个动词不变。
- 已归档的 Change 目录一个字节都不动（这正是不选候选 B 的直接后果）。
- `.gitattributes` 不变，因此工作树不会出现一次大面积的行尾重写 diff。

## 未决问题

1. **投影副本到底算不算入口**（决定 18 走哪条路，是本次唯一的定位裁决）。选「算」→ 候选 A 第 6 项，入口加回落分支，opsx 文档不动；选「不算」→ 候选 C，入口逻辑保持单一，但要改 17 处文档、补一条合同表述，并因触及 `.omp/**` 而须先修正 `changeObject` 声明、重走一次治理合同档的分析线。
2. **`.gitattributes` 是否扩展到 `.md` / `.ts`**。做 → 少一个 CRLF 产生源，代价是一次大面积形式化 diff 加路由表修订；不做 → 维持现状，行尾归一化继续是唯一防线（该防线本身已有 spec 条文与断言保护，见 `03-现状/现状.md`，故「不做」并非裸奔）。
3. **`010` / `011` 的修法组合**。三档：只治读侧（补 longpaths）／加防增长断言冻结在 155（推荐）／再加缩名存量归档压到 120。第三档要改写已归档的治理证据，与「存量不迁移」的既有取向相抵，需明确裁定。
4. **路由表是否补前缀行**。上面第 2、3 条一旦选「做」，就必须先给 `change-routing-v1.json` 补上 `.gitattributes`、`.github/`、`openspec/changes/archive/` 三处的归类。路由表自己写着「第一次误挡的处置方式是调这张表，不是关门」——本批次正是第一次误挡。裁定：现在就补（哪怕本批次不用），还是等真要碰时再补？
5. **`runtime-lib.ts` 的三个零调用导出**（`findUp`、`gitCommit`、`ensureInside`）。本仓是公开共享运行时，导出即公开面。删掉 → 公开面收窄；保留 → 需显式登记为预留 API 并说明理由，否则下次清扫还会被当成死代码。
6. **两处文档与代码的分叉是否本批次顺手修**（均落在 `openspec/intake/`，不触发档位问题）：其一，`intake/README.md` 仍写着五阶段顺序与「disposition 之后才能 promote」，而登记线已并站为两节点；其二，同一份 README 要求「存在 Issue 时记录 URL」，但 `assertSafeContent()` 的绝对路径正则会把任何 `https://` 一并拦下，带 URL 的条目无法被处置——是改正则还是改文档？
7. **档位交叉校验的空洞是否登记为独立事项**：`declaredRoute()` 在条目未声明 `changeObject` 时直接跳过核对，即「如实声明的被核对，沉默的不被核对」。这不构成降档漏洞（未声明本身按最重档过立项门），但核对面上确有空洞。本 Change 不处理，是否单开条目？
8. **`VC-039` 的断言形态是否改**（本轮撞上的新问题）：`test/contracts.test.ts` 的 `VC-039` 用 `deepEqual` 钉死了 active Change 目录的**完整集合**。这不是不变量而是点时快照——**任何人新建任何 Change，这条测试都会立刻转红**，本 Change 就是第一个撞上它的。本轮已按最小机械改动把 `fix-thorn-batch` 登记进期望集合并加注说明，未改变断言强度。裁定：维持快照形态（每次新建 Change 顺手登记），还是改为断言真正的不变量（两个早期目录不在 active、且 metrics 目录仍在）？后者更耐用但会放松一点断言强度，按本仓「保留的强校验不得削弱」的既有取向需要维护者点头。
9. **两个批次外的开放问题**（随门顺带裁，不影响本 Change 的实施）：其一，消费仓 agent-system 的工作树残留——`profiles/` 其实已在版本控制内、只是有一处未提交修改，真正未跟踪的是 `tools/sk/`（含一个约 94 MiB 的 `sk.exe`）；其二，两仓 main 分支保护规则不一致，且差异比原以为的一条更大：本仓 `enforce_admins=false`、**无任何必过 status check**、要求 1 个审阅批准，agent-system `enforce_admins=true`、五个必过 check、要求 0 个审阅批准——即立法者本仓对自己的 CI 不设硬门。
