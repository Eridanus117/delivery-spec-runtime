## 接受的后果

- **CRLF 产生面不缩小**：`.gitattributes` 仍只覆盖 `*.json`，`core.autocrlf=true` 的机器上 `git add` 继续打行尾警告。受管投影校验不受影响——行尾归一化已是 `runtime-distribution` spec 的显式要求且有断言守住。
- **路径预算冻结而非恢复**：既有最长归档证据路径 155 字符原样保留，预算上限按现状设定，只挡住继续恶化。既有归档目录一个字节不动，这是不选 B 的直接后果。
- **入口定位多一条回落分支**：投影副本可作入口，意味着 `sourceRootFromScript()` 不再是单一路径。必须同批加断言钉死回落边界，否则真正的「未初始化」场景会被回落掩盖成另一种错误。这条风险由测试承担。
- **公开面收窄**：删除 `runtime-lib.ts` 的三个零调用导出会改变本仓的公开 API 面。接受，理由是 git 历史即存档。
- **四条已知机器缺陷带病运行**：路由表缺三处路径前缀、交叉校验对未声明条目跳过、`VC-039` 是点时快照、intake README 与代码分叉——全部保留原状。接受，理由是它们将随工作流重设计一并处置，且已在台账记录在案。
- **本 Change 自身受路径预算约束**：验收证据的命名必须短，这是新增的自我约束。

## 拒绝方案

- **候选 B 根治包**：拒绝。额外收益（少一个 CRLF 产生源、路径预算恢复余量）与代价（一次淹没实质改动的大面积形式化 diff、一次路由表修订、改写已归档的治理证据）不对称；且 A 的防增长断言已经拿到「预算不再恶化」这一真正需要的一半。`.gitattributes` 扩展顺延至工作流重设计。
- **候选 C 收缩合同包**：拒绝。其与 A 的分歧是定位裁决而非工程分歧，维护者裁定「投影副本算可执行入口」，C 的前提即不成立。附带避免了改动 `.omp/**` 所需的重档分析线与 17 处文档改写。
- **批次层面 B 拆三个 Change**：拒绝（方案提案阶段已论证）。要付三次完整交付仪式，且会切开同根因的三条刺。
- **批次层面 C 走 light-change 快车道**：不可行。路由表判定 `tool-code` 必走完整档，属门禁问题而非取舍问题。
