# 需求理解

## 目标

先消除实时消费仓升级会修改 Runtime submodule 的确定性风险，使现有锁定运行时保持不可变。这个 Change 是 Runtime 自举升级实践的第一步，不负责实现完整候选版本导入框架。

## 术语

- **实时仓**：实际保存项目或资产 Spec 的仓库，例如 `agent-system`、`webcoding-spec`、`work-spec`。
- **Runtime submodule**：实时仓中的 `.delivery-spec-runtime` gitlink checkout。
- **Runtime Update**：当前 `runtime-entry.ts runtime-update` 包装的官方 `openspec update`。
- **受控升级**：后续独立 Change 中，在隔离临时目录生成和比较候选上游输出，不写实时仓。

## 范围

- 让实时仓中的 `runtime-update` fail closed，且在启动官方生成器之前失败。
- 为目录软链覆写路径增加真实行为回归测试。
- 修正 `/opsx-update` 和 Runtime 说明，删除不成立的“update 后恢复投影”承诺。
- 建立 Runtime 自身仓内 OpenSpec 配置和本 Change 资产。

## 非范围

- 不在本 Change 中升级 OpenSpec `1.10.0`。
- 不在本 Change 中实现 current/candidate baseline、fragments renderer 或完整升级报告。
- 不迁移既有消费仓资产，不改变三个相对软链合同。
- 不修改 OpenSpec 核心代码。

## Change 拆分

1. 当前 Change：`prevent-live-runtime-update-mutation`，关闭实时仓写入风险并建立回归合同。
2. 后续 Change：`establish-controlled-openspec-upgrades`，实现隔离生成、upstream/local delta、候选版本合同与多消费仓 smoke。

## 已确认结论

- 改造目标仓是 `delivery-spec-runtime`，不是 `agent-system`、`webcoding-spec` 或 `work-spec`。
- 实施单元按 OpenSpec Change 拆分；PR 只是每个 Change 的代码交付载体，不代替 Change。
- Runtime 用仓内 OpenSpec + 版本化文档治理自身演进。
