# 方案提案

> 历史迁移：本 Artifact 根据已合并 PR #1 的原始需求、技术方案、实现和验收证据回填，用于把 v4 Change 纳入 v5 生命周期合同；不改写原决策语义。

## 候选 A：允许实时更新并依赖备份回滚

消费仓调用 Runtime Update 时先备份 submodule 和受管软链，运行官方生成器后在失败时恢复。它保留操作入口，但生成器可能直接覆写共享 Runtime，备份与并发失败边界难以证明。

## 候选 B：实时仓硬拒绝，升级只在 Runtime 独立 Change 中执行

`runtime-entry.ts` 在启动任何官方生成器前拒绝 `runtime-update`，保持父仓 gitlink、Runtime submodule 和受管软链不变；升级需求进入 Runtime 仓独立 Change，执行隔离评估和审查。

## 候选 C：仅为维护者保留强制开关

普通消费仓拒绝，但通过环境变量或 CLI flag 允许维护者绕过。操作灵活，却形成难审计的后门，无法保证实时仓的单一 fail-closed 不变量。

## Trade-off 矩阵

| 维度 | 候选 A | 候选 B | 候选 C |
|---|---|---|---|
| 实时仓零写入 | 差 | 优 | 差 |
| 失败边界 | 差 | 优 | 中 |
| 操作便利性 | 中 | 中 | 优 |
| 审计一致性 | 差 | 优 | 差 |
| 长期维护风险 | 高 | 低 | 高 |

## 推荐

推荐候选 B。它把危险行为从共享实时仓彻底移除，并把升级责任收敛到 Runtime 独立 Change。PR #1 已按该方案实现并验收。

## 未决问题

无。拒绝路径、官方生成器可用场景、Commands 摘要、父仓 gitlink、Runtime 工作树和三个消费仓 smoke 均已有 PASS 证据。
