# 改造方案

## 决策

建立两条互相隔离的能力：

1. **Commands 确定性渲染**：Runtime 自己维护结构化真源并生成 `.omp/commands`。
2. **OpenSpec 候选评估**：官方 current/candidate 只在临时根运行，输出三类 delta、CLI probes 和消费仓 smoke 报告。

两者共同形成升级门禁。评估器不会修改 Runtime source；维护者依据报告修改 fragments 和 manifest，再由 renderer 与合同测试验证。

## 目标文件布局

```text
.omp/
├── command-sources/
│   ├── manifest.json
│   ├── runtime-preamble.md
│   └── bodies/
│       └── opsx-*.md                 # 九个命令独有正文
└── commands/
    └── opsx-*.md                     # 确定性渲染物
openspec/
├── contracts/
│   ├── openspec-cli-probes.json
│   ├── openspec-upgrade-request.schema.json
│   └── openspec-upgrade-report.schema.json
└── tools/
    ├── render-commands.ts
    └── openspec-upgrade.ts
test/
├── command-renderer.test.ts
└── openspec-upgrade.test.ts
```

## Commands 渲染合同

### Manifest

`manifest.json` 使用精确字段：

- `schemaVersion`
- `commands[]`：`id`、`description`、`body`

命令 ID 唯一、ASCII kebab-case；body 必须是 `bodies/` 下安全相对路径；排序固定。manifest 不接受未知字段、绝对路径、`..`、重复 ID 或缺失 body。

### Renderer

```text
render-commands.ts write --runtime-root <path>
render-commands.ts check --runtime-root <path>
```

渲染格式固定为：frontmatter description、一个空行、公共 preamble、一个空行、body、单个结尾换行。`write` 原子写入并删除不在 manifest 中的受管 `opsx-*.md`；`check` 零写入，逐路径报告 missing/extra/modified。

迁移先证明由 current sources 渲染出的九个文件与现状逐字节一致，再单独吸收 1.11 `opsx-explore` 规则。合同测试禁止直接漂移 rendered Commands。

`opsx-explore` 不机械复制上游 plain ASCII 示例。OMP 能渲染 Mermaid，因此结构、状态、流程和依赖图使用 `mermaid` fenced block；保留“禁止 Unicode 线框字符”的兼容边界，只有外部目标不能渲染 Mermaid 时才降级为简洁 ASCII。

## 升级请求与入口

```text
openspec-upgrade.ts evaluate --request <request.json>
```

请求精确字段：

- `schemaVersion: 1`
- `currentVersion`、`candidateVersion`：精确 `x.y.z`
- `runtimeRoot`：Runtime checkout
- `evidenceRoot`：当前 Change 的 run 目录
- `consumers[]`：`name` 与绝对 `path`

工具固定使用 `npm exec --yes --package @fission-ai/openspec@<version> -- openspec <argv>`，通过 executable + argv 调用，禁止 shell。测试通过临时 PATH 注入 fake npm，不增加任意命令配置面。

## 隔离生成流程

```text
完整解析请求与路径
→ 摘要 Runtime/真实消费仓受管状态
→ mkdtemp 创建 current/candidate/fixture 根
→ 分别用精确版本初始化 OMP 并生成 Commands
→ 执行声明式 JSON probes
→ renderer check Runtime current
→ 构造 Runtime candidate 渲染结果
→ 生成三类 delta 和 SHA
→ 构造空白 Git fixture 验证候选 Runtime/CLI
→ 克隆三个消费仓到临时 Git fixture
→ 将 candidate Runtime 作为临时 submodule commit 注入
→ 通过临时 PATH 注入 candidate CLI
→ 执行 runtime-check 与 JSON probes
→ 复核真实仓摘要和 Git 状态不变
→ 原子写入 evidence report
→ finally 清理全部临时根
```

官方生成器的 cwd 永远位于工具创建的临时根。`runtimeRoot` 和消费者路径只允许读取、摘要和本地 clone；它们不能作为 update/init cwd。

## 三类 delta

每类 delta 保存：

- `from`、`to` 的版本/来源标识；
- 规范化 POSIX 相对路径；
- `changeType`: `added | removed | modified | unchanged`；
- 两侧 SHA-256 或 `null`；
- 行级统计 `additions`、`deletions`。

报告必须包含全部九个路径，包括 unchanged，防止文件集合静默变化。正式 `1.10.0 → 1.11.0` upstream delta 预期只有 `opsx-explore.md` modified；正式 run 若不符合预期，停止并重新审阅，不硬编码忽略。

## CLI JSON probes

`openspec-cli-probes.json` 声明：

- probe ID；
- argv 数组；
- fixture 类型；
- 期望退出码；
- required fields：JSON path 与类型。

首批至少覆盖：

1. `status --change probe --json` 的 Change 状态结构；
2. `status --all --json` 的候选新增能力（candidate-only capability 以版本条件声明）；
3. `show probe --json` 的稳定结构。

报告只保存结构签名、字段类型和退出状态；不复制 artifact 正文。

## 消费仓 smoke

- 输入固定为 `agent-system`、`webcoding-spec`、`work-spec` 的显式 `name=path`。
- 使用本地 Git clone 创建临时副本；所有候选 gitlink、软链和 CLI PATH 只存在于副本。
- candidate Runtime 先复制到独立临时 Git 仓并提交，消费仓副本的 gitlink 更新到该临时 commit 后再运行 `runtime-check`。
- 报告仅保留仓名、原 HEAD、候选 Runtime SHA、命令状态、required fields、受管摘要前后值。
- 任何真实仓 Git 状态或受管摘要变化均为 critical。

## README 重写

README 不再以“内容清单 + 零散说明”为主，重写为以下阅读路径：

1. Runtime 解决什么问题，以及不保存哪些消费仓/业务资产；
2. Mermaid 架构图：父仓 gitlink、Runtime submodule、三条相对软链；
3. 消费仓接入与 clone/update 顺序；
4. Runtime 不变量和 fail-closed 语义；
5. Commands 结构化真源与 renderer write/check；
6. 受控升级 request JSON、三类 delta、CLI probes 和结果解释；
7. 本仓自治理、开发验证和 PR 交付。

README 示例必须可复制执行，但不能暗示在实时消费仓运行官方 `openspec update`。


## 1.11 提升决策

若正式 run 全部通过：

1. 在 `opsx-explore` body fragment 吸收写入前单独明确确认和配置文件写入范围；将上游 plain ASCII 偏好适配为 OMP Mermaid，并保留非 Mermaid 目标的简洁 ASCII 降级；
2. renderer 更新 `.omp/commands/opsx-explore.md`；
3. `runtime-manifest.json` pin 更新到 `1.11.0`；
4. manifest/合同测试同步更新；
5. public candidate allowlist 纳入 `.omp/command-sources`、renderer、评估器和新合同。

任一门禁失败：保持 `1.10.0`，保存失败 run，本 Change 不能 PASS。

## 风险与控制

| 风险 | 控制 |
|---|---|
| fragments 形成第二份整文件复制 | 公共 preamble 唯一；body 只含命令独有内容；rendered 文件禁止手改 |
| npm 执行版本不确定 | 精确 SemVer；报告保存实际 `--version`；不接受 tag/range |
| 网络失败被误判兼容失败 | 单独分类 setup failure；保持 pin，不写 PASS |
| 消费仓业务内容进入报告 | 只输出预定义字段、摘要和状态；测试用敏感哨兵断言报告不含正文 |
| 临时 submodule 与 gitlink 不一致 | 在 fixture 内提交 candidate Runtime 和父仓 gitlink，再执行 runtime-entry |
| 真实仓被写 | 前后摘要与 Git status 双重断言；生成 cwd allowlist 只接受工具临时根 |
| 1.11 上游实际结果变化 | 正式 run 记录 package version、SHA 和完整 delta；预期不匹配立即停止 |
